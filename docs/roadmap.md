# Roadmap

Every phase in Orchard's original development plan — the full build-out of everything [`docs/spec.md`](spec.md) describes — is complete. [`CHANGELOG.md`](../CHANGELOG.md) is the authoritative record of what got built and how each phase was verified; this document is the other direction: what's deliberately *not* built yet, and why.

Nothing below is a missed gap. Each item was looked at directly, during the phase most likely to have needed it, and set aside on purpose — either because `spec.md` itself names it as a stretch goal not worth the complexity until real use asks for it, or because it turned out to be genuinely new, unscoped work once concurrent cycles made it relevant. That distinction is called out per item below.

## Deliberately deferred

These were considered and explicitly set aside, in most cases directly in `spec.md`'s own text. Revisit only if real use actually surfaces the need — not speculatively.

- **Native file storage for Task resources.** Spec's own bet is that link-only (a URL to wherever the file already lives) holds up in practice. Revisit only if that friction actually shows up for a real community.
- **Real-time multiplayer editing of unowned Spatial-planning Placements/Zones, and snap-to-boundary/grid drawing tooling.** Both explicitly deferred in the original spatial-planning design pending real use surfacing an actual need — the propose→pending→approve flow that did get built handles the common case (a member adjusting their own stuff) without needing either.
- **On-site mode's resync/offline-first behavior.** Explicitly out of scope for v1 — "if a request fails, retry it once the connection's back," no PWA/service-worker layer.
- **Multi-tenancy.** Explicitly decided against — Orchard is single-tenant, self-hosted per Community, and that's a deliberate architectural stance, not a stopgap.
- **A public cross-deployment Task Pack registry/marketplace**, beyond the JSON-file hand-off Task Packs already support.

## Real, scoped-but-unbuilt work

Unlike the above, these are genuine gaps — real design questions worth a session of their own once a community's actual use asks for them, not things spec.md ruled out.

- **`ModuleState`'s richer off/testing/on rollout.** Only the flat on/off list got built. The Tier-scoped `testing` state spec describes — a module visible-but-labeled to everyone, or scoped to a "Playtesters"-style Tier, for a soft launch of a new module — is real, unscoped work.
- **A "community savings" concept** — a persistent community-level pot a cycle can move money into or draw from. Worth having now that Budget, Event scheduling, and Spatial planning are all fully independent per Cycle (see `spec.md`'s "Concurrent cycles & view scope"): nothing today lets value or state span cycle boundaries on purpose. Not yet scoped — nothing has asked for it concretely.
- **Calendar's "layers" never got a real selectable/toggleable UI, cycle-nested or otherwise.** Today's `/calendar` merges every dated thing — phase boundaries, milestones, calendar events, assembly deadlines, and more — into one flat list with no filter or show/hide control, and no cycle-based grouping. Spec's own data model even names a "community-wide bucket" for a cycle-independent `CalendarEvent`, but that distinction was only ever specified, never actually built — a cycle-linked and a cycle-independent event render identically today. Selectable layers, nested by cycle (a concurrently-open cycle's items grouped and independently collapsible), is a coherent redesign worth doing now that concurrent cycles are real — today's flat list stops reading clearly once two cycles' worth of milestones and deadlines mix together.
- **Cycle-linked Recruitment applications, an "accepting applications" toggle, and baseline vs. per-cycle questions.** An application should link to the specific Cycle it's for, not just to the community in the abstract — which would also give Recruitment's pipeline view an honest per-cycle remaining-capacity number instead of today's single-cycle heuristic. This enables the real need behind it: some cycles (a members-only Reunion weekend, say) shouldn't be open to outside applicants at all. Sketched direction: a `Cycle.acceptingApplications` flag, off by default for a cycle type like Reunion; if more than one cycle is currently accepting, the public application flow asks the applicant which one it's for before anything else. Since joining *any* cycle as a new applicant means joining the community itself, there'd be a baseline set of application questions every applicant answers regardless of which cycle they pick, plus optional cycle-specific supplemental questions layered on top once a cycle is chosen — one submission, two question sources merged, the same field-shape reuse pattern the Form/ProfileQuestion builder already established elsewhere. Open questions: the exact schema shape for "baseline Form plus a cycle's own supplemental questions" (most likely a second, smaller question set attached to the Cycle itself, rather than a second Form entity); whether evaluator/decision-rule configuration (today entirely community-wide) should ever vary per accepting cycle. Explicitly distinct from an **existing** member joining a cycle, which already goes through Participation declarations, not this application funnel at all — this only affects prospective new members.
- **A finer-grained, subset-based permission model for tasks.** Every access gate today is all-or-nothing per module — holding the gating task grants everything that module's owner can do. A more expressive alternative exists: a task's grant could specify a *subset* of a module's permissions (e.g. a task that can approve programme slots but not budget spend), and coordination's own single bundled permission (waive requirements, nominate, see the escalation view) could in principle split the same way. Module-level granularity is almost certainly adequate for most communities' actual needs, so this stays a documented possibility rather than a scoped phase — worth a real look only once a specific community's use case actually needs it. The schema already reserves storage for this (`PermissionGrant.permissionKey`, null today meaning "the whole module") — a future phase would define real keys and teach specific enforcement checks to read them, not redesign the table.

## Before real member data goes live

Not a build item — a legal/organizational step outside the codebase, but a real blocker before any real Community runs this with actual member data. Peach Please, the reference deployment, currently has no legal entity behind it (a French "association de fait"), which means GDPR/data-protection liability for whoever sets up and runs the server falls personally on that individual, not on any organization. Resolved direction: incorporate as a French *association loi 1901* (free registration, roughly five business days, full separate legal personality) before real member data goes live — the incorporation itself lives in the association's own governance docs, not here. Once a real legal entity exists, its board — not just whoever holds the sysadmin task — needs to be the one actually deciding what data gets collected and why; see `spec.md`'s **Data governance** subsection (under Sensitive data) for how that's meant to interact with the platform's task-based model. Any other community self-hosting Orchard should work out its own equivalent before going live with real member data — this isn't a code concern, but it's a real one.

## A note on how this list is maintained

This file tracks *what's next*, not *what happened* — when an item above gets built, it moves out of here and into `CHANGELOG.md` as a normal phase entry, the same way every item through Phase 69 already did. New ideas that come up through real use of a deployed Community get added here once they're concrete enough to describe, not before.
