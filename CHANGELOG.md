## Unreleased: permissions a Community can open to everyone, and a Recruitment pipeline that can finish

Every permission in the system was task-gated: a capability existed because whoever currently held a task carrying a `permission_grant` row could do it, and nobody else could. That is a good default — authority you can point at, that goes away when the person leaves. But it has one failure mode with no way out. A Community that wants everyone to be able to evaluate applications, or draw the Zone plan, or close the budget has no way to say so, and the alternative — inventing tasks and claiming them so a resolver returns true — is not a setting anyone would find.

`open_permission_grant` adds that setting: one row per `(community, module)`, meaning *this Community has decided this capability is open to all its members*. It is deliberately a separate table rather than a nullable `permission_grant.task_id`, because every resolver reaches authority by joining a grant's task id to a `taskAssignment` — a `NULL` there would match nobody and grant nothing while looking correctly configured, which is the worst direction for a security setting to fail in. Thirteen of the fourteen modules can be opened this way; `backstop` cannot, because its authority is a *named person to notify* and a backstop with no name has nothing to do. Its checkbox is absent and says why.

The second half is what opening Recruitment actually fixes. `recruitmentEvaluatorCount` defaults to two, `recruitment` is single-cardinality per scope, and `computeRecruitmentOutcome` refuses to evaluate below the threshold — so a Community with one holder could never satisfy any rule above the mandatory fallback, and every application parked at `decision_pending` forever, surfacing only as a "stuck waiting on you" dashboard line. The data model always wanted an evaluation *panel* (`evaluation.evaluatorId` is per-evaluator); the access model permitted exactly one person. Opening the module is the fix, and `tests/open-permissions.test.ts` now has two ordinary members file evaluations and reach a `proceed` outcome, which was unreachable before.

Opening a module also had to not break the things that read "is this set up?". Eleven sites were using *grant existence* as a stand-in for *module configured*, and each failed differently: an open `conflict_team` left members able to review conflicts but **unable to file one**; its nav item disappeared; the recusal picker went empty while the recusal action itself worked; the Spatial-planning page told everyone "nobody can draw or edit"; and open Recruitment silently stopped scheduling intro calls and accompaniment tasks, because both take their `branchId` from the granting task and a member has no branch to fall back on. That last one is reported rather than papered over — inventing a branch would file a real poll and a real task under an unrelated one — and the hub says so.

Two smaller things fell out of doing it honestly. The needs-action lists were per-actor by construction, with copy in the second person ("Budget needs *your* attention"), so opening a module put everyone's outstanding work in everyone's feed and multiplied the nav badge; they now split `personal` from `shared`, where the distinction is **consent, not headcount** — a task with `capacity: 3` is deliberate redundancy and its holders each keep a personal item. And the Access & permissions tab never showed who actually held a task, even though `capacity` is the real control on that and nothing in the permission layer read it; each row now shows the holders by name up to three and a linked count above that.

Still deliberately not done: opening a module does **not** unlock a sensitive field gated to that module's grant. That coupling is real and invisible, and whether it should compose is a separate question about profile questions and consent — being worked out on its own.

## Unreleased: a phase you can read at a glance, and a number that stops being a number

The phase list on `/participation` rendered each phase's entire authoring form inline — two bordered date fieldsets with a segmented control apiece, a "Save dates" button, and a module-picker row — and buried the phase itself underneath. With a handful of phases the section became a wall of controls, and the one thing you'd come to check (when *is* this phase?) was the thing you had to read past the form to find. The rules below are all consequences of taking the summary seriously enough to write.

- **Each phase is now two lines and an `Edit`.** The card states its resolved date range, then says where it sits relative to the event in words; the date and module controls only mount when you ask for them. That's the `<details>`-for-edit rule the design conventions already set on every other form in the app — the phase view was the last surface still violating it. A pinned module moves from an invisible dropdown value to a `Tag` in the card header, because it changes the nav for everyone arriving while that phase is current and was otherwise only discoverable by opening the form that held it. The date range carries a shared year once ("Sep 1 – Sep 14, 2027") so a scannable list gives you a date rather than a repeated year.

- **The stored recipe is read out loud, and there is now one copy of the prose.** `src/lib/dates/describe.ts` replaces two near-identical inline formatters — this page's, and `tasks/[id]`'s milestone footer — both of which printed the raw machinery: `-4 day(s) from the event's start`, `0% of the way through the event`. Three rules, each because the number is a poor description of the day it points at:
  - **A negative offset is "before", a positive one is "after."** The sign is carried by the word, so nobody has to read a minus sign as a direction, and "1 day" is no longer "1 day(s)".
  - **A proportion is never printed as 0% or 100%.** Those aren't "the start" and "the end" of anything — they're just the first and last day of the event, which now says so. This is not an exotic case: `inferRelativeDate` compares strictly, so a phase beginning on the event's *first* day is stored as a `between` at 0, and `normalizeBoundary` re-bases to one every time the parent span changes.
  - **Zero days from an edge is the edge itself**, so "0% through the event" and "0 days after the event starts" — two different stored recipes for the same instant — now read as the same sentence.

- **Rounding a percentage needed a clamp, and finding that out was the point of checking.** The first pass rounded the proportion to a whole percent and *then* tested for 0/100, which quietly turns "0.27% of the way in" into "the first day" — a false claim about a phase that starts the day after the event does, and reachable on any event longer than a few months. The edges are now recognized by the stored value being *exactly* 0 or *exactly* 10000, and the displayed percent is clamped into 1–99 so the rounding can't walk a real proportion back out onto an edge. The exact date is on the line above regardless.

- **"A date you set by hand" was being reported about phases with no date at all.** `EMPTY_BOUNDARY` is itself `dateType: "absolute"`, so an unset boundary and a deliberately hand-typed one are identical across the recipe fields — the resolved date is the only thing telling them apart. Caught by rendering real authoring flows end-to-end (type a date → `inferRelativeDate` → stored recipe → printed prose) rather than hand-written fixtures: a phase with one boundary and no other claimed "ends a date you set by hand". The shared helper therefore takes the resolved date as part of its input — a milestone row has no cached `date` column the way a Phase boundary does, so `tasks/[id]` threads its `resolvedDate` in under the shared shape's name — and an unset boundary now reads "The end isn't set yet."

  Two things deliberately left alone. The **storage** is unchanged: 0 and 10000 remain perfectly good stored values, and collapsing them at write time would break the recipe-preserving edit path (`boundaryForEditing`) and the canonical re-basing in `normalizeBoundary` for no gain — the rule is about what gets *said*, not what's kept. And the **inference** is unchanged, so a phase entirely before the event still reports both edges against the start ("Starts 4 days before the event starts, ends 1 day before the event starts"); the repetition is honest about where the offsets are anchored, and eliding it with a pronoun would have made each line depend on the one above in a list people scan.

  Verified by `tests/dates-describe.test.ts` (13 cases pinning each rule, including the two-recipes-one-instant equivalence and the clamp at both ends), the existing `dates-resolve`/`date-display` suites, `tsc`, `eslint`, and a clean `next build`. Not verified in a browser: this working tree carries uncommitted migrations `0063`–`0074` that the local Postgres has never been migrated to, so every DB-backed test and the running app both fail on `cycle_indicators_enabled` regardless of this change — pre-existing, and reproduced on a clean stash to confirm it.

## Member competences: guided tags, language proficiency, and trait-based matching

Standalone new work, not a continuation of the phase sequence above — no `docs/development-plan.md` entry, no phase number. `member.tags` had always been meant to double as skills, interests, *and* languages (`docs/spec.md`'s own member sketch said so), but only ever got built as one flat, unnormalized `text[]` a member edits at `/profile` — no vocabulary (so "Spanish"/"spanish" silently failed to match each other), no onboarding step despite spec explicitly describing one ("the member defines their own tags and availability; this is the matching input"), and no way to record a language's proficiency at all. Coordinators need this for two different jobs — finding someone with a specific skill (search) and surfacing good-fit tasks to a new member who doesn't know what to pick (ranked suggestion) — and one flat tags array can't do both well at once.

**Guided tags**: `/profile`'s tags input, and both task-tag inputs (`/propose`, proposal activation), now suggest from a combined member+task tag vocabulary (`src/lib/tags.ts`'s `listAllDistinctTags`) via a plain `<datalist>` — zero client JS, still plain free text underneath, so nothing existing that reads `member.tags`/`task.tags` needed to change.

**Language & proficiency**: a new `member_language` table (language, one of basic/conversational/fluent/native) — repeatable, unlike a `ProfileQuestion` answer, which is why it's its own table rather than a reuse. Editable at `/profile` (add/delete, no admin gate, same self-service posture as tags/contact methods). The `language` Requirement type now checks this table (case-insensitive, any level) instead of `member.tags` — a real behavior change, so every existing language-Requirement test was updated to set up a `member_language` row instead of a `tags` array.

**Trait axes — the bigger addition**: bipolar scalar dimensions (e.g. "wants direction" ↔ "wants independence"), set on *both* members (their own stated preference) and tasks (a proposer's suggestion, reviewed at activation), compared by proximity to rank onboarding's task suggestions. This is deliberately distinct from tags, which stay a search/filter tool rather than the primary suggestion signal now that axes exist. A new `trait_axis` registry (`communityId`, `key`, `lowLabel`/`highLabel`, optional 5 `optionLabels` to render labeled choices instead of a generic scale, `askAtOnboarding`, `sortOrder`, `archivedAt`) is admin-managed at `/settings`'s Profile & Privacy tab, mirroring `ProfileQuestion`'s own CRUD pattern exactly — a registry rather than hardcoded columns/enum, so the exact axis list can change without a migration. Scale convention: integer -2..2 (5-point). `member_axis_value` and `task_axis_value` hold the actual positions, one row per member/task per axis they've set — except the one axis named `commitment_preference` (one-off ↔ ongoing/ownership), which has no `task_axis_value` row at all: its task-side value is derived live from the existing `Task.effort` enum instead (`one_off`→-2, `ongoing`→0, `owns_a_thing`→+2), since duplicating what's already on every task would drift.

The Dashboard's onboarding panel gains a new "How do you like to work?" section rendering whichever `askAtOnboarding` axes this member hasn't answered yet (`listOutstandingOnboardingAxes`) — kept deliberately short (3 axes is the working default) since more than that is too much for one first-session screen; every other axis is still settable any time at `/profile`, alongside the 3 onboarding ones (re-editable there too, not one-shot). A new shared `AxisScaleField` component (plain radios, no client JS) renders either mode. Task-side suggestions reuse the in-flight `suggested*` pattern already built for `suggestedTags`/`suggestedEffort` on `TaskProposal`: a new nullable `suggestedAxisValues` jsonb column, offered on `/propose`'s "Add more, if you know it" section, shown (and fully overridable) again at activation, written into real `task_axis_value` rows by `activateProposal` — mirroring exactly how `suggestedTags` becomes `task.tags` today. Tasks created through any other path (`subtasks.ts`, recruitment's accompaniment task, scheduling-poll auto-tasks, the `/api/tasks` route) simply start with no axis values, same as they already start with empty `tags` — no new UI needed there, and a task with no axis data just doesn't contribute to axis-proximity ranking rather than breaking anything.

`listTaskFitSuggestions` (`src/lib/onboarding.ts`) changes from "tag overlap OR a satisfied individual_gate Requirement, first N matches in arbitrary query order" to computing an internal (never displayed, never serialized) score per included candidate — average proximity across every axis both sides have a value for, plus a flat boost for tag overlap and for a satisfied gate — and sorting by it before taking the top N. Inclusion is now three-way (tag overlap, gate fit, *or* at least one shared axis), a real widening from the old two-way test. This is a deliberate reversal of that function's own prior comment claiming ranked suggestion was "permanently out of scope, same line Phase 50 draws" — confirmed with the user that what's actually meant to stay out of scope is *automatic assignment*, never internal scoring used only to order a surfaced list; nothing here gates a claim or picks anyone automatically. `docs/spec.md`'s matching MVP-deferral section and its Member/Requirement/onboarding sketches were updated to say so, rather than left stating the opposite of what's now true.

**Availability** (how much time someone has *this phase*, as opposed to trait axes' stable style preferences) needed no new code at all — `ProfileQuestion.feedsCapacitySignal` plus `/coordination`'s "Availability" table already implement it end to end, just never configured for a real question in this deployment before. Kept as a distinct signal from the new `commitment_preference` trait axis on purpose: one is a fluctuating capacity number, the other is a stable "when I do take something on, do I want it quick or ongoing" preference — collapsing them would lose one or the other.

Two new migrations (`member_language`; `trait_axis`/`member_axis_value`/`task_axis_value`/`task_proposal.suggested_axis_values`), both purely additive. 22 new tests (`tests/member-languages.test.ts`, `tests/trait-axes.test.ts`, plus extensions to `tests/onboarding.test.ts` and `tests/proposals.test.ts` covering axis-ranking order, axis-only inclusion, the commitment-preference/Effort special case, and `suggestedAxisValues` flowing through activation into real rows) — 1101 total passing, `tsc`/`eslint` clean.

Manually verified end-to-end against the real Docker Compose stack, against this deployment's real accumulated data: created all 7 real trait axes (autonomy, structured↔creative, desk↔physical, solitary↔social, general↔precision, detail↔big-picture, commitment preference) through the new `/settings` UI; confirmed the 3 onboarding-flagged axes rendered on a fresh member's dashboard, saved one, and confirmed it correctly dropped out of the outstanding list on reload while still showing (pre-filled) at `/profile` alongside the other 4; added a language at `/profile` and confirmed the tags `<datalist>` populated from real existing member/task tags; submitted a real proposal with suggested tags + a suggested `desk_physical` axis value, confirmed the activation form defaulted from that suggestion, activated it, and confirmed via direct DB query that the real task carried the right `task_axis_value` row; confirmed the dashboard's "Open tasks that might fit you" correctly surfaced that exact task once the member's own tags and axis answer matched it. All artifacts (the 7 axes, the test member's tag/language/axis answers, the activated task) left in place as real, working configuration rather than reverted — the axes especially are the actual intended feature content, not incidental test residue.

## Assembly agenda-item duplication, a board-card layout overflow, and missing context for Assemblies/Input rounds

Standalone bug fixes and copy, not a phase — reported by a real user (Leaf) testing Assemblies and the board for the first time.

**Assembly agenda items could be added more than once per click** — `assemblies/[id]/page.tsx`'s "Add to agenda" button was a plain `<button type="submit">` inside a Server-Action `<form>`, with no pending-state guard, so a slow round-trip (or an impatient double-click/double-Enter) fired `addAgendaItem`'s unconditional insert more than once for the same submission. New `src/components/ui/SubmitButton.tsx` (a `"use client"` wrapper around `useFormStatus`, disabling itself and swapping in a pending label for the duration of its own form's submission) fixes it at the reported form; confirmed by three rapid clicks against a real Postgres producing exactly one `assembly_question` row.

Fixed to match the wrapping row already established one line up in `TaskCard.tsx`; confirmed down to a 320px viewport.

**Assemblies had no explanation of its own phases or what an "agenda item" is** — a member creating one for the first time had nothing beyond a bare form. Added a "What's an Assembly?" `<details>` block to the assembly detail page (right where the phase/agenda-item confusion was reported) and expanded the propose-Assembly page's own copy, both grounded in `docs/spec.md`'s own "Propose → agenda → notice → vote → close" language rather than freely paraphrased. No schema or migration. Manually verified end-to-end against an isolated Docker build (its own image, a disposable Postgres, never the live deployment) — logged in, created a test Assembly, triple-clicked "Add to agenda," confirmed exactly one row via a direct DB query; resized the board to 375px and 320px and confirmed the Park row wraps cleanly instead of overflowing.

## Budget: line-item multipliers, per-branch tracking, a contribution balance, and a structured entry form

Standalone, not a phase — a direct response to real usage feedback (also from Leaf): budget line items had no way to express "8 tables at $50 each" or "$10 per person," proposals couldn't be broken down by which Branch they were for, and there was no way to see whether pledged contributions actually covered costs.

**Line-item multipliers** — `BudgetLineItem` (the shape shared by `BudgetCycle.fixedCosts` and `BudgetProposal.lineItems`) gains two mutually-exclusive optional fields: `quantity` (a plain manually-entered count) and `perAttendee` (scales live off however many members currently have Participation `coming` for the BudgetCycle's linked real Cycle, via a new `getBudgetCycleAttendeeCount`). New `lineItemQuantity`/`lineItemTotal`/`sumLineItems` helpers (`src/lib/budget/cycles.ts`) compute a line item's real contribution; `getBudgetVotingView` now recomputes every proposal's live total against the *current* attendee count on every read rather than trusting `budgetProposal.totalAmount`'s write-time snapshot, so a perAttendee item's contribution stays accurate as Participation answers come in, right up through confirmation. The mutual-exclusivity constraint is enforced both by a zod `.refine()` (for Server-Action callers) and by a new `requireValidLineItems` re-check inside the lib functions themselves (for direct lib callers, e.g. tests) — the zod-only version silently passed for a direct caller until a test caught it live.

**Per-Branch tracking** — any line item, fixed cost or proposal item, can now carry its own optional `branchId`, independent of (and overriding, for display) `BudgetProposal`'s own top-level default branch — covering a single proposal that spans more than one Branch. `requireValidLineItems` validates every referenced Branch belongs to the actor's Community in one batched query. The Budget page computes a live "requested/confirmed budget by branch" rollup (fixed costs plus either every currently-submitted proposal's items, or just the confirmed set once the cycle is `confirmed`) directly from already-loaded data, the same posture `fixedTotal`/`proposalsTotal` already took rather than a new lib function.

**Contribution balance** — `getBudgetVotingView` now sums every non-null `contributionSignal` vote into `totalPledged`/`pledgeCount`, and (once a cycle is `confirmed`) computes `confirmedTotal`/`confirmedBalance` against the actual funded set. Surfaced as one clear "pledges leave a $X surplus/shortfall" summary line, colored success/danger — a deliberately simpler design than an earlier per-rank "balance if funded to here" column, dropped after looking at Open Collective (open-source; leans on one always-visible balance line, not a detailed per-transaction projection) as prior art before settling on the shape.

**A structured line-item entry form replaces the old `label|amount` textarea convention** — new `LineItemsEditor.tsx`, a `"use client"` component modeled directly on the existing `FormBuilder.tsx`/`FieldShapeEditor.tsx` add/remove-row pattern (itself already precedent for exactly this shape, not a new exception to this codebase's mostly-server-rendered posture): local row state mirrored into one hidden JSON input, still submitted through the same plain `<form action={serverAction}>` as before — `actions.ts`'s new `parseLineItemsJson` replaces `parseLineItems`'s pipe-delimited text parsing with a straight `JSON.parse`, feeding the same Zod schemas unchanged. Each row is Label/Amount/a single multiplier select (×1, a fixed quantity, or × attendees — one control, not two independent checkboxes, after Splitwise's own team declined to ship quantity multipliers on itemized bills specifically over the confusion risk of stacking multiplier types) plus an optional Branch. Replaces all four `label|amount` textareas across the Budget page (create-cycle fixed costs, edit-cycle fixed costs, submit-proposal line items, edit-proposal line items).

No schema or migration — every new field is an optional key on the existing `jsonb` line-item arrays. 17 new tests (`tests/budget.test.ts`: quantity multiplier math, the quantity/perAttendee exclusivity re-check, perAttendee scaling live off Participation `coming` including a case where headcount changes *after* submission, perAttendee counting as 0 with no linked Cycle, per-item Branch storage independent of the proposal's own, cross-community Branch rejection for both proposals and fixed costs, and the pledged/confirmed-balance computation) — 41 of 41 passing in `budget.test.ts`, 1109 of 1109 across the full suite, `tsc`/`eslint` clean.

## Forms fields can map to a Profile question, closing the application→profile gap

Standalone, not a phase — the user noticed the trait-axis sliders and Profile questions built in an earlier standalone pass (see "Member competences," above) had nowhere to be filled in, which led into a design question: shouldn't the answers someone already gives on a recruitment application (name, pronouns, an emergency contact) just become their real profile instead of being asked a second time at onboarding? `docs/spec.md`'s own Profile questions section already frames `surfaces` as open-ended ("application, onboarding, wherever") but notes recruitment's application intake was built on the separate Forms primitive instead (Phase 33) — a Form's fields are submitted together as one opaque, all-or-nothing bundle, a Question is always independently answerable, a real behavioral difference `docs/spec.md`'s Forms section draws deliberately, not an oversight. Rather than retrofitting Forms into `surfaces`, this generalizes the existing `isNameField`/`isEmailField` pattern (`src/lib/forms.ts`, Phase 48): any Form field can now name which once-ever `ProfileQuestion` its answer should seed.

**`mapsToProfileQuestionId`** — a new optional key on a Form field (alongside `isNameField`/`isEmailField`), validated at `createForm`/`updateForm` time against three rules: the referenced question must exist, belong to the same community, and be `once_ever`-scoped (`per_cycle`/`phase` questions have no cycle to stamp against at the point an applicant converts — a real, deliberate restriction, not a gap). At most one field can map to the same question, same posture as the existing name/email uniqueness check. The Settings → Forms builder (`FormBuilder.tsx`/`FieldShapeEditor.tsx`) grows a "maps to profile question" dropdown per field, populated from the community's own once-ever questions, with the same client-side dedup-on-select `updateFieldAt` already gives isNameField/isEmailField.

**Seeding at conversion** — `maybeConvertApplicantToMember` (`src/lib/recruitment/decisions.ts`) now loops every mapped field after resolving the new member, reusing `answerProfileQuestion` itself (not a parallel write path) to validate and write a real, `answered` `ProfileAnswer` from that same application value. Best-effort: a blank answer or a shape mismatch (e.g. the applicant's free text doesn't match a since-changed `single_choice` question's options) just skips that one field rather than blocking conversion — the member can always answer it directly afterward. Runs under the same `convertedMemberId` idempotency guard the rest of the function already has, so it can never double-write.

**Onboarding doesn't re-ask what it already has** — `listOnceEverAnswers` (`src/lib/profile-questions/answers.ts`) gains the same `{ surface }` narrowing `listOutstandingQuestions` already had, so the Dashboard's onboarding panel can ask for just the once-ever, onboarding-tagged questions this member already has a real answer for. New `PrefilledAnswersReview.tsx` (`"use client"`) renders that set as one compact "Already on file from your application — Pronouns: they/them · …" line with a small pencil button; clicking it swaps in a real edit form (prefilled, one field per mapped question) with Apply/Cancel, styled as a single confirmation step rather than re-litigating each question one at a time the way a genuinely outstanding question still does. New bulk action `submitOnboardingPrefilledAnswersAction` (`dashboard/actions.ts`) answers every reviewed question in one submit via repeated `answerProfileQuestion` calls — the only form in this codebase's profile-question surfaces that bundles more than one question per submit, deliberately, since the review UI presents them together even though each answer is still independently validated and written.

No schema or migration — `mapsToProfileQuestionId` is an optional key on the existing `form.fields` jsonb array. 9 new tests: `tests/forms.test.ts` (accepts a valid once-ever mapping; rejects two fields mapped to the same question, a `per_cycle`-scoped target, an archived target, a cross-community target, both at create and update time), `tests/recruitment-conversion.test.ts` (a mapped field seeds a real `ProfileAnswer` that both shows up via `listOnceEverAnswers({ surface: "onboarding" })` and is correctly excluded from `listOutstandingQuestions({ surface: "onboarding" })`; a shape-mismatched mapped field is skipped without blocking conversion), `tests/profile-questions.test.ts` (`listOnceEverAnswers`'s new surface filter) — 1118 of 1118 passing across the full suite, `tsc`/`eslint` clean.

Manually verified only at the automated-test layer this time — `tsc`/`eslint` clean and the full real-Postgres suite green, including direct exercises of the conversion-time prefill, the best-effort skip, and the onboarding-exclusion behavior end to end at the lib layer. A live click-through of the two new UI pieces (the Forms builder's new dropdown, `PrefilledAnswersReview`'s summary/edit toggle) was attempted against this deployment's real `docker compose` stack but abandoned: `docker compose build app` hung indefinitely on every `docker pull`/`docker build` invocation, traced to `docker-credential-desktop` itself never returning (reproduced with a plain `docker pull docker/dockerfile:1` even though the underlying registry answered curl directly) — a local Docker Desktop credential-helper hang in this session's environment, unrelated to this change, that a `docker compose build app && docker compose up -d app` (no schema change, so no migration needed) should confirm once Docker Desktop is in a working state. ## Board views: a view switcher, a by-phase layout, and deadline milestones

Standalone, not a phase — every numbered phase (0-69) is done, and per the user, nothing after that gets numbered; this and every entry above it that says "not a phase" is that same kind of work. Picked off a gap in `docs/spec.md`'s own Views section rather than a stretch goal spec.md ever explicitly named: that section describes four board lenses — "group by status → kanban; sort by phase/deadline → schedule; group by branch → coordinator coverage; filter by tags → what fits me" — and only the first and last were ever actually built. `/board` had a single hardcoded kanban-by-status layout the whole time; `task.phaseId` and the milestone system already carried the data a phase/deadline view needs, just never surfaced. This ships the view-switcher scaffold, a real "by phase" layout, and a deadline concept riding on the existing milestone mechanism; branch coverage and an advanced-filters disclosure are next (see `docs/development-plan.md`).

**Deadline as a flagged milestone, not a new field.** `TaskMilestone.isDeadline` (boolean, default false) — at most one true per task, auto-transferred rather than blocked with an error when a different milestone is flagged instead: unlike Form fields (a whole array submitted and validated together, where `forms.ts`'s block-with-error pattern fits), milestones are added/edited one at a time with no natural "unset the old one first" step, so `createTaskMilestone`/`updateTaskMilestone` (`src/lib/tasks/milestones.ts`) wrap the write and a same-task sibling-clearing update in one `db.transaction`. The same "flag one of several" shape `TaskAssignment.isCoordinationSlot` already established, just actually wired up and enforced this time. A new `getTaskDeadline` resolves the flagged milestone's date via the existing `resolveMilestone`, falling back to the task's own Phase end date when nothing is flagged, `null` otherwise. `listTasksWithAssignments` (`src/lib/tasks/crud.ts`) gains a `deadlineDate` field per task, batch-fetched the same way `assignments`/`requirements` already are rather than one query per task. ## Kitchen: food & drinks, as an optional module

Standalone, not a phase — picked up from `docs/roadmap.md` and specced in `docs/food-drinks-module-plan.md`; `docs/spec.md`'s "Food & drinks (Fruit)" section is the original description this restores. Off by default, like every optional module: a Community turns Kitchen on under Settings → Modules, then grants the `kitchen` permission module on a task the same way Admins, branch coordination, and the Budget owner already work. Five new tables (`menu_plan`, `meal`, `dish`, `dish_ingredient`, `food_idea`), three enums, and one new sensitive-data column, in migration `0061_busy_luminals.sql`.

**Access rides the task, and a grant is multi-cardinality.** No Kitchen role column anywhere — `isKitchenOwner`/`requireKitchenOwner` (`src/lib/kitchen/access.ts`) answer "does this member currently *hold* a task granting `kitchen`," the same holder-join every other module uses, and a cycle-less task means the standing menu while a cycle-placed one means that cycle's. Because a community may legitimately have several people cooking (weeknight cook, weekend cook, a festival rota), `kitchen` joins `admin`/`branch_coordination`/`support` in `MULTI_CARDINALITY_MODULES`: one grant is full module access *in its own scope*, and grants on different tasks never displace each other. `isKitchenOwner(actor, cycleId?)` takes the scope the way `isEventSchedulingOwner` does.

**One publish gate, not a status column.** A `MenuPlan` is a named, dated container scoped to a cycle (or the standing menu), with a single `publishedAt`: null is a draft, visible and editable only to a scope's owner; set is published, readable by the whole community and locked against every further edit — meals, dishes, ingredients, and idea adoption all funnel through one `requireEditableMenuPlan`, so "published" can't be enforced in some places and forgotten in others. A non-owner sees the newest *published* plan in their scope and can file ideas against the newest plan of any kind; a draft in progress is genuinely invisible to them, not just hidden in the UI.

**Headcounts are the core, so recipes scale into an actual shopping list.** A `Meal` carries a plain absolute date (v1), an optional phase anchor, an optional link to a shifts `ShiftSeries` for the cooking roster, and a `headCount`. Each `Dish` records the `serves` its recipe as written feeds, and `scaledIngredients` multiplies every `dishIngredient` by `headCount / serves` **on read only** — nothing is ever written back, so changing the headcount or a serving count is free and never drifts. `purchaseList` then groups those scaled amounts into a per-meal shopping list by *exact* ingredient name: two dishes' "flour" merge into one line, but "flour" and "plain flour" deliberately stay separate, because quietly merging near-synonyms is how a shopping list loses an ingredient. A meal with no headcount stays at recipe scale and computes no purchase list at all, rather than inventing one from a guessed number.

**Food ideas are attributed, persistent, and adopted in one step.** Any member can file a recipe suggestion, dish request, or preference against the active plan — open to everyone, no grant needed, deliberately *not* anonymous, since a cook often needs to ask a follow-up about a recipe. Statuses are open/adopted/declined, and `adoptFromIdea` creates the dish (`source: "from_idea"`, back-linked both ways) and flips the idea in a single transaction, so an idea can't be adopted into a menu without its dish landing.

**The dietary panel reads member data only through the sensitive-data module's own gate.** `getMealConstraintPanel` returns `null` — the panel simply doesn't render — unless the field is actually unlocked for the reader, and it re-checks active consent per read exactly as `getSensitiveDataTable` does, so a withdrawal takes effect immediately. Allergen flags are a bounded `ALLERGEN_FLAGS` const rather than a DB enum (new flags are a one-line change, not a migration), matched against members' free-text allergy fields by keyword, which catches "dairy" for a `milk` flag and "cashews" for `tree_nuts` and honestly reports "may conflict, verify" rather than pretending to be a safety guarantee.

**A third sensitive-data unlock route, which this is the first consumer of.** A field can now be unlocked by "whoever currently holds *any* task granting module X," not just one named task or one tier — `sensitiveFieldAccessRule.unlockedByGrantModuleKey`, exactly one of the three routes per rule, configured in Settings → Access & permissions. It is deliberately **community-wide**: a sensitive field is one community record, so the rule names the module and the granting task's own cycle placement does *not* narrow the unlock. That's the shape allergies→kitchen needs — a cook holding the Kitchen grant for one cycle still plans against the whole community's menu, and the module route matches per-rule, so holding a `budget` task can never satisfy a rule that names `kitchen`.

An **ordering/equipment lens** rides the same page rather than duplicating task data: open tasks in the menu's scope whose tags match the supply vocabulary (`ordering`, `equipment`, `supply`, `shopping`), with their task resources, shown only to the scope's Kitchen owner. Holders also get a Dashboard needs-action row for an unpublished draft and for open ideas waiting on a draft they own; the feed entry is module-gated and degrades to `[]` for everyone else.
