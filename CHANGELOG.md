## 0.1.0 — 2026-10-06

The first tagged release, cut so there is a known point to deploy, pin and upgrade from. Everything below, to the end of this file, is how the application got here: it was written as the work landed and was never grouped by release, so it isn't split into versions after the fact. From the next entry on, work is grouped under the version it ships in.

## migrations are tested on data that already exists, and the repository is set up to be picked up by someone else

**The migration that would have crash-looped a deploy now has a test that catches it.** The suite migrates an empty database once and truncates between tests, so every migration runs on no rows — the one case in which a migration that breaks on real data looks fine. `tests/migration-helpers.ts` builds a throwaway database on the same server, migrates it to just before the migration under test, lets a test insert rows in the *old* shape with plain SQL, runs the rest and reads back what happened. `tests/migrations.test.ts` uses it for the four migrations that rewrite existing rows: 0083 (the `objection.community_id` backfill — with the original SQL restored the test fails with exactly `column "community_id" of relation "objection" contains null values`), 0082 (emergency consent fails closed for answers that predate it and keeps what was already agreed), 0085 (one primary contact method per member, none duplicated, an existing primary or a self-added login address untouched, an OIDC email not marked verified) and 0087. `tests/migration-lint.test.ts` is the static backstop: it fails on any `ADD COLUMN … NOT NULL` without a `DEFAULT` (with an explicit, reasoned marker comment for a table that has no rows), and runs `scripts/check-migrations.mjs`, which existed since e902f19 but was wired in nowhere. Both guards were mutation-checked against the original 0083.

**Releases.** A release is a `vX.Y.Z` tag. Pushing one makes CI publish `:X.Y.Z` and `:X.Y` alongside `:latest` and `:<sha>`, so an instance can pin a version instead of following `main`; the suite still has to pass first. The CHANGELOG now has an `## Unreleased` section and a `## 0.1.0` heading: the forty entries that were each headed "Unreleased:" (the whole of the post-Phase-69 era, with no way to tell what had shipped) are one release, and `releases.ts` cites them by their new headings. `CONTRIBUTING.md` gains *Releases and upgrading*: how to cut one, back up before an upgrade, rehearse a data-rewriting migration on a restored copy, and — as of the first tag — **a migration that has shipped is never edited**, because editing the file changes nothing for an instance that already ran it. (0083 was edited in place; that was safe only because nothing had been tagged and nobody else had deployed.)

**For people who find the repository.** `SECURITY.md` says how to report a vulnerability privately (GitHub's private reporting), what counts, and which versions are supported. `.github/dependabot.yml` opens grouped weekly minor/patch updates for npm and monthly ones for Actions and the base image, and deliberately ignores majors — Next, Drizzle and TypeScript are planned work, not green PRs. The README states plainly that it is pre-1.0 with one small community using it. `CONTRIBUTING.md` no longer says the plan docs are "never committed" while both are tracked; they are described as what they are, working notes and not specification.

**`nodemailer` 9 → 10.** The audit listed seven advisories against the old version, among them recipient-address parsing bypasses and denial-of-service in address parsing, which is reachable here because addresses typed by applicants and invitees end up in `sendMail`. The in-range update to 9.1.1 closed some of them; the rest are fixed only in version 10. `mailer.ts` uses only `createTransport` and `sendMail`, which are unchanged; v10 ships its own types, so `@types/nodemailer` is removed and the one `Transporter` annotation is spelled `ReturnType<typeof nodemailer.createTransport>`. Smoke-tested with the JSON transport, type-checked, and `next build` passes. Still open in `npm audit --omit=dev`: `drizzle-orm` (the SQL-injection advisory needs identifier or alias input, and the app uses neither — a major upgrade is planned work), `next`/`postcss` (needs Next 16), and `sharp` (an optional image library that Next pulls in; the app stores no uploaded images).

## a manual tier is asked for and confirmed, and opening Admins or View-as needs a confirmation the server checks

**A manual tier is no longer a checkbox on your own profile.** The spec says leads designate members into a manual tier; the app let anyone tick any of them. Tiers gate real access — a sensitive-data audience can be "unlocked by tier X", starting an event can be limited to a tier — so every tier-keyed gate was, for a manual tier, a self-service one. Now a member asks (`tier_request`, migration 0088), and an Admin or someone already in that tier confirms. A pending request grants nothing; `member.tierIds` changes only on approval, in the same transaction as the decision, and a request is decided once however many people press the button. The requester can't confirm their own — except an Admin, who could already redefine the tier and who may hold it, and would otherwise lock a one-Admin community out of its own tiers. Leaving a tier needs nobody. A declined request is shown to the member (they can ask again); decided rows are kept as the record of who confirmed whom, and a member leaving the community takes their pending ones with them. A tier that is deleted takes its requests with it.

Where it shows: the profile's tier checkboxes are replaced by a Tiers section (ask to join / waiting / leave / ask again); the dashboard gets a "Tier requests waiting on you" section with Confirm and Decline for whoever may decide, counted in the sidebar badge. `updateProfile` no longer writes tiers at all, so saving a name can't change what a member holds. Existing assignments are untouched. There is deliberately no unconfirmed manual tier: a harmless label is what tags are for. Fourteen tests in `tests/tier-requests.test.ts`, including the cross-community case, the self-confirmation rules and the decided-once guard.

**Opening Admins or View-as to everyone needs a confirmation the server checks.** The settings dialog asked, but a confirmation that exists only in the browser is one a forged request skips. `setModuleOpen` now refuses to open `admin` or `support` without `confirmedBlastRadius`, repeating what it would do; closing, re-submitting an already-open module and every other module are unchanged. The wording lives in one place (`OPEN_BLAST_RADIUS`) and both the settings row and the refusal read it.

## a form can't ask a sensitive question, the last Admins grant is a way out and not a trap, REST writes respect View-as, and the docs stop describing things that don't exist

The second batch from the audit, after the three faults in the entry below. Five code changes and one documentation pass, each with tests that fail on the old behaviour.

**A sensitive question can no longer be mapped from a form field.** A Form field can name a once-ever Profile question to seed at conversion, and nothing excluded a sensitive one — so an application answer was saved with `shareWithAudience` defaulting to true, i.e. consented to the question's whole audience, which the applicant (no account yet, nothing shown to them) had never seen. It is also a second answer to "who sees this?" on one page: who may read an application's responses is the community's choice and is not the question's audience. `requireValidMappedProfileQuestions` now refuses a sensitive target (create and update), the builder's picker no longer offers one, and conversion drops the answer for a form saved before this rule rather than saving it. Sensitive questions are asked at onboarding, where the member is shown who can read the answer first. Tests in `forms.test.ts` and `recruitment-conversion.test.ts`.

**Creating a sensitive question is one transaction.** It used to commit the question, then create its access rule, then set the flag. A failure between (a task deleted since the form rendered) left a question that was *not* sensitive, readable by everyone, with the Admin shown an error that read as "nothing happened" — and because `sensitive` can't change after creation it could only be archived once members had answered it as a public question. `createSensitiveFieldAccessRule` now takes an executor and `createProfileQuestion` runs the whole thing in one transaction. The new test leaves the old code failing.

**The last Admins grant is a way out, not a trap.** `requireAdmins` checked the ever-claimed latch first and then threw if no Admins grant existed, so a community that removed its last grant (or whose granting task was deleted) was locked out of the only screen that could create a new one, for ever. No Admins grant now means open to every member — the same answer as before the first one was made. A grant that exists but has nobody holding it stays gated: that is a role waiting to be claimed. Because removing the last one is the only removal that changes who may change settings community-wide, `removePermissionGrant` refuses it without `confirmedLastAdmin`, and the permissions tab shows the checkbox on exactly that row. Four older tests relied on "latched with no grant means forbidden" and were changed to give the community a real grant; they were testing the trap.

**Opening the conflict team to everyone asks first when it would expose reports.** The per-report exclusion works and is enforced in the query (an anti-join, with an open team too — tested). What it can't do is reach back: the reporter could only exclude members of the team *as it was*, so anyone a report concerns who wasn't on it has never been excluded, and opening the team makes every member a team member who reads every unacknowledged or escalated report. `setModuleOpen` now refuses to open `conflict_team` while any such report exists, saying how many, unless `confirmedReportExposure` is given; the row's dialog shows the count and the box. Acknowledged, unescalated reports aren't affected and don't trigger it. Not done: freezing pre-existing reports to the old team's readership, which would need to store who that was.

**REST writes respect View-as.** View-as is documented as strictly read-only, "disabled at the UI layer and re-checked server-side regardless", and only the Server Actions kept the second half — 112 of 130 mutating API routes carried on writing, as the support holder's own identity (not as the viewed member). `requireWriteMember()` in `src/lib/api.ts` is `requireMember()` plus `assertNotViewingAs()`, and all 111 handlers that read identity through the unguarded one now use it; GET handlers are untouched, since the old comment was right that guarding the shared function would break reads. `tests/api-write-guard.test.ts` reads the route tree and fails on a mutating handler with neither, with an explicit allowlist for the six public/auth routes.

**The in-app documentation says what exists.** Pages described browse-mode auto-claim and contested-slot resolution, a finish-task capture prompt, View-as being visible to the person viewed, a "weekly" input round that is actually configurable, an emergency-access reason that is always required, the contribution toggle being on the profile, and polls going on everyone's calendar. Each was checked against the code. Real behaviour is described as such; what is intended but unbuilt is marked with a new `planned` block (types, renderer and test updated) that carries a fixed "Planned — not built yet" label so the status can't depend on wording. Two claims were removed outright rather than marked: that rarer skills are "pushed harder" (nothing weights by rarity, and it isn't in the spec) and that View-as is visible to the person viewed (the spec only promises it is logged). The README's stale "Members tab" sentence now points at `/members/import`.

## a first-login screen, and the name a member is actually called

### Nobody was ever asked their name

There are five ways into this app — a magic-link first login, an SSO first login, an invite redemption, an accepted application, and an admin roster import — and **all five derived `Member.name` from something that is not a name**. Three used `email.split("@")[0]`. One used the name an application applicant typed, which is real. One used the standard OIDC `name` claim, which is a legal-ish full name rather than a name somebody goes by.

None of them asked. The only place to change it was `/profile`, which most people never visit. So the community's roster was a list of `t.doe`, `toby.w` and `sam.smith` — every member's name to every other member — and the only way it ever got fixed was individual members independently thinking to go and fix it themselves. That is the actual problem, and it is not visible from inside a single member's account.

`/welcome` is the fix, and it is asked **once, on the way in**, by a redirect from the login entry points rather than a gate. It asks for a name, for who may read each contact method, and for languages. The name field is pre-filled with the derived one and required, so the common case is editing `t.doe` into `Toby` rather than retyping it from memory — a blank field would be worse, because it makes the member remember a name we already had and turns the validation error into a punishment for doing exactly what we want.

**It is deliberately not a gate, and nothing enforces it.** There is no layout-level guard reading the new `member.profile_completed_at`, so a member who closes the tab on `/welcome` is in the app on their next click like anyone else, and the "skip" button sets the same column the submit does — which is what makes it genuinely once-only rather than something that follows somebody around. This is the same posture `hasCompletedOnboarding` has always taken, and it is a **separate flag on purpose**: that one means "has seen the Dashboard orientation panel", which is where spec's "a new member's first session should end with at least one task claimed" actually lives. Folding the two together would mean finishing here silently deletes the task suggestions.

### The IdP's nickname, not its legal name

SSO first login now reads `nickname`, falling back to `given_name` and then to the email's local part. The full-name `name` claim is not read at all, because a roster entry is a name somebody chose to be called and "Toby Whitfield" is the least useful thing an identity provider can offer for that. `nickname` was already inside the `profile` scope this code requests, so no scope change was needed.

The one detail that would have bitten: **Zitadel sends `nickname: ""` rather than omitting the claim** when nobody has set one. A plain `typeof x === "string"` check hands the name chain an empty string, and the fallback happens to survive it by accident — so the bug would have looked like a working chain and then changed under the next refactor. Claim parsing now treats blank as absent, and the mock IdP in `tests/mock-oidc.ts` sends the empty string by default precisely so a regression can't reintroduce it.

### An invite could create a second account for somebody who already had one

`redeemCommunityInvite` checked whether the address belonged to an existing member by looking for a `magic_link` identity — and only that. `findOrCreateMemberByEmail`, written earlier, checked three things: a magic-link identity, an OIDC identity, and the address as somebody's own primary contact method.

So an **existing SSO member who was sent an invite link and redeemed it with their own address got a second Member row**: two accounts, one person, and a login link now going to the wrong one. The same held for anyone whose primary contact method was an address they chose rather than their login address.

Both call sites now ask `findExistingMemberByLoginEmail`, one shared definition of "who already owns this email", so the two can't drift apart again. This is the third time that pair has diverged, which is the actual argument for the shared function rather than the tidiness of it.

### A login link is a proof, and three paths were discarding it

Invite redemption, application conversion, and admin roster import all seed a member's primary contact method with `verifiedAt: null`. The reasoning in each was correct: nobody has yet received anything at an address somebody *else* typed, and `verifiedAt` is a fact about the inbox rather than about a belief.

But the first magic-link login **is** that receipt. A magic link is only ever sent to an address its recipient controls, and reaching the verify route means somebody clicked the one that arrived there. That proof was being read and thrown away, so an invitee, an applicant, and an entire imported roster were left on `/profile`'s one-click "send me a confirmation" for a confirmation they had, in effect, already given. The verify route now records it.

Scoped to the member it just logged in as, **not** to the address. The address is a string an unauthenticated caller chooses — it's the thing the app mails a login link to — so a value-only match would let one member's verified login stamp a verdict on another member's contact method, and two members may legitimately hold the same address as a non-primary row.

### A form can now supply languages, so the screen doesn't ask twice

Asked "what should the screen collect?", the answer included languages "if that information is not already available from application". That condition was **never true** — nothing in the codebase could write a language from an application. A `FormField` could tag `isNameField`, `isEmailField` or `mapsToProfileQuestionId`, and the only route to languages was a ProfileQuestion answer, where the starter set's "Languages you speak" is a free-text blob that stays a blob. A `member_language` row — which is what a task's `language` Requirement actually queries — was unreachable from any form.

`isLanguageField` follows the existing two exactly, and conversion seeds real rows from a comma/newline-separated value at `conversational`. That level is the schema default and the one that claims nothing: the form asked one question, not five, and a community that wants to distinguish fluent from native needs a form that actually asks. Values are deduped case-insensitively against what the member already has, so a Member who logged in and set their own languages before a decision was filed doesn't get a second row or a downgrade.

### A pre-existing bug: seeding questions could fail a login

Five OIDC tests failed on a clean checkout of this branch, before any of the above. The cause was a comment that described the intent and code that did the opposite.

`findOrCreateMemberByEmail` and `findOrCreateMemberByOidcSubject` both call `maybeSeedDefaultProfileQuestions` *outside* the member-creating transaction, with a comment explaining exactly why: "a community with no questions and a settings button beats a failed login." But the call was `await`ed unguarded, so any throw inside the seeder propagated straight out and took the login with it — a deadlock or constraint blip during a first login returned a 500. Being outside the transaction was never sufficient on its own. Now wrapped and logged, because a community that silently has no starter questions is only discoverable from the settings page and this one line.

## an audit's three real faults — event admission rules, the overrule threshold, a migration that only worked on empty databases — and the suite runs in CI

An independent review of the work done since 2026-09-26 (by reading, not by trusting the commit messages) turned up three faults that the suite could not see, because each lives in a place the tests did not look. All three are fixed here with tests that fail on the old behaviour; the full suite was green before and after.

**Any member could rewrite an event's admission rules.** `updateCycleLaneRulesAction` called `setCycleJoiningLaneRules` and `deleteCycleJoiningLaneRules` directly, and neither takes an actor — so the only thing between a logged-in member and an event's admission design was the form being hidden from them. Someone posting the right fields could make an event's invites admit with no application, interview or second. The gate is now `updateCycleLaneRules(actor, cycleId, rules, dropped)` in `src/lib/recruitment/joining-lanes.ts`: it requires whoever may start an event (the same authority as `updateCycleSettings`, and the one the page already used to decide whether to show the form), that the event belongs to the actor's own community, and that it is still open. Four tests in `tests/lane-overrides.test.ts`, including the same call succeeding for an eligible member so the refusal is shown to be the gate and not a broken call. One thing worth knowing rather than fixing here: if no `cycleInitiationTierId` is configured, *every* member is eligible, here and everywhere else that gate is used — that is the existing design, not something this changes.

**The mediation "overrule threshold" was never a threshold.** `resolveObjection` checked `overruleAvailability` — whether the body was big enough for the community's threshold to be reachable in principle — and then let the single member who clicked settle it. So with a body of five and "3 of 5" on the button, one click admitted someone over a standing concern; the protection the plan builds the whole mechanism around (a lone objector must win the room, and so must a lone overruler) did not exist on the overruling side. An overrule is now a *position* each holder records (`objection_overrule_support`, migration 0086, unique per objection and member, with their note), and the objection is only overruled once enough of the body *as it stands now* have one: a supporter who has since left the role or been recused by the objector stops counting. The permanent record names every supporter and what they said. Clearing and upholding are unchanged — one holder, as before — and a body of one still overrules alone. The queue shows who has supported so far and the button says so ("Support an overrule (1 of 2 so far)"). Four tests in `tests/joining-lanes.test.ts`; with the threshold check disabled, three of them fail.

**Migration 0083 failed on any database that already had an objection.** It added `objection.community_id` as `NOT NULL` with no default and backfilled afterwards; Postgres checks the constraint against existing rows the moment the column is added, so on a populated `objection` table the `ADD COLUMN` itself fails, the batch rolls back, and `docker-entrypoint.sh` (`set -e`) never starts the server — a crash loop on deploy. The comment above it described the failure as deliberate, which is the part that suggests it was only ever run on an empty database, as the suite always does. Reproduced against a scratch database migrated to 0082 with one objection in it, then fixed the usual way (add nullable, backfill, `SET NOT NULL`) and re-run on both a populated and an empty database. Edited in place: drizzle applies by journal position, so a database that already ran the old version is unaffected. The suite still cannot catch this class of fault, since it migrates an empty database — that gap is open.

**The suite now runs in CI, and gates the image push.** `.github/workflows/docker-build.yml` gains a `test` job that runs `ORCHARD_TEST_HOST=1 npm test` — the same `scripts/test.sh` as locally, so the same production-tuned Postgres and batching — on Node 22, and `build` now `needs: test`. Before this, every push to `main` published `:latest` after only lint and a type-check.

## the app stops looking like every other app built in the last two years

A design pass with a narrow scope — tokens and identity, no per-page work — aimed at one thing: this is a tool for a specific community with a specific voice, and it was carrying the house style of a design system bound to it by a handoff document. `docs/design_handoff_conventions/README.md` said so in its own words: *"This design project has Anthropic's Nocturne design system bound to it (dark, soft-8px-radius, Inter, mono-accent, outline-only buttons)."* `globals.css` implemented all eight of Nocturne's hexes verbatim, its neutral ramp was Tailwind's `neutral` scale — the file even said *"matches the Tailwind neutral scale"* — and the body was set at 13px in **689 places**, with a further 350 at 12px.

**Three families, each with exactly one job.** IBM Plex Sans for the interface, Fraunces for anything that is a heading, IBM Plex Mono for figures that are identifiers rather than prose. Fraunces over Newsreader because its optical-size axis lets one family set a 32px page title and a 16px card title without one being a shrunken copy of the other; its `WONK` axis is pinned off, since that is the character and also what makes it read as a display face, and this is an all-day tool. The mono rule is new as a *rule* — the conventions doc has specified one since it was written, and the codebase contained **six** uses of it.

**A real type scale, replacing 1,236 hardcoded sizes.** Every arbitrary `text-[Npx]` in the app mapped onto one of eight named `--text-*` steps, and there are now **zero** arbitrary font sizes left. The body moved from 13px to 15px, which is the substantive change; the tail of the scale (13/12/11) is kept deliberately, because small is correct for a caption and was being used for everything. Every page is now one token change away from a different body size, which is the point of doing this at the token layer rather than page by page.

**The palette is no longer Tailwind's, and `--bg` is no longer the same colour as `--surface`.** Both were `#ffffff`, so every card was separated from the page by a hairline alone and the layout read as a wireframe; there are three distinct surfaces per theme now. The ramp is a warm grey rather than `neutral`, and the status colours were `red-600`/`amber-700`/`green-700` verbatim — each is now darker and slightly desaturated at the same role, so a status colour on its own soft background clears 5.6:1 instead of sitting at the edge. All text/background pairs were checked: 17.4:1 for body text in light, 14.1:1 in dark, 5.4:1 for muted.

**An identity, of which there was none.** `public/` was empty, so every install served the default Next.js favicon; there is now a mark at `src/app/icon.svg`. The wordmark in the sidebar was an undifferentiated 14px Inter span identical to every other string in the rail and is now set in the display face, as is the landing hero. And `metadata.title` was the literal string `"Orchard"` — the same on every install, forever — so the tab said "Orchard" for a community named something else entirely. It is generated from the community row now, behind `generateMetadata`, with the community query wrapped in `cache()` so it costs one round-trip per request rather than two.

**Three bugs, all of them silent.** The first named the `next/font` variable `--font-display`, which is also the semantic token in `globals.css`; `:root` overwrote the class, the `var(--font-fraunces)` reference dangled, and every heading quietly fell back to the body font. The second was worse and had no visible symptom: `text-[var(--text-body)]` is **ambiguous** to Tailwind, which emits `color:` for it rather than `font-size:`, so all 1,436 migrated sites reset to the browser's 16px default — the page still looked plausible, just not as designed, and nothing errored. Size tokens are now always written `text-[length:var(--text-body)]`. The third was a cascade mistake of my own making: the new `h1`/`h2` rules were written outside any layer, and unlayered CSS outranks every `@layer utilities` rule regardless of specificity, so they silently overrode Tailwind's own utilities and pinned the landing hero to 32px. Base rules live in `@layer base` now.

**What this deliberately does not fix**, and why it isn't in this commit: the app is still 144 bordered boxes of which the task detail page alone has 20, 35 of 60 pages still open with a centred narrow column, and roughly 7,000 characters of page-description prose still explain what a page is. Each is a real part of why it reads as generated, but each is per-page work that would be done twice if attempted before the type and palette settled. This is the floor those passes now build on.

Verified by `npx tsc --noEmit` and `npm run lint` (clean; the 7 warnings are pre-existing and all in test files), and by probing the running app in a real browser across `/`, `/login`, `/dashboard`, `/board`, `/calendar`, `/members`, `/community`, `/settings`, `/documentation`, `/shifts` and `/recruitment` in both themes — computed font resolution per element, plus checks for horizontal document scroll, clipped text and overflowing nav rows, all of which are clean and unchanged from the pre-change baseline. **`npm test` could not be used as a signal on this machine**: run against a clean tree with these changes stashed it already reports 535 failures, of which 222 are `the database system is shutting down` and 128 `starting up` — the test Postgres container cycling mid-run on a memory-constrained host. That is pre-existing and unrelated, but it does mean this change is unverified by the suite rather than verified as not breaking it.

## the ⋯ overflow menu is unusable on a phone

Reported from Chrome on an iPhone: tapping the three-dot overflow opened the menu, and the actions in it were not there. Not a styling nit and not a broken tap handler — the menu rendered, correctly, in a place that was mostly off the screen. On the task detail page and the board header the actions all sit in one right-aligned row, so on a narrow screen that row wraps and the trigger lands wherever the wrap leaves it. The menu was anchored by `absolute right-0 top-8` inside the button's own inline-block span, which only ever positions it correctly relative to that trigger — it never once asks where the trigger is on the *screen*. With the trigger near the left edge, `left` came out at **-156px on a 320px-wide iPhone SE**: every row in the menu rendered to the left of the viewport, clipped, so the menu opened looking empty. The same unmeasured anchor also let a menu open downward off the bottom of the screen, which the board's own action menu does in selection mode, where it reaches nine rows.

**Fixed by measuring instead of assuming, the same arithmetic a native popover does.** The geometry is `src/lib/menu-placement.ts`, a pure function with no DOM dependency, so the rules are testable without a browser: place below the trigger unless that would run off the bottom *and* there is more room above, right-align to the trigger then clamp into the viewport, and where the chosen side is short, cap the height and scroll inside the cap rather than hanging off the edge. A menu wider than the viewport is narrowed to fit — clamping can't help there, but narrowing lets the rows wrap.

`ActionMenu` now positions from measured geometry (`position: fixed` plus coordinates from that function) in a **layout** effect, so the menu never paints at an unpositioned origin first — on a touch device that is the difference between appearing under the finger and visibly jumping. Re-placed on scroll, resize and orientation change, because a fixed menu stays put while its anchor moves under it, and the scroll listener also covers iOS collapsing its toolbar, which is what finally makes a menu near the bottom of a phone screen fit. The scroll listener is registered in the capture phase, since the trigger can sit inside any scrollable ancestor and those don't bubble to `window`. Two smaller things the change forced into the open: `z-20` is the desktop sidebar's layer, which a phone-sized menu must not disappear behind, so the menu is now `z-50`; and a menu that scrolls gets `overscroll-contain`, so scrolling it doesn't chain to the page behind and lose the menu you were reading.

Verified by measurement in a real browser rather than by eye, driving the actual component at iPhone SE (320×568) and iPhone 15 (393×852) sizes: the left-edge menu that the old anchor put at `left: -93` now clamps to `left: 8` and shows all its rows; a trigger near the bottom flips the menu above itself; the nine-row menu stays fully on screen with its first row visible and its last row reachable by scrolling. Plus a sweep in `tests/menu-placement.test.ts` asserting that *no* trigger position on either phone screen puts any row off-screen or covers the button that opened it. Six tests, no database.

## every page 500s in dev, and the dev database runs out of connections

`next dev` served a 500 on *every* route — including `/login` — with an error about `require('stream')` in nodemailer. The dev database also died independently with `sorry, too many clients already` after a few minutes of editing. Neither reaches production, and that asymmetry is what made both look like environment flakiness for a long time.

**The 500 was a Next dev/build asymmetry, and it was never about mail.** `src/instrumentation.ts` is how the cron scheduler starts, and it reaches `src/lib/mailer.ts` through `@/lib/tasks` → `tasks/nominations.ts` → nodemailer, whose base64/mime helpers do `require('stream')` at module scope. Next compiles that hook twice: nodejs and edge. `next build` only adds the edge copy `if (edgeRuntimeAppCount || edgeRuntimePagesCount)` and this app has no edge routes, so **production never compiles it** — zero occurrences in the build log, which is exactly why it read as dev-only. `next dev` doesn't apply that gate and compiles the hook under the edge config, which externalizes no Node builtins. The `process.env.NEXT_RUNTIME !== "nodejs"` guard in `register()` can't help: webpack resolves every `import()` target at parse time, reachable or not. And because instrumentation is compiled at server start and Next then serves *that* failure as the response, the whole app was down with a message pointing at email.

**Two fixes were wrong before the right one.** `serverExternalPackages: ["nodemailer"]` is the documented remedy and does nothing here — proven, not assumed, by adding an invalid key beside it and confirming Next validates and reads the file, so the option really was applied; Next's `optOutBundlingPackages` simply isn't wired into the instrumentation compilation. Bumping to 15.5.26 also does nothing (reverted, lockfile untouched). Declaring the externals by hand did clear `stream` and immediately surfaced `node:crypto` — which is the tell that the edge compile was failing on Node builtins *in general* and nodemailer was only the first one reported. So the fix is at the actual asymmetry: the edge compile is handed `builtinModules` as externals, bare **and** `node:`-prefixed (externals match the request string exactly, so one spelling isn't enough). The code that compile pulls in is node-only and never runs on edge — the runtime guard is what guarantees that, and it's the guard production already relies on.

**The connection exhaustion was a real dev-only leak in `src/db/index.ts`.** The client was created at module scope, and `next dev` re-evaluates server modules on every recompile, so each edit made a *new* pool while the old one was never closed. postgres.js defaults to `max: 10` per client with `idle_timeout: null`, so those connections never reap themselves either — a handful of edits stranded 35 idle connections against the dev database's `max_connections` of 50, after which pages failed with an error that looks nothing like a connection leak. Production evaluates the module once and gets exactly one pool, so this was invisible there too. Now cached on `globalThis` in development, the standard fix and a no-op in production. Verified by counting `pg_stat_activity` across six forced recompiles: flat at 18, where it previously grew by up to 10 per edit.

Also found while here: the host runs **Node 23.11.0** while the Dockerfile, the `checks` stage and the production runtime are all `node:22`, with no `.nvmrc` or `engines` pin anywhere. The most recent commit (`0c1cdbe`) moved the *test* suite into a container on node:22 for precisely this reason — lint and types were checked on 22 while tests silently ran on 23. Dev was still on 23. Node 23 is not the cause of either bug here (both reproduce identically on 22), but the gap is real and worth closing: a `.nvmrc` is a one-line fix that makes the whole class of "passes locally, fails in production" mistakes impossible.

Verified: `next dev` now serves 200 across dashboard, board, members, calendar, settings, propose, proposals, messages, assemblies, contribution, questions, feedback and the whole documentation section; the scheduler still registers all nine cron jobs; connection count flat across recompiles; `tsc` clean, `eslint` 0 errors, `next build` clean with both documentation routes, and the full suite green (1786 tests, 89 files).

## the Library gets a documentation section, and the "why" moves out of the interface

The design conventions' copy rule — UI copy answers *what does this control do*, never why it was built that way, what the design rejected, or which reading of the spec it implements, with the reasoning in a code comment instead — is being applied right now, across settings, tasks and recruitment. It is the right rule and the pages are much better for it. But a code comment is only complete for the next person editing the code, and "reasoning lives in a comment" was quietly leaving members with nowhere to ask *why*.

So: `/documentation` gains a third section. **Orchard documentation** is how the tool works, how to use it, and why it behaves the way it does — including the reasoning behind the controls that no longer explain themselves, which is now the whole reason the section exists. Alongside it, a curated **What's new** feed.

**It is static content, not wiki rows, and that was the first real decision.** The obvious move was to seed these as `wiki_page` rows: the renderer already exists, it needs no new UI, and the Library is where they belong. Every part of that is wrong for platform documentation. It would mix a page about how a control behaves into the same list as a page about where to buy timber, written by the same people with the same permissions — when the two differ precisely in that the first is read-only to everyone and the second is writable by any member. It would need a migration and per-install seeding to exist at all, and it would put the documentation's lifecycle inside the database it documents. It would also make a build record the community can edit.

**So the content is typed TS modules** (`src/lib/docs/content/`), read from a registry and rendered by one small component. No new dependency, every shape checked by `tsc`, and it bundles into `.next/standalone` — which matters more than it sounds: `.dockerignore` already excludes `docs` and `*.md`, so the alternative of reading markdown off disk needed a Dockerfile change and an un-ignore to ship documentation about the app inside the app. A side benefit is that the block vocabulary is the enforcement mechanism. It has one block that carries reasoning (`callout`) and five that don't, so a "why" can't quietly spread through a page of instructions — which was the failure mode the copy rule was written against in the first place.

**The "why" pages are one decision per page, named by the decision.** Not a feature tour with justification attached. Each answers the same three questions: what the alternative was, what it would have cost, what tipped it. That constraint is what stops the section becoming the thing the rule was written against, and it's why "Why it's like this" has six pages rather than one long one — the standalone dropdown that reverted on save is a decision about a control, and the control's own page shouldn't have to carry it.

**`/documentation/orchard` coexists with `/documentation/[id]` as a static segment beside a dynamic one.** Next.js resolves static ahead of dynamic, so the doc index wins for that path and a wiki id can never shadow it — wiki ids are UUIDs, so `orchard` is not one. Worth stating rather than leaving to be rediscovered, since the obvious "simplification" is folding them into one route.

**Pages for optional modules hide themselves** when the community has that module off, reusing the `modulesEnabled` gate the nav already uses, with a test asserting every declared `moduleKey` is a real module. A community without Budget shouldn't be shown documentation for Budget. Deliberately *not* applied to the shipped-optional `documentation` module itself, which would be a page whose only failure mode is that it isn't there.

**No search, so the index does the work.** Page titles and summaries are phrased as the question someone would arrive with, because the index is the only way in and there is no full-text lookup to fall back on. The section rail sits above the body on every page for the same reason. A link from the dashboard onboarding panel is the obvious follow-up and deliberately not done here — that page has a defined role and adding to it deserves its own decision.

Sixteen structural tests, no database: unique slugs across the flat namespace, every `see-also` resolving, table rows matching their header, neighbours walking the whole set across section boundaries, and release notes newest-first with each one citing a CHANGELOG heading that still exists. That last one is the whole mechanism keeping the curated feed honest, and it's why the pointer at the top of `CHANGELOG.md` and in `docs/roadmap.md` names the file rather than gesturing at it. One of the tests caught a real broken link during the build — three pages pointing at a privacy page that hadn't been written yet, which became `privacy-and-access` rather than three deletions of a reference that turned out to be a genuine gap.

## the Coordination view becomes a dashboard, and the self-assign check stops being a wall

Three things that turned out to be one problem. The Coordination view had no tasks in it, its menu item lit up for exactly as long as a redirect took, and the coordinator self-assign check deleted the Claim button on every unclaimed or flagged task in a coordinator's scope whether or not they were trying to claim anything.

### The menu item's flash, which was a real bug and a known failure mode

`nav-config.ts` gives Coordination `href: "/coordination"`, but that route is a redirect shim onto `/[cycleScope]/coordination`. `AppShell`'s `isActive` is a plain prefix match, so the row lit for the duration of the redirect and could **never** be lit again on the page it actually led to. `Budget` had been doing exactly the same thing, and `CHANGELOG.md` already recorded that the Events row was *deleted* rather than fixed for this reason — so this was the third instance of a bug the project had diagnosed, in a row that nobody had connected to it.

The fix reads `cycleScoped` off the nav item and strips the leading segment when matching, so the href stays a clean, shareable `/coordination` and one function knows it resolves further. Flagging the item is what keeps the next page moved under `[cycleScope]` from silently reintroducing it, and a test asserts every item whose page lives there is flagged.

**The scope switcher was broken on these two pages for the same underlying reason, and that one was a live bug.** `AppShell`'s `cycleScopeMatch` regex listed only `participation|budget`, so on `/active/coordination` the switcher had no sub-path and `selectScope` fell through to `router.refresh()` — a coordinator picking a different event on the Coordination view silently stayed on the old one, with no indication it had done nothing. The regex and the switcher's `subPath` type are now one shared `CycleSubPath` union, so a page added to one without the other fails to typecheck rather than quietly refreshing in place.

### The self-assign check fired on sight rather than on attempt

`claimOrRequestToJoin` was already right: it throws `ConfirmationRequiredError` (428) at the moment of the claim. The problem was entirely in front of it. `tasks/[id]/page.tsx` computed the same predicate client-side, used it to **delete the header Claim button**, and rendered a permanent amber banner instead — on every unclaimed or flagged task in a coordinator's scope, on every reload, whether or not they were attempting a claim. On the board the card's Claim button was swapped for a "claim (confirm on task page)" link. So the check was not a question, it was a wall, and the 428 it was supposed to raise was unreachable through the UI entirely — reachable only from the REST API and the board's bulk claim.

**Claim is an ordinary button again, and clicking it is what asks.** Both surfaces now route the button through `components/tasks/ClaimGate.tsx`: a native `<dialog>` that opens the real question — *are you sure there isn't someone with just the skills for this?* — with the same three answers. The predicate is unchanged and still enforced server-side; what moved is the trigger. The one shared definition is now `isSelfAssignWorthAskingAbout(task)`, imported by the claim path and by both surfaces, so the three can't disagree about who's asked.

**Two of the three options were duds, and that was the more interesting finding.** "Suggest someone" called `suggestMemberForTask`, which writes one column — `task.suggested_member_id` — and **nothing in the app read it back**. Not the task page, not the board. The suggested person was never told, and the suggestion wasn't even visible to the coordinator who made it on reload. Only "Yes, I'll take it" did anything. The middle option is now a **real nomination** (`nominateForTask`): the member gets the emailed yes/no/not-now window, the assignment is visible, and a decline releases it.

**"Flag it for the group" is the escalation, and it was quietly the wrong call the first time round.** It shipped as a `createSignal` call, which is a *branch-scoped, anonymous, dismissable* nudge — visible only to this task's own branch coordinators. The stated intent is the opposite on all three counts: it puts the task on the shared Escalation queue **every** coordinator community-wide sees, which is the whole mechanism behind "cross-branch placement is encouraged." A coordinator who decides someone else should take this has to reach coordinators who don't cover their branch at all, and a branch-scoped signal structurally cannot do that. It now calls `escalateTask` — the same function the ⋯ menu's Escalate uses — and `escalateTask`'s own authority check (any coordination holder, or the task scope's backstop) is satisfied by definition here, since the dialog only appears for someone who coordinates this task's scope.

**It is also the one option in that dialog the wider community can see**: `attention_level: "escalated"` renders as a red "escalated" tag on the board for every member, not only coordinators. That is a real disclosure, and it is why the button is labelled as putting the task in front of other coordinators rather than phrased as a quiet nudge — and why the button hides entirely once the task is already escalated, matching the ⋯ menu's Escalate/De-escalate swap. The anonymous signal is kept where it already was (the task page's own signal control, and the coordination dashboard's response queue) because it's a different tool for a different caller: it's how someone with *no* coordination authority raises a concern, and requiring a coordinator to send one would defeat it.

**The ask-someone list is ordered by tag fit, and the ordering is a ranking and never a filter.** Spec's own wording for this option is "suggest a person (tag-matches surfaced)", so `src/lib/tasks/fit.ts` orders by shared tag count, case-insensitively, then alphabetically so equally-matched people don't swap between renders. It filters nobody: spec defers automatically weighting or default-ranking who gets suggested as real matching automation, so a member sharing zero tags stays offerable, just further down. A member's own name and existing holders are excluded, since asking yourself is not a fit.

### The dashboard, and the suggestion that finally has a reader

The view was two flat lists — engagement patterns and an availability table, neither about a single task and neither keyed to the coordinator's actual scope. It's now a page of modules, each answering one question a coordinator opens it to ask: **task status in your scope** (the headline), waiting-on-you, suggestions awaiting judgment, needs-an-owner, flagged, unanswered check-ins, the full task list, and the two existing sections. Every module resolves the *same* authority — the actor's branch column union their cycle row, intersected with the view scope — through one shared `scopedTaskCondition`, so no two modules can disagree about which tasks are theirs. Counts are derived from the rows the list already fetched rather than a second `count()`: a dashboard that says "3 unclaimed" above a list of four is one nobody trusts twice.

**A suggestion was supposed to reach a coordinator, and nothing ever read the column.** This turned up while fixing the dead "Suggest" button, and it's the more interesting of the two. `/propose` has an "I'd suggest this person" field; `activateProposal` copies it onto the new task; and from there it went nowhere. The proposal queue renders it, so the proposer and anyone reviewing saw it — but the moment the task was created, which is exactly when a coordinator could act on it, the suggestion evaporated. That is the whole gap the user described, and it was a missing reader rather than a missing feature.

So `listPendingSuggestions` is the module that makes it a signal, filtering on the only state where a suggestion is actionable: unowned, and with no live nomination against it. Once somebody's on it, or the ask has been made, it stops being a queue item. **The note is not carried across** — `suggested_member_note` stays on the proposal row. The coordinator gets the name, and the reasoning behind it is a click away on the proposal. That was the user's explicit call, and it avoided a migration for a field that only the proposal queue ever displayed.

The suggestion is also surfaced on the task page's existing Nominate disclosure, so the loop closes in both directions: a coordinator arriving by clicking the dashboard row, and one arriving by clicking the task, both find the same suggestion and the same one-click ask. A proposer's suggestion does not appear on board cards — a card carries status, and a pending suggestion is not status.

### Smaller things worth recording

**The check-in grace window reuses `stalenessHardDays`**, as `community.ts`'s own comment already anticipated, rather than adding a third near-identical column. A check-in due an hour ago is not overdue; overdue is `nextCheckinAt` plus that grace.

**Declined join requests are now visible to coordination**, which is spec's own sentence — "a stalling task with a logged decline is a different situation than a stalling task nobody's offered to help with" — and had no surface anywhere. Filtered to tasks still going, since a decline on a finished task is history rather than a stalling signal.

**Shadows don't count as holders** in the holder lists, matching `assignmentCount` and every other holder view. The holder count comes from a batched lookup rather than a join, because a join would fan a three-holder task into three rows and count it three times in the summary.

**The anonymous signal deliberately resolves to no name** in the response queue. Recovering a sender from anywhere would defeat the point of the flag.

Verified by `tsc`, `eslint` (0 errors), `next build` clean, and the full suite green (1753 tests, 88 files) against a throwaway database migrated from empty, including 15 new tests covering scope isolation in both directions, the suggestion lifecycle, the grace window, the queue, tag-fit ordering, and the cycle-scoped nav flags.

## "Other" is one control, not two stacked ones

The escape hatch on a choice field was the only part of the question form that took two clicks and still wasn't obvious. It rendered as an **"Other" row appended to the option list**, with its own text box indented underneath and the placeholder "Tell us in your own words" — which reads as two separate things: an option you can pick, and a box that happens to follow it. The reader had to work out that the box only counted if the row above it was ticked, which was never stated and not quite true.

It is now **one control: a marker beside a text field whose greyed placeholder is "Other"** — a radio for pick-one, a checkbox for pick-any, matching what each actually means. "None of these, my own words" against "these, and also my own words".

**The text field is a sibling of the marker, not nested inside its label, and that is load-bearing.** Nested — the obvious way to build "a checkbox next to a field" — every click into the field to type would toggle the marker, so somebody answering in their own words would be fighting the control meant to be enabling them. Both are siblings in a flex row now, the marker named for a screen reader and the field carrying its own label.

**The marker is now a real gate, because typing ticks it — which is what makes unticking it mean something.** The first version of this deliberately didn't: the reader took the text whenever it was non-empty, marker or not, which is forgiving but means unticking the box changed *nothing*, so a pair of controls was really one control wearing a disguise. Two existing tests pinned that forgiving behaviour by name, so this reverses a documented decision rather than fixing an oversight — and the reason it can be reversed safely is the auto-tick. `OtherFieldInput` is a **client component** for that one behaviour: the first keystroke checks the box, so "typed an answer" and "said I want it counted" are the same state by the time anyone can submit. Unticking afterwards is then a deliberate retraction, and the read side (`choiceValuesFromFormData`) honours it — a member who ticks "north", types an alternative, then un-ticks is left with just "north", not silently keeping words they withdrew.

The reader is **one function, not two**: `forms.ts`'s `formValuesFromFormData` had this logic inline as well, and a Form response and a ProfileQuestion answer reading the same shape differently is exactly how the two halves drift. Both now go through `choiceValuesFromFormData`, with a test on each side. The client component uses a **ref, not `useState`** — the marker is uncontrolled, so flipping `.checked` touches the DOM once and no re-render of the whole `FieldPreview` follows on every keystroke.

**`"Other"` is now `OTHER_MARKER_VALUE`,** because it is a contract rather than a label: the renderer emits it, `/members/data`'s report view counts a bucket of the same name, and the indicator aggregate calls the same thing "Something else". Two spellings of one word in a codebase this particular about one-definition rules is how those two start meaning different things.

**The "Other" bucket in `/members/data` could never report anything, and the same answers were being aggregated two different ways.** The per-option breakdown offered a row literally labelled "Other", then incremented only rows whose label *equalled the stored value* — but free text **is** the member's own words and never equals the string "Other", so the chip read zero no matter how many people wrote one. It was a plausible-looking number, and nothing tested it because nothing looked at it. The published indicator already had it right, inline, under a different name.

Both now go through one `tallyChoiceValues` in `field-shape.ts`, which routes every value matching no option into a catch-all. Two decisions inside it are worth stating. The catch-all is called **"Something else"** rather than "Other", because it is not only free text — an answer holding the label of an option an Admin *deleted* after people answered also lands there, and "Other" would assert a provenance that cannot be recovered from the stored value. And whether to *show* it at zero stays with the caller, because the two genuinely want different things: the indicator omits an empty catch-all, while the member-data grid shows it at zero like every other unpicked option, since that page exists to make the shape of an answer visible rather than inferred from an absent row. The grid also inherits a visible consequence of the shared tally — **answers whose option was removed are now counted rather than silently dropped**, which they previously were in both places.

Also corrected: the settings field builder's own description of the escape hatch said "They pick 'Other' and type it", describing an interaction that no longer exists.

## the test suite runs itself, and stops eating the machine

`npm test` now runs `scripts/test.sh`, which creates the test database if it isn't there, migrates it, and runs every file in batches — restarting the database when it crosses a memory budget read from the VM's actual size. No setup steps, nothing to remember, and no per-machine edits. The raw runner is still there as `npm run test:raw`.

**Why it was necessary: the suite's own database grew to 3.2GB.** The tests truncate between files, and a long-lived Postgres grows steadily for the length of a run — **~11MB per test file**, measured at 35MB → 261MB over 20 files. The part that made this unfixable by tuning: the growth **does not fall back** between files or between separate `vitest` invocations. It accumulates in the server, which is doing 36,000+ transactions against a ~20MB database. A full 88-file suite reached ~3.2GB, which is invisible on a large VM and a hard OOM on a small one — and Docker Desktop's allocation is a fraction of host RAM that the project doesn't control. A `docker restart` returns it to ~24MB in about a second, and the migrated schema lives in a volume, so nothing needs re-migrating (drizzle's migrator is idempotent regardless — 0.2s on an already-migrated database, ~1s from empty).

**This is not a production concern, and the distinction is worth stating.** Production runs the same Postgres against the same schema and never truncates; its memory is already capped by the deployed `shared_buffers=128MB` / `max_connections=50`. Measured: production Postgres sat at ~80MB after two hours of uptime, against 3.2GB for the test database. The growth is a property of the test harness, not of the app.

**The test database now runs under production's Postgres settings.** The documented `docker run` used to start on stock defaults, so a suite could pass locally and still break against the configuration actually deployed — a real gap, not a hypothetical one, and free to close.

**The container is recreated when it's gone.** It's `--rm`, so it does not survive a Docker restart; the failure mode without this was a bare connection error after a `docker compose up`.

**Verified, not assumed:** the runner was checked to exit nonzero on a failing batch (both a single failing file and a failing file mixed into a passing batch), to bootstrap from no container at all, and to report memory per batch. A cold `npm test` runs 88 files / **1769 tests** green in 5:41 with a 345MB peak, and the per-batch count matches a static `it()`/`test()` count of the whole suite exactly — so batching loses, duplicates and skips nothing.

One thing this entry is also a correction of: an earlier diagnosis blamed the kernel's `dentry` cache. That was wrong — `/proc/slabinfo` inside a container is **VM-wide and unnamespaced**, so the number read was the host's total, not the test database's. The `docker stats` figure the script actually uses is namespaced per container, which is why the script reads that instead.

## a member is told who is reading, and gets to choose which of them

The answer form was asking a member to agree to something nobody had described. It offered a single tick for "the people this Community has given access to it" — a set the member never saw, covering the kitchen team, the welfare team and anybody added next year, with no way to accept the first while declining the second. Meanwhile two facts about the question sat nowhere at all: whether the answer is counted in a published community figure, and whether a crisis can reach it. The fix is mostly disclosure, plus one change in granularity that turns out to be the load-bearing part.

**Consent is now asked per audience, one named box each.** This is the same granularity the *widening* flow has always used — a rule added after the fact gets one prompt per group, because a group is the thing being consented to — so the first asking and the second asking now agree with each other. A single shared `describeAudience` renders both, which is the point: a member asked about the Kitchen twice should recognise the same words, and a rule carrying no route at all is named as unreachable rather than as "another group in this Community", which would be a lie in a prompt asking someone to agree.

**A cleared box now takes an audience away, which is the half that makes per-audience boxes worth having.** Re-saving with a box unticked deletes that audience's consent row rather than leaving it. Without that, the control could only ever *add*, and a member still had no way to narrow sharing to a subset of what they'd already agreed to — which would have made this worse than the single box it replaced. `shareWithAudience` is now *derived* from the intersected choice (intersected against the question's own rules first, so a forged or stale id stores "unshared" rather than "shared with an audience nothing can be"); it stays as the coarser "reduce this to me and emergency" flag, and the per-rule consent rows remain the precise gate.

**Three tags above the field: who can read it, whether a crisis can reach it, whether it's in a community figure.** All three were previously either invisible or on a different page, and all three are things a member is entitled to know at the moment they type their medication into a box. Being counted in a chart matters most here — "prefer not to say" is the lever that gets you out of it, and it was impossible to use a lever you can't see. The `/profile` section explaining indicators is gone, and this is why: it was two paragraphs of text sitting nowhere near the questions it was about, which is what you get when the information isn't attached to the thing it describes. A restricted question with **no** audience gets a sentence rather than boxes, because it resolves to nobody and a box there would be a control that decides nothing.

**`sensitive` + a separate audiences list became one discriminated union** in the shared form, and the reason is a failure mode rather than tidiness: a restricted question whose caller forgot the list would have rendered no boxes and then stored "shared with nobody" on save. The union makes that a type error, so the dangerous version of the mistake can't be written, and `defaultSharedRuleIds` now lives on the restricted arm where it means something. All three call sites (`/questions`, `/profile`, the Dashboard's onboarding panel) read their audiences in one batched query per page rather than one per form.

**The extra paragraph under the share box is gone**, and the consent *purpose* notice under its own checkbox stays — that one is the notice itself, and a member is entitled to read the terms they're agreeing to.

Verified by `tsc`, `eslint` (0 errors) and the full suite green, including nine new tests: per-audience grant, per-audience revocation, the all-unticked case, a forged foreign rule id, the legacy whole-audience boolean, and the naming fallbacks.

## the member directory gets its primary action back, and mail finally has an address you chose

Two changes that both came out of actually using the pages, and both of which are mostly *removals* — of paragraphs, of a duplicated surface, and of a rule that had quietly become untrue.

**The member directory stopped being three paragraphs and started being a directory.** It opened with an explanation of the contact-visibility model, a paragraph recommending the `/members/data` grid, and an Admin-only paragraph recommending the import — all three of which were the page's *actions* written as prose. Member data is now the one primary action, importing is in the overflow behind a `⋯` for Admins only, and the visibility explanation is gone because it was never about this page (the methods are on the member's own page, which is where you go to read them). This is the app's standing action hierarchy applied to a page that hadn't been: **one filled button, at most one secondary, everything else a menu** — and an overflow that only exists when there's something in it, since a menu with a single row on a page for non-Admins is a control that says "there is nothing here".

**The community indicators moved from `/community` to `/members`, and the page now follows the view scope.** They had been on the Dashboard, then on `/community`, and on both they were the wrong thing: several cards of a graph pushing the actionable half of the page down a screen. `/community` keeps its four numbers — active members, branches, on-track branches, tiers — because a summary you read in a second and a set of charts are not the same surface, and a page with events and assemblies to show has room for one. `/members` is where they belong on the merits: an indicator is an aggregate *about members*, built from questions the members asked and answered themselves.

**That is also what gives the per-event indicator setting something to do again.** `cycleIndicatorsEnabled` (Settings → Coordination) exists to decide whether an indicator may be broken out for a single event's attendees, and the Dashboard was the only surface that ever asked for an event scope — so moving the indicators anywhere else would have left a settings screen promising "On, each event gets its own figures" where no page did that. `/members` is the one page that can be *about* an event, so it now follows the nav switcher the Dashboard and the board already read: a single event in view, and the directory is that event's attendees with the charts describing the same group; "all open events", and both describe the whole Community. **One control for one question.** A second toggle on the page would have been a second thing that could disagree with the switcher above it. The setting's own copy was rewritten to name where it takes effect, and a `stateLabel` that still promised "the smallest population one is shown for" — the headcount floor dropped in `0081` — was corrected in passing.

**The list and the charts read the same query, because a chart reading "of 8" above a directory of nine names is exactly the disagreement the denominator exists to prevent.** `eventPopulationIds` in `indicators.ts` had its own copy of "who's coming to this event", which the directory now also needs — so it's one exported function (`listComingMembers`, in `participation.ts`, next to the participation it reads) that both call, rather than two that have to be kept agreeing.

### The email address, which turned out to be a real gap and not a missing feature

**Every email in the app went to `member_identity.login_email`, and no member could see or change it.** Announcements, targeted messages, task nominations, the backstop hard-flag: four call sites, each reading that one column independently. It is the magic-link *credential*, so it is deliberately not editable, and nothing in the UI ever displayed it. Meanwhile `contact_method` — the only thing `/profile` offered to add an address to — was **never sent mail at all, by any path, ever**. So a member could add a second email, be told their announcements went there by nobody, and receive them at an address they couldn't find on their own profile. The one control in that area, "Email me targeted messages and announcements", gated delivery to somewhere invisible.

**The fix is one flag on the row the member already manages: `contact_method.is_primary`** (migration `0084`), with `resolvePrimaryEmail` as the one definition every send now reads. It is deliberately independent of `visibility` — which is who else may *read* the address, versus who the platform *writes* to — so the delivery address can stay `emergency_only`, which is how it is seeded, because a member's mail address is nobody else's business by default.

**Two rules, both because the alternative is mail going somewhere surprising.** A row must be **verified** before it can be primary: `verified_at` is set by clicking a link sent to the address, and is cleared whenever the value changes, because otherwise pointing delivery at an address you don't control is a way to aim a Community's mail at a stranger. And the primary **cannot be deleted while it is primary** — cascading the flag away would leave a member receiving nothing with no error anywhere — so the row states what it is instead of offering a Delete button that exists only to be rejected.

**Verification is a real check, and it stops at the right place.** The cheap version — treat any address as eligible — would make the gate decorative. A full RFC parser would be theatre: the only honest test of an address is whether mail to it arrives, and that is what `verified_at` records. A shape check exists only to stop a telegram handle or a half-typed address being offered as a delivery target, and `contactMethod.type` being free text is exactly why it has to be. Provisioning seeds the row from the login address on all five arrival paths (magic-link first login, OIDC, invite redemption, application conversion, admin import) and marks it verified **only where the address is already proven**: a magic link that was clicked, or an OIDC `email_verified` claim of `true`. An inviter's or Admin's knowledge of an address is not proof of the inbox, and pretending otherwise would make the flag mean "somebody in the loop believed this" — much weaker than the thing the primary gate relies on. OIDC with no `email_verified` claim at all is common, and is carried as `null` rather than collapsed into `false`, so "the IdP has no opinion" never looks like "the IdP said no".

**The primary is also the magic-link address, and that is safe.** A member who moves their primary to a second address could otherwise find that "this is where we email you" isn't true of the one thing the app emails you about most. `findOrCreateMemberByEmail` matches it — and this is not a new credential store, because a match still only produces a link *sent to that address*, so possession of the inbox remains what proves you, exactly as before. **OIDC never consults it**: an OIDC identity is keyed on the `sub` claim, and the spec is explicit that it is never an email.

**A latent double-send, fixed on the way past.** `deliverToRecipients` mapped over every `memberIdentity` row per member with no dedupe, so a member with two identities — a magic-link and an OIDC one on a single account — would have received every announcement twice. Not reachable today, because every provisioning path creates one identity per member and OIDC deliberately refuses to attach to an existing member; but `recruitment/pairs.ts` already deduped for exactly this reason while this path hadn't caught up. Delivery now resolves one address per member, which is the rule rather than a patch.

**`0084` seeds the five provisioning paths; `0085` backfills everyone already in the database.** A member who arrived before this shipped had no row, so their delivery address stayed an invisible column — the same gap the feature was built to close, just for old accounts instead of new ones. The backfill copies each member's login address into a primary, and is deliberately timid in three places: a member who **already has a primary** is left alone; a member who has **already added that address as an ordinary contact method** gets no duplicate, since promoting their row would mean the migration choosing a `visibility` they picked; and `DISTINCT ON (member_id)` because a member can hold both a magic-link and an OIDC identity, which would otherwise produce two primaries. Verified idempotent by running it three times against a seeded database: one row, one primary.

**`verified_at` is set only for magic-link identities, and that asymmetry is the interesting part.** Those are *provably* verified — a magic link only ever goes to an address, and the identity existing at all means somebody clicked the one that arrived. An OIDC identity is left unverified because `email_verified` was never stored: `member_identity` keeps `login_email` and nothing about how the IdP vouched for it, so the honest answer to "was this address verified?" is *unknown*, and an unknown must not be written down as a yes. It costs the member nothing — the fallback delivers to the same address, and their profile offers the one-click confirmation that settles it. Three tests now pin the invariants the backfill depends on (one primary per member, per member not per community, and a two-identity member), since a migration can't be covered by a test that runs against it.

Verified by `tsc`, `eslint` (0 errors) and the full suite green.

## who joins, how, and what the community decides — plus a settings screen you can read

`docs/joining-admission-plan.md` had been sitting half-built: the lane table, the resolution chain and the `direct | referral` retirement landed, and steps 2–8 of its own work plan — the third door, the mediation grant, support and nomination, consensus, pairing, and every surface that would show any of it — had not. This is the rest of it, and a rebuild of `/settings` around it.

**The idea, in one sentence: a declaration picks a lane, and the community's rule for that lane is the whole experience.** Not a matrix, not a second decision system bolted onto the old checkboxes. The inviter's marks (or a public applicant's own arrival) select one of four lanes, and each lane carries two settings and no more — how much extra proof it wants, and whether it asks for a form and an interview. Both marks count as *knows personally*, because the stronger signal should win rather than inventing a fourth lane for "ticked both".

**The defaults are today's behaviour, and that is asserted rather than hoped for.** Knows-personally admits outright; a good-fit or unmarked invite, and a public application, go through the evaluated funnel. A test walks all four lanes of the §2.9 table and the settings panel's "Welcoming" preset is compared against the same object — if the two ever drift, one of them fails.

**A settled nomination lane admits outright, which took two functions and is the bug worth naming.** §2.2 says a second's support "converts it to the light path" and J6 says a lapse "falls through to the lane's process path". Both are statements about the lane's **process**, not its mode, so `settledPathForRule` asks the process and `laneRedemptionKind` still answers "is this direct right now". Reading the mode instead — the obvious thing, and what the first version did — sends every settled nomination lane to `/apply`, including the ones that asked for no application, so a person who skipped a wait they never needed landed on a page saying applications aren't accepted. The same question decides where "skip the nomination" goes: the support page hands them their *invite's* URL rather than `/apply`, because `/invite` is the one page that knows both destinations.

**The third door is checked in three places, not one.** `interviewsOpen` exists per cycle and community-wide, and it is enforced when an invite is created on a lane that wants an interview, when a poll is scheduled on a decision, and when a shared interview is offered. Enforcing it only at scheduling time would have made "interviews closed" a thing the backend broke a moment after being told.

**The mediation grant is its own module, community-shaped and multi-cardinality, with the plan's hint text verbatim** — "Holder mediates recruitment objections …, sees objector identities that are shielded from everyone else, and may exercise the majority overrule where the community has enabled it." It sits next to Recruitment in the permissions panel rather than under it, because §2.7's whole point is that a community can hand it to a different task from the one that evaluates applications; a name that read as a sub-role would quietly re-couple them. Nothing holds it by default, and the mediation page says so to a member who has arrived without it, rather than rendering an empty queue.

**An objection is no longer thrown out by a clock, and a timer can now only ever admit.** The old evaluated path held an outcome `pending` until a holder happened to act, which in a passive team meant the objection vetoed the arrival forever and nobody was told. Now: no concern by the deadline and they're in; a concern stands, becomes a duty item on the Dashboard, and goes to the mediation body. `resolveWiderDiscussionManually` refuses while one is standing — the server was already the source of truth, and the Resolve buttons are now *gone* rather than disabled, because offering an action that silently does nothing is how a team comes to believe it waved a concern through. The mediation page is the first page here built around a duty rather than a queue, and it names the body and the threshold before it lists anything.

**A concern can cost somebody their place, and that is the default.** Clearing it and upholding it are mediation's own conclusions and need no threshold; admitting somebody *over* a concern nobody could resolve is the exception, and it takes a majority of the body's current holders (strictly more than half, clamped to 1 for a body of one, since half of one rounded down lets a person overrule their own veto) or a fixed quorum the community sets. A quorum the body can't reach reports itself as *unavailable* with the reason — a community that has decided objections are never voted away gets that as a decision, not as a threshold of one.

**The shield is at rest, and it leaked in a place the plan only hinted at.** `objection.raised_by` was always stored and always hidden; now it's readable by the mediation body and the objector and nobody else — not the evaluators, not the applicant, and not the inviter, since §2.6 names the leak "through the invitee's friend". The inviter is also barred from raising an objection at all, which is the cheapest way to keep that promise. The objector can recuse anyone from the body's view and can consent for one named person to be told — and being told is deliberately *not* the same as being able to see the row, so a consent never silently un-recuses anyone.

**Two consent steps, stored where each one's subject can be read back.** The inviter ticks "I've told them" at send and cannot send without it; the invitee reads the generated disclosure and ticks their own box at redemption, and the exact words are stored with the tick, so the record answers *what were they told* rather than *did they say yes*. Without it the arrival never becomes visible — concretely, a consensus invitee's participation row isn't seeded until the window closes clean, which is what makes the gate real rather than decorative.

**A new support page, one link, two faces.** The same token renders the support view to a member (with the know/fit marks, and "already a member? log in" for everyone else) and the application to a logged-out visitor. The inviter's flow shows the live consequence sentence for whichever combination of marks is currently ticked — the same sentence the settings panel and the applicant read, from the same function, so the three can't disagree about what a rule does. A nomination lane hands back a support link at creation and lets the inviter name members to email it to, one email per person, because the plan is explicit that nothing broadcasts the nominee's existence beyond who the inviter chose.

**Pairing is recorded and the platform decides nothing from it.** A named member gets the support view (which *is* the second's vouch); a named non-member gets a link that routes to the application pre-paired, and the namer then confirms the person who arrived is who they meant. Paired applicants can be offered one interview instead of two — offered, and only accepted if exactly one side has a poll of its own, because merging two existing interviews is a different operation from sharing a new one. No lane, capacity count or decision rule reads a pair anywhere.

**And the settings screen, which is the other half of this.** It was one giant form per tab: a typo in the decision-rules JSON silently rolled back the door toggles somebody had just changed, every unrelated setting had to be resubmitted to fix one number, the whole tab body sat inside one `<fieldset disabled>` so a member reading settings they have a stake in reading got a wall of 60%-opacity text, and the consequence of any given toggle was a paragraph somewhere below a group of unrelated toggles. Now one card saves itself, every card says what its setting *does*, the disabled state is per-control so the explanation stays legible, and the decision rules have their own card with the example in a block you can copy rather than escaped JSON inside a hint. The read-only wrapper is still one `<fieldset disabled>` — it is the only thing that reaches the client-side editing widgets, and it now carries no blanket dim, so the explanations stay legible while only the controls fade. The ten tabs are ten files; the page keeps the access check, the shared data, and which tab is active.

**The lane editor is the one place the page spends a client bundle, and it's there for a specific reason.** The plan's legibility argument is that a rule reads as a consequence sentence, and a sentence that only appears after a save is a changelog, not a consequence — so the sentence is derived on every keystroke. It imports only the *pure* half of the lane model, which is why that half was split out of the db-touching module in the first place.

**Then it was driven in a browser, and the first thing the browser said was that a settings screen can be wrong in a way no test was looking for.** `scripts/rebuild.sh --build` (the entry below) makes a local build reachable, so this was built, migrated and clicked rather than described. One thing turned up that 1668 passing tests had not.

**The lane summary said "plus an application and a interview".** The one-line sentence above each lane card is the whole legibility argument for the panel — it is what a rule *is* to somebody deciding whether to open it — and it rendered a wrong article on three of the four cards of a community that has touched nothing, which is the default state. The article was written once in front of the list (`plus an ${process.join(" and a ")}`), so it read correctly for exactly one combination. It is chosen per item now, with a comment saying that the table isn't carrying cleverness, it is carrying the third process step that doesn't exist yet. **The test that should have caught it asserted `length > 0`**, on the one function whose entire job is that the string comes out readable; it now rejects `undefined`/`null`/`NaN` and a wrong article in either direction, and the four combinations are spelled out.

And re-navigating to the tab after a failed save drops the `?error=` parameter, so the banner vanishes and the second reading reported a silent failure that wasn't. ## a saved dropdown no longer reverts on screen — 23 more sites, and the diagnosis the first commit didn't carry

Changing a setting and watching the control snap back to its old value, then finding the change *had* saved, is a bug that punishes the person who just did the right thing: it reads as "my edit was rejected" and invites a second, contradictory save. Found on `/settings` → Events & Tiers, where changing an event type's suggested starting event appeared to revert, and a refresh showed it had worked.

**Cause, read out of the React source rather than guessed at.** `defaultValue` on an uncontrolled input is a *mount-time* default, not a value React keeps in sync. In react-dom 19.2.8's `updateDOMProperties`, the `select` case resolves to:

```js
null != _propKey8                              // has a `value` prop? → controlled
  ? updateOptions(domElement, !!multiple, _propKey8, false)
  : !!lastProps !== !!multiple && (             // ← only when it changes between renders
      defaultValue != null ? updateOptions(domElement, !!multiple, defaultValue, true) : ...);
```

A settings form is uncontrolled in both renders, so that second condition is `false !== false` and `updateOptions` never runs again. The selection was set once at mount and nothing re-applies it. So the Server Action's `revalidatePath` genuinely refetched, the component genuinely re-rendered with the correct value, and the browser still showed the pre-save selection — a hard refresh then looked like proof the save worked when it only re-mounted the element.

**This is specific to `select`.** `<input defaultValue>` goes through `setProp`, which moves the displayed value when the field isn't dirty, and the person saving is the one who last typed in it — so text fields already looked right. `<input defaultChecked>` is self-consistent for the same reason. That asymmetry is why this read as a dropdown-only bug and why a text field never exposed it.

**`SelectField` (`src/components/ui/SelectField.tsx`) fixes it by remounting on the value.** `key` is the one thing that reliably re-establishes a mount-time default, and keying on the *value* rather than anything incidental means the element is only remounted when the server's answer actually changes — an unrelated re-render (someone else's edit, a nav prefetch) leaves it, and any half-made selection in it, completely alone.

**`SelectField` and the eight `/settings` call sites landed unlabelled in `ef121a3`**, swept in by a `git add -A` alongside the question work, with no mention in that commit's message. This commit finishes the job: **23 more sites across 15 files** — `/tasks/[id]`, `/calendar`, `/participation`, `/budget` (including the voting rank select), `/profile`, `/applications`, `/feedback`, `/shifts`, `/spatial-planning`, `/proposals`, `/task-packs/import`, `/scheduling-polls/new`, and the two shared components `DateModeField` and `ProfileQuestionForm`. `SelectField`'s `defaultValue` accepts `number` as well as `string` because a value pulled out of a `Map` is usually typed `string | number` and an `<option>`'s value is a string either way.

**Two `<select>`s deliberately left alone:** `board/BranchFilter.tsx` and `board/TagFilter.tsx`, whose values are React state driving the control rather than a saved setting re-read after a write. Remounting them gains nothing and would add churn on every filter change. The two `previewView` grid/list toggles are excluded on the same reasoning. Selects already carrying a `key`, and controlled ones (`value` + `onChange`), were skipped by construction — `DateModeField`'s parent/phase switcher is controlled and its phase picker is not, so exactly one of the pair changed.

Verified by `tsc` and `eslint` clean and the full suite green. **Not verified in a browser** — the argument is read out of react-dom's own source and the remount is a documented React guarantee, but the dropdown holding its new value after a real save has not been watched happen, and that is the one claim worth a real pass on `/settings` → Events & Tiers.

## an event's admission rules are stated to the whole community, and a community rule says which events it won't reach

A community can set four admission lanes — one member's word, N members' backing, announced to the community — and each event can run differently by overriding a lane, falling back to the community's. Both halves of that were already built: `joiningLane.cycleId` is nullable, resolution is cycle-then-community-then-default, and the event page has had a per-lane "this event has its own rule for…" checkbox for a while. **Two things were missing, and both were the same omission — nobody could see the state.**

**Members saw nothing at all.** `cycleLaneRules` and the lane rows were gated on `canConfigure`, so which rule applied to the lane somebody would arrive by was invisible to anyone who couldn't start an event. That is not an administrative fact about an event; it is this community's admission design, and the person being measured against it is entitled to read it. The rules are now stated to every member — lane, what it currently requires, and whether that's the community's rule or this event's own — with only the fork controls Admin-gated. **The same split the settings screen uses: the state is everyone's, the editing is an Admin's.** This required moving the block out of the Admin-gated "Event settings" section, since it was nested inside it.

**Nobody editing a community rule could tell what it would reach.** Inheritance here is the *absence of a row*, not a copy of the community's value — deliberately, so a community default stays true instead of freezing into a second unmaintained version at the event that overrode it. But that only works if the shadowing is visible, and it wasn't: an Admin could change a community lane and have no way to know it would reach next season's event but not the one next month. `listLaneOverridesByCycle` is new, and the community screen now names the events that override which lanes, links to each, and says plainly that a change reaches every event *except* these. `listOverriddenLanes` already existed and had no callers; the event page's new "N of 4 lanes work differently here" line is its first.

**Six tests for the inheritance model, and one of them is the point.** Un-ticking a lane deletes the row, so the lane resumes *tracking* the community rather than being restored to whatever the community happened to say at the time. A test asserting only the immediate value would pass even if the code snapshotted instead — so the test changes the community rule *after* the reset and asserts the event follows it. That is the property the whole never-snapshotted design rests on, and it was previously untested. Also covered: one overridden lane not dragging the other three, resetting one lane leaving other overrides alone, the community-wide listing (including that a `cycleId`-null row is not an override of itself), and a community row never appearing in the override list.

**A correction to something I said earlier in this work:** I claimed nothing could write a per-event override and that the writer was missing. It exists and is called — `setCycleJoiningLaneRules` from the event page's action. The gap was never the write path; it was that nothing *read* the state back to a person. `listOverriddenLanes` having zero callers was the tell.

Verified by `tsc` and `eslint` clean, `next build` clean, and the full suite green. **Not verified in a browser** — moving a block out of a gated section into its own member-visible one, and the read-only variant of the lane list, both want a real look.

## every settings card states what the setting currently is

The settings screen had been rebuilt into one-card-one-save, which fixed the real hazard — a rejected decision-rule set silently reverting the doors — but left the screen unreadable as a *description of the community*. Every card was a form. Opening the tab told you how many cards there were and nothing about what any of them was set to: not how many branches exist, not whether single sign-on is on, not what a tier's threshold was, not whether anyone can apply. Reading the configuration meant opening all ten tabs' worth of cards and reading the controls.

**`SettingsCard` takes a `state` and is now a disclosure.** Collapsed, it is a title and a sentence saying what the setting currently is; expanded, it is exactly the card that was there before — all the controls together, then one Save. The structure is forced rather than chosen: a `<summary>` and a `<form>` cannot share a parent, so the header is the summary and the form is its sibling. `aside` stays out of the summary too, since it carries destructive actions and a nested form.

**All 25 cards now state their value**, and several needed judgement rather than a mechanical read of the column:

- **Colours** show the *resolved* accent with a swatch, not the raw column. A null accent is not "no colour", it is the design tokens' own documented default, so a state line reading "none" would be a lie about what the app is currently showing. Same fallback the inputs use, so the line matches what saving an untouched form writes.
- **Single sign-on** reads "Not configured — everyone signs in with a magic link" rather than three empty fields, and otherwise names the host rather than the full issuer URL, because `https://id.example.com/realms/main` is a configuration detail and `id.example.com` is the thing you recognise.
- **A tier whose criterion is derived** states the threshold and the event type on the collapsed side, which is where it already appeared inside the form — so that paragraph is removed rather than said twice.
- **Decision rules** are summarised in the sentence an admin would use: *"2 rules, first match wins — if 2 say proceed, they're in; if anything else, announce it to the community (resolving to proceed if nobody objects)."* This is the field the surrounding comment calls the one most likely to be wrong, and it was previously only legible as escaped JSON; being able to read the intent without decoding is what makes a wrong rule obvious before it decides somebody's application. The JSON editor is untouched — the state line is a reading of it, not a replacement.
- **A branch** says whether its call requirements are its own or inherited, rather than showing three selects that all read "inherit".
- **Admission rules** reuse the lane summaries the read-only view already had, so an admin and a member are reading the same sentence.

**Create cards say "Create", not "Edit."** A card whose subject does not exist yet was inviting you to open something there was nothing to edit. That is an `affordance` prop rather than a guess based on the absence of `state`, because a real setting can legitimately have no state to show.

**Two unit labels were wrong and are fixed.** "Answer a task nomination within (hours)" and "A call summary waits this long before counting as unread (hours)" were both labelling **day** columns. An admin following the label would set `3` meaning three hours and get three days, on two settings where the number is the entire point. The state lines now also carry the unit — "a nomination is backed for 24h · a community-checked arrival is announced for 48h" — because a bare number next to a setting whose unit matters is the same unreadable figure the bad label was hiding.

Not done here: the decision-rules JSON editor itself is still a textarea (the joining lanes got a real `LaneRulesEditor`; this field did not), and the cycles page is still the old flat layout. Both are the remaining items of this sweep.

Verified by `tsc` and `eslint` clean, `next build` clean, and the full suite green. **Not verified in a browser** — this change is almost entirely about what a collapsed card looks like, which is the one thing static checks cannot see. The two-click cost of editing anything, and whether a list of twenty collapsed cards reads better than twenty open forms, both want a real look before this is trusted.

## a question's audience moves onto the question, and the Access rules section goes

Restricted-question access was configured in two places on the same screen. The audience was chosen in the question's own form at creation, and the separate **Access rules** section existed only to append a group to a question that already had one — a list flattened across every question, identifiable only by reading the question label inside each row. Answering "who can read this?" meant finding a question's row in one section, and changing it meant visiting another.

**The data model never had that split, and removing it is therefore clean.** `createProfileQuestion` stores the creation-time audience *as a rule row* (`questions.ts` — it inserts the question, then calls `createSensitiveFieldAccessRule` with the audience and the new question's id, then sets `sensitive`). So "the audience it was created with" and "a group added later" were never two mechanisms; they are both `sensitive_field_access_rule` rows keyed by `questionId`. The two UI locations were presentation, and one resolved list per question is the honest shape.

**Each question card now states its audience on the collapsed side**, resolved to the same sentence an admin would say out loud — "readable by anyone in Tier *Kitchen*", "anyone holding a *Welfare* grant" — reusing the resolution the rules list already did. It also states the **answer options** for a choice question, which were previously only visible by opening the card. Both were the state of the thing, and a card that only said `restricted` made a reader open it to learn the one fact a privacy surface exists to communicate.

The empty case is stated rather than left blank: a restricted question with no rules reads "Readable by the person who answered, and by whoever activates Emergency access on their page. Nobody else." That sentence is **relocated from the section this commit removes**, which is where the honest description of the empty audience already lived. It matters because that state resolves to nobody-but-the-owner, which reads as broken rather than as private unless it is said.

**Adding a group is on the card, and says what it does.** The form needs no question picker any more — the card *is* the question — which also removes the one way to widen the audience of the wrong question. The consent consequence sits on the control rather than in a preamble some distance away: a new rule reaches only answers given from the moment it exists, everyone who already answered is told and asked to extend sharing, and until each of them says yes their answer stays with the audience that already had it. Removing a rule is the opposite and needs nobody's agreement, so the two read differently rather than both being an unremarkable "Delete".

**A new disclosure explains how privacy and consent work for these questions** — restricted-is-fixed-at-creation and why, what a rule is, widening versus narrowing, emergency access as an override rather than a permission, and why publishing needs no separate consent. It sits beside the existing "how answering and required questions work" disclosure: both are long and true and nobody needs them on every visit, while the per-category blurbs below carry only what is specific to that category.

Nothing about the question list's organisation changed — the public/restricted sections and the per-event grouping stay as they were.

Verified by `tsc` and `eslint` clean, `next build` clean, and the full suite green. **Not verified in a browser** — the audience line, the options line and the relocated disclosure have not been seen rendered, and the cards' collapsed/expanded balance is exactly the kind of thing that wants a real look.

## `sensitive` becomes the one immutable thing, and widening an audience starts asking

**The flag that governs who can read a person's answers could be flipped by anyone with settings access, in both directions.** Ticking it made a question restricted; un-ticking it made every answer given so far readable by the whole Community — including answers given while it was restricted to the kitchen, by people who answered against that narrower audience. No confirmation copy makes that a setting rather than a disclosure, so `sensitive` is now **absent from `updateProfileQuestionInput` entirely** rather than validated-and-refused. It is the one profile-question attribute with no update counterpart, and unrepresentable is the stronger of the two: a validation can be bypassed by a caller that doesn't go through the schema, an absent field cannot be set at all. The remedy is the one the codebase already has for questions — archive and re-add, which leaves the old answers on the old question rather than reinterpreting them. Emergency access stays mutable, because switching it *off* discloses nothing; the two flags are deliberately not symmetric.

**And a sensitive question is now restricted *by* its audience, at creation.** There is no third "owner-and-emergency-only" state to choose: a rule-less sensitive question resolves to nobody-but-the-owner, which reads as broken rather than as private, so an admin who believed they'd narrowed something to the kitchen had narrowed it to something that looks like a bug. The write side refuses a restricted question with no audience and an audience with no restriction. `createProfileQuestion` takes `sensitive` and `audience` together and does the insert → rule → flag sequence internally, which retires a dead end that had been in the UI for a while: creating a restricted question used to be three visits to two settings sections, because the flag was refused on create and freely toggleable afterwards.

**The gap the immutability work uncovered: adding a group to an audience took everyone's answers with it.** A rule says who *may* read a question, and that was the whole answer — so an Admin adding a welfare Tier to a question that already had answers reached every one of them at once, with the people themselves never asked. `profile_answer_rule_consent` (0081) is the second half: a rule reads an answer only where the answer's owner agreed to **that rule**. Answering consents to the rules in effect at that moment, because the member was answering against a known audience; a rule added afterwards has no row and cannot reach the answers that predate it, and each of those members is shown a prompt to extend sharing on their own profile. The read side requires the row, so every path fails closed.

Per **(answer, rule)** is the only correct granularity, and the two alternatives are each wrong in a different way. Per-question is the existing `shareWithAudience` boolean, and an answer given when the audience was {kitchen} and later widened to {kitchen, welfare} is a case it cannot express: `false` hides the answer from the kitchen too — a narrowing nobody asked for and that the kitchen did not consent to — and `true` exposes it to the welfare team, a widening nobody agreed to. Per (member, rule) is wrong because a rule deleted and re-created is a *different* rule, and consent to a rule that no longer exists should not silently carry over to whatever replaced it. The consent table lives in its own schema file for the same reason: it's the one table in this corner that references both `profile_answer` and `sensitive_field_access_rule`, and the latter already references `profile_question` where the former lives.

**The starter set's emergency contact now asks instead of assuming.** Its `needsChosenAudience` flag is a statement that none of the fourteen permission modules means "responds to emergencies" — Admin least of all, since holding Admin is about who manages a Community's settings and is no reason to hold someone's welfare details. So the review step offers it with the audience picker empty and required, and the **unattended signup path skips it**. That is the one intentional difference between the two entry points, and it is a difference of omission rather than of guesswork: a wrong guess there is a disclosure, not a formatting error.

**`member.consentsToCommunityIndicators` and `community.cycleIndicatorsMinMembers` are gone** (0081), along with the standing "may I be counted in indicators" opt-out on `/profile` and the per-event headcount floor. The consent's own justification was that "a decline is a response to *one* question, and a question invented later has no decline for them to have used" — which stopped being true the moment publication was restricted to public questions, because an indicator is then an aggregate of answers the whole Community can already read individually, so publishing one discloses nothing the underlying data doesn't already say. What the column actually controlled was whether someone was *counted*, and the per-question decline is the right lever for that: it's required on every publishable question, and it's a stored refusal with its own number in the aggregate rather than a gap, because silence is visible and would leak through the very gap meant to protect it. The one thing the column bought that a decline doesn't is "answer, but don't be a bar in a chart" — and that combination only wanted to exist because an aggregate of private answers existed, which it no longer does.

The floor guarded nothing for the same reason: a published indicator is an aggregate of answers everyone can read one at a time, so a chart over three people discloses nothing the member-data grid of the same three doesn't. The declined count is the case that *looks* like it should need a floor and doesn't — "1 of 3 declined" tells you one of three named people declined, and a decline is a decision about a question everyone can read rather than a fact about the person. Someone who declined to give their pronouns is made identifiable by an *answer*, which was never published. What survives of the old behaviour is the one guard that was never a privacy question: an event with *nobody* signed up falls back to the community-wide figures with a note saying why, because there is no group to group by and an empty chart with a heading on it is a broken widget.

**And switching `emergency_access` *on* asks too** (0082). The flag stays mutable while `sensitive` is immutable, and that asymmetry is the point rather than an oversight: switching emergency access *off* discloses nothing, so a Community should be able to stop advertising a standing emergency reachability of its members' facts, and nobody's consent moves. Switching it *on* for a question that already has answers is a widening over answers given under a different posture, so it resets the consent on every existing shared answer and prompts each owner — the same story as the audience, in a different shape.

The consent is a **column, not a table**, and the difference is worth stating because it looks like an inconsistency. An audience is a *set*: agreeing to the kitchen team must not hand over to whoever was added last week, so consent is per (answer, rule). Emergency access is a single route, so there is nothing finer to distinguish — "I agree to this being reachable if someone activates emergency mode on my page" is one fact about a person. Putting it in `profile_answer_rule_consent` would have needed either a nullable `rule_id` with a magic value for "the emergency route" or a sentinel rule row that isn't a rule, and both put a fake audience into a table whose entire meaning is "somebody in this Community may read this question".

Two populations are deliberately not asked, and both are cases where **nothing actually widens**. An answer that already un-ticked the share box is emergency-only *by that choice*, so asking again would be asking about a reach they chose — and worse, it would leave a permanently unanswerable prompt, since re-answering with the box still unticked is the same choice. And a decline or a deferral holds no value, so there is nothing to reach. Re-answering *does* agree, for the same reason as the audience half: someone re-answering a question has just been shown what it is and who it is shared with, so making them find a separate button for the same fact would be a second thing to remember about a question they already know.

**The settings screen is now two sections, public and restricted, and the questions are rows rather than forms.** A full editable form per question was the right editing surface and the wrong listing surface: with twenty questions the tab was twenty forms, each carrying a field editor, a live preview, seven checkboxes and two submit buttons, and the only way to find the one you wanted was to read past all of them. Each card now states the facts — what it's called, how it's scoped, whether it's restricted, published, required — with the form behind an Edit disclosure. One explanatory paragraph per section, the general mechanics behind an info button, and the event-scoped questions in their own sub-section showing the current cycle's phase questions with the rest behind a link. The Access rules section is reframed as what it now *is*: adding a group after the fact, which is a widening, which is why it only reaches answers given from that moment on unless each affected member says yes.

Verified by `tsc`, `eslint` (0 errors) and `next build` clean, and the full suite green (1627 tests, 83 files) against a throwaway database. The tests are the interesting part: the ladder tests were rewritten around a `createRestrictedQuestion` helper because the three-step create/rule/flag incantation was the only order the old write side permitted, and a shape that has to be spelled out in thirty places is a shape that will be wrong in one of them. New coverage asserts the property that decides the disclosure — a rule added after an answer does not reach it, in both the narrow and the batch resolver, and agreeing to one group does not agree to the next — plus the kitchen case where getting it wrong hurts somebody, since a nut allergy nobody could see is the sharp end.

## the dev deployment can be updated again, and two bugs a passing test suite had missed

`scripts/rebuild.sh` had one path, written for the production VPS: pin the image to `git rev-parse HEAD`, `docker compose pull app`, restart. That is right for a 1-2GB box where building caused the "Ineffective mark-compacts near heap limit" OOM and the "no space left on device" that moved the build to GitHub Actions in the first place (`03ce132`), and it is still the default. It is wrong for a development machine, for a reason that is not about resources: **a pull can only ever deploy a commit that CI has already finished building.** Working-tree changes — which is what a session produces — are undeployable. To look at your own work in a browser you had to commit, push, wait for Actions, then pull, and that is how a run of changes ended up carrying "not verified in a browser" through several changelog entries when the browser was sitting right there on `localhost:3000`. The running container had drifted to a two-week-old `:latest` while HEAD was three commits ahead, so even committed work wasn't reaching the dev box.

`--build` (or `ORCHARD_BUILD_LOCAL=1`) builds here instead and tags the result with HEAD, the same tag CI would have used. Nothing about the VPS path changes, and the `docker image prune -af` that goes with pulling is deliberately not run on the build path — that prune answers a slow disk leak on a production box, and applying it to a machine that builds constantly would throw away every other local image and the base layers the next build would reuse.

Two things the build surfaced while fixing it. `docker compose build` in Compose v5 has no `--target`, so the `checks` stage is run with `docker buildx build --target checks --output=type=cacheonly` — which is exactly what the CI workflow already does, and restores the fast lint-then-build pre-check the Dockerfile's own comment describes but the script had stopped doing. And the review-step import that broke the build (see below) is the documented reason `defaults-table.ts` exists: a client component cannot import anything from a module that reaches `@/db`.

## the two sensitive-data systems collapse into one, and the audience ladder finally runs

There were two. The four fixed `member` columns (health conditions, allergies, emergency contact, orientation) had a module toggle, a roster grid at `/sensitive-data`, a consent gate, and exactly one live reader between them — the kitchen's dietary panel, for allergies. Sensitive profile questions had a per-answer audience, indicators, emergency reveal, a per-answer share switch — and **no cross-member read surface at all**. They shared the access-rule table and nothing else.

**The consequence was that `sensitive` restricted nothing.** `resolveReadableQuestions` had exactly one production caller and it passed the viewer as the owner, so level 2 of the ladder short-circuited on every real request. Its own comment said so: *"Inert while /profile is self-only… already correct for the members view that's coming."* Every test that exercised the audience called it directly with a fabricated second member — the tests were true and the feature was inert. On a real surface, `sensitive` did two things: it blocked publishing, and it marked a question *eligible* for emergency reveal. The rules meant to restrict it reached nothing, which is why the Access Rules section read as configuration for an inert thing: an admin tuning a question's audience was editing a value no read path consulted.

So the questions win — an enum could only ever name those four, whereas a question carries any of them plus a share switch, an audience from three routes, emergency eligibility and consent gating. Migration 0080 drops the columns, the enum, the `sensitive_data` module, `/sensitive-data`, its API route, and the column half of both the rule and consent tables. `question_id` is now `NOT NULL`, so "which of two things does this rule name" is unrepresentable rather than validated by the application layer. No data migration: no Community held values in those columns, which was checked rather than assumed.

**`/members/data` replaces the grid, and isn't sensitive-only.** Every question the viewer may read about other people, with column selection, a value filter, per-column counts, and per-option breakdowns for a choice question — "4 vegan, 2 gluten-free" rather than a number with the raw values beside it. Column selection is honoured verbatim, so a stale bookmark can only ever *remove* a column, never add one, and the readability check still runs per row on top of it. Not sensitive-only on purpose: a coordinator planning an event wants the same table either way, and a sensitive-only page would be a worse version of the one that exists.

**The consent gate on questions now exists.** `getGatingPurposesForQuestions` was written, validated, made configurable in Settings, and had **zero callers** — an admin could pin a purpose to a question, a member could grant and withdraw it, and withdrawing changed nothing at all. It's now the read path's gate, so a withdrawal takes effect on the next read, and `answerProfileQuestion` refuses to store an answer to a gated question without consent. Both are tests now. A gated column also reports how many members have agreed, because "0 of 12" reads identically whether nobody answered or nobody consented.

**The kitchen reads questions, and no longer needs to know which one is "the allergies" one.** There is no stable identifier on a question to mean that — the starter set's `key` is a form-field name and isn't stored — so a lookup by it would be a guess. Instead the panel keyword-matches *every* sensitive answer the holder's audience covers. A community that restricted "Dietary needs" now gets it checked, which it didn't before. Non-sensitive questions are excluded deliberately: matching against them would turn "languages you speak: soy?" into a food-safety incident. This also closes a gap where the dietary panel read `member.allergies` with `sensitive_data` off, contradicting the food-and-drinks plan's own D9.

**Marking a question sensitive with no rule is now allowed, and the emergency contact depends on it.** It used to be refused: a rule-less sensitive question has an empty audience, so an admin who believed they'd narrowed something to the kitchen had narrowed it to nobody, invisibly. The reasoning about the mechanism was right and the conclusion was wrong. Owner-only is a real answer — it is what an emergency contact wants, since nobody routinely needs it and it surfaces when someone activates Emergency access. Refusing the state meant the only way to ship an emergency contact was to invent an audience nobody had asked for, and inventing an audience for someone's medical or welfare details is a worse failure than the one the guard prevented. The starter set now seeds one emergency-accessible question — the emergency contact, and only that one — arriving owner-and-emergency-only. **Its default audience is deliberately nobody**: holding Admins is about who manages a Community's settings, not a reason to hold someone's emergency details, and a Community that wants a wellbeing Tier instead adds an access rule. The settings copy names all three states — public, an audience, the owner alone — so reaching owner-only is a choice on the screen rather than a slip past a guard.

**What the tests are for now is the thing that was missing.** `tests/sensitive-data.test.ts` used to be about four columns. It's now about who may read a member's answer, through the function the app actually calls, and it asserts the properties that decide a disclosure: the three routes resolve identically, a shadow holding doesn't count, the share box and the consent gate each cut in the right direction, owner-only resolves to nobody, and an archived or per-event answer is not in the roster read at all. The kitchen gained four tests for the same reason — it was the one live consumer, and the column it read is gone.

Verified by `tsc`, `eslint` and `next build` clean, and the full suite green (1625 tests, 83 files), run against a throwaway database since the suite truncates between files. The migration was checked against a real database — the four columns, the enum and both nullable targets are gone and `question_id` is `NOT NULL` — and the drizzle snapshot was diffed against that live schema rather than hand-written.

**Then it was driven in a browser, and two bugs that 1611 tests had passed turned up in the first ten minutes.** Both are recorded because the shape of them matters more than the fixes.

**The review form had never worked.** It submits `choice.<key>.<field>`; the action parsed with `formData.getAll("choice")`, which matches a field name *exactly* and so matched nothing at all. Every submission created zero questions and reported no error — because an empty choices object legitimately means "the admin kept nothing", so the failure was indistinguishable from a deliberate choice to keep nothing. No unit test could see it: they all call the seeder directly with an already-built object, and the only code connecting the two was a `"use server"` module that cannot be called from a test without a request context. The parse now lives in the lib as `parseStarterSetChoices`, takes a real `FormData`, and the field names come from one `starterChoiceField` used by the form, the parser and the tests — so the form and the parser cannot disagree again without a test failing. I reintroduced the original bug to confirm the new tests catch it: seven of them fail.

**The member data grid showed no columns on a new Community.** Which columns are on offer was derived from the answer map, and an answer map only contains questions somebody has answered — so with no answers yet, every *public* question vanished from the picker and the grid was empty with no way to discover why. It is now derived from the flags and the viewer's own access, which needs no answers and is what the question was always actually asking; the comment in that function had explicitly warned against the shortcut and then taken it. `tests/member-data.test.ts` covers it, including the day-one case and the distinction between "withheld" and "doesn't exist".

Also fixed from what the browser showed: a stale sentence in the Access rules copy still claiming a sensitive question is *refused* without a rule, which stopped being true in this same change; and un-ticking then re-ticking "restricted" in the review form silently dropped the emergency-access setting rather than restoring it.

The `scripts/rebuild.sh` change is the other half of this, and it is a fix to a broken loop rather than a feature: see the entry above.

## every member can read the settings — only Admins can still change them

`/settings` refused non-Admins outright: *"Only a current holder of an Admins-granting task can view or change these."* The write half was always the one that mattered, since every action in `actions.ts` calls `requireAdmins` itself regardless of what renders. The read half was gating a screen `docs/spec.md` says a community is supposed to be deciding collectively — assembly results are "always advisory, never auto-applied" (`:1257`), a foundational-settings change is expected to reach quorum against the whole roster "before Admins act on it" (`:430`), and decisions about what data is collected and who sees it belong to "the Community's collective decision-making … not to whoever currently holds the sysadmin task" (`:1267`). None of that is reachable while the settings themselves are unreadable: the body weighing a change has to be able to read what it is weighing. The gate moves from the read to the write.

**The loaders had to move too, and that was the actual work.** Ten of the fourteen queries this page runs were written as `authorized ? list…() : Promise.resolve([])` — free while a non-Admin never saw past the banner and the data was pure waste for them. Deleting the early return without touching them would have rendered a settings screen whose dropdowns and lists are silently empty: a Branches tab showing no branches, Profile & Privacy listing no questions, the Modules tab's pickers offering nothing. A green build, an inert-looking failure. Every one of them is now called unconditionally.

**One loader stays gated, and not as a privilege.** `listPendingBranches` calls `requireAdmins` itself, so calling it for a non-Admin throws rather than returning `[]` — it would have turned the page into a 500. It also happens to be the right exception on the merits: a pending branch is a request from a member awaiting confirmation, so the list is a queue of member requests rather than branch configuration. The tab's pending section renders empty for a member.

**The Members tab is hidden from non-Admins rather than shown read-only.** It is a roster-paste tool whose content is other people's names and email addresses, and "should we import this list" is an action rather than a setting to deliberate about. A deep link to `/settings?tab=members` falls back to General rather than rendering an empty body, and every existing `tab=members` link comes from the bulk-import flow itself, which only an Admin can reach.

**Read-only is a `<fieldset disabled>`, not a `readOnly` prop threaded through every control.** HTML disables every descendant form control of a disabled fieldset, so one attribute covers the inputs, the submit buttons, and the per-row `ActionMenu` triggers — which therefore never open. It also covers the `type="button"` handlers inside `FormBuilder`, `FieldShapeEditor` and `StarterQuestionPicker`, which are the reason this is not a prop: they are not form controls, so a prop is the only thing that could reach them, and threading one through a 1,972-line file across ten tabs is a much larger and more fragile change than the mechanism is worth. The fieldsets carry `disabled:opacity-60` because nothing in this codebase's Tailwind setup dims a disabled control on its own, and a normally-coloured form whose controls silently do nothing is worse than an honest refusal. `FoundersAssemblyPrompt` sits outside the fieldset deliberately — it is two links, and any member really can start an Assembly.

Verified by `tsc` and `eslint` clean, `next build` clean, and three new tests in `tests/settings.test.ts`. Those tests pin the loaders' contract rather than the page: they lock the community's Admins shut first (a fresh fixture has `adminsEverClaimed` false, and `requireAdmins` lets *anyone* through in that state as its bootstrap path, so without it "a non-admin" would still be an admin and the test would prove nothing), then assert every loader the page depends on resolves for a member holding nothing, that a non-admin gets the settings *themselves* rather than an empty list, and that the pending-branch queue still refuses. **The limit of that coverage is worth stating**: it cannot catch someone re-adding an `authorized ?` guard to the page's `Promise.all`, because that is a Server Component and this suite has no rendering tests — `tests/view-as.test.ts` records the same limitation for `session.ts`. The ungating is verified by reading the diff and still needs a browser.

**Not verified in a browser.** This deployment runs a prebuilt Docker image, so none of it is in it.

## settings changes leave a record — one row per changed field, and only the fields that really moved

`docs/open-permissions-plan.md` §9.1 recorded, as a deliberate deferral, that **"there is no audit mechanism for settings changes at all"** — no audit, history or revision table anywhere in the schema, with the schema comments on `profile-question.ts` and `call.ts` explicitly disclaiming one. What exists was incidental: `proposedBy` on a milestone as "a pure audit field", `objection.raisedBy` as "a real audit trail" that is deliberately never surfaced back out. Those are columns that fell out of a feature, not a log. The plan kept only the cheap half (`opened_by` on `open_permission_grant`, already built) and deferred the rest, on the reasoning that a faithful log has to cover every `requireAdmins` action behind the ten settings tabs rather than just the community row.

This is that work, starting with `updateCommunity` and the `settings_change` table it writes to. **It is not finished**: the other ~24 settings mutations across ten `src/lib/` files, and the surface the log is read on, are not in this commit.

**One row per changed field, and only for fields that actually changed.** Every settings tab's form submits *every* field that tab owns on every save — the four `updateXSettingsAction` functions each post their own full subset, because an omitted key rather than a false/empty value is what stops one tab blanking another tab's checkbox. So a log built from what was posted would bury a single real edit under every field merely re-sent, and an admin opening a tab and saving without touching anything is the common case, not the rare one. `recordSettingChanges` therefore diffs the submitted keys against the row as it currently stands and emits nothing when they match. Tested by resubmitting a full general-tab payload unchanged and asserting the log did not grow.

**A jsonb key-order trap, found by testing rather than reasoning.** Postgres jsonb does not preserve object key order — it normalises by length then bytewise — so a rule set read back off the row is not key-ordered the way the same rules arrive from `JSON.parse` of a textarea. Comparing the two with `JSON.stringify` reports a change on *every* save of a rule set nobody touched, which given the resubmits-everything behaviour above would have made that the most common entry in the log and would have quietly destroyed its value. The comparison canonicalises object keys first. Array order is deliberately left alone, because decision rules are "evaluated top-to-bottom, first match wins" and reordering them is a real edit — there is a test for each direction.

**A null that means two things, and a column that makes it unambiguous.** Both SQL NULL and a JSON `null` in a jsonb column read back as JS `null` through Drizzle — checked, not assumed. So "the logo was cleared" and "this value was deliberately not written" would be the same row, indistinguishable to any reader. `values_withheld` settles it: true with both values SQL NULL, false for a field genuinely set to null. The alternative, letting the UI keep its own list of which fields are sensitive, puts the policy in two places that can drift. Nothing is withheld yet — the one field that will be is `member_identity.login_email` in the bulk-import path, whose old/new pair would otherwise turn a member-readable log into a permanent roster of every member's login address.

**The entity is labelled with its name at the time of the change, not resolved on read.** Branches, tiers and profile questions get deleted and the log outlives them, so a name joined in at read time would read "—" forever. `entity_label` is the tombstone that §9.1 says the flag table alone cannot answer.

**The write and its log share one transaction.** A crash between the two would leave a change with no record, which is the one failure mode that makes an audit log worse than none — the gap is invisible, so the log looks complete. The whole `updateCommunity` write moved inside `db.transaction` to get that.

**Why the log is member-readable rather than admin-only** is a spec point worth recording, since it is the opposite of where the other settings logs sit: `docs/spec.md` treats a settings change as a collective decision, with assembly results "always advisory, never auto-applied" (`:1257`) and a foundational-settings change expected to reach quorum against the whole roster "before Admins act on it" (`:430`), while decisions about what data is collected and who sees it belong to "the Community's collective decision-making … not to whoever currently holds the sysadmin task" (`:1267`). A community cannot deliberate about a threshold it is not allowed to read. That is a gap in the current read gate rather than something this commit closes — `/settings` still refuses non-admins at `settings/page.tsx:690` — and closing it is separate work.

Two things carried in the schema rather than left to convention: no index on `(community_id, changed_at)`, because this schema carries no non-unique index anywhere and one community's settings history is small enough that a sequential scan is the cheaper plan on the 1-2GB VPS this targets; and `community_id` stored rather than derived from the member as `emergency_access_log` and `view_as_log` do, because this is a community-wide feed read by scoping on the community rather than a two-party row read through the actor's own id.

Verified by `tsc` and `eslint` clean, and 12 new tests in `tests/settings-change.test.ts` covering the per-field diff, the unchanged-resubmit case, unsubmitted fields, array and object round-tripping, both directions of the ordering question, a refused update leaving no row, per-community isolation, the withheld flag, and that a withheld row still records its actor and timestamp. **Not verified in a browser** — nothing renders this yet.

## the sensitive-question work, finished — the starter set is reviewed before it lands, and an audience can be set at all

Four separate gaps in the question work, three of them reachable only by a new community and all four of them the kind that look finished. The sensitive questions, their access rules, and the default set were all built and tested; what was missing was the last mile of each, and in one case the code was unreachable from the UI entirely.

**Setting an audience on a sensitive question was impossible from settings, so `sensitive` was too.** The access-rule form rendered its column select with no empty option and a default of `health_conditions`, so every question-keyed rule submitted a column *and* a question and was refused by `createSensitiveFieldAccessRule` for naming two targets. Since marking a question sensitive is itself refused until a rule names it, the two refusals formed a closed loop: the seeder could create a restricted question, and nothing else could. The column select has an `— none —` option now, and `tests/sensitive-data.test.ts` covers the question-only, both-targets, neither-target, archived, and cross-community cases — the first coverage that file had of `questionId` at all.

**The starter set now gets reviewed before it's added, and the review is where an audience is picked.** It was one button and twenty questions, and the only remedy afterwards was archiving them one at a time — for questions no member could have answered, since a community with no questions has no members. So the set is now a form: untick what you don't want, retitle anything you'd phrase differently, and choose each restricted answer's audience from the same three routes the access-rule form offers. That last part isn't a convenience, it's the point: `sensitive` needs a rule and a rule needs the question, a two-way dependency with no reachable start, so doing all three in one action in the only valid order is what makes a restricted question addable by hand at all. The submitted set is authoritative — an unmentioned row is not seeded — because a partial set that defaulted the rest to "add them anyway" would put back the exact bug the step exists to fix.

**Nothing is written unless the whole submission is valid.** The seeder isn't transactional, so a refusal raised partway through would leave the rows already created committed — and `hasProfileQuestions` is what closes the review step, so a partial write would strand a community on an arbitrary prefix of the set with no way to get the rest. Every checkable thing is now checked up front, and a refusal reports all the problems at once rather than one per resubmit.

**The set dropped its per-event group, and the Restricted group stopped lying.** Every seeded question is now once-ever: a `per_cycle` question is skipped on every read surface while the member has no declared cycle, and the seed runs at signup, before a community has run an event — so seven of the twenty questions were invisible and unanswerable in exactly the state they were created in, and permanently so for a community that never enables cycles. The doc's "For an event" group is not seeded; a community adds those itself, per event, once it has one. "Date of birth" is gone too — a precise identifier nothing in the set needed, collected with no decline offered, alongside the age band that already covered it. "Home city or town" and "Full legal name" were in a group whose blurb promised each row arrives with an audience attached, and had no audience at all, so they seeded **readable by the whole community**; and "Anything that would affect what you can take on" sat in a group promising the same while its own `why` called it "the escape hatch for disability, caring, faith". All four now carry a real default audience, and `validateDefaultQuestionTable` throws at seed time if a Restricted row ever lacks one again — a check that is itself tested against four deliberately broken tables, on the reasoning that a validator nothing has ever seen fail is not a validator.

**The Access rules section stopped describing only the four columns.** It said rules "unlock each field … on `/sensitive-data`" and "only takes effect once Sensitive data is checked under the Modules tab", which was true of columns and false of questions — `resolveReadableQuestions` is not module-gated; only the columns page is. It now says which is which, and states the rule-first-then-tick order, because the empty-state note was still telling admins to do it the other way round, pointing at the one sequence with no reachable start. The rule list renders through fallbacks rather than non-null assertions, so a hand-edited row reads as the broken row it is instead of the string "undefined".

The table and its types moved to `src/lib/profile-questions/defaults-table.ts`, which imports no database and is therefore safe for the client-side review form; `defaults.ts` re-exports them. That split is load-bearing rather than tidiness — importing the seeder into a client component pulls `@/db` and fails the build on `postgres`/`tls`/`fs`, which it did on the first attempt.

Verified by `tsc`, `eslint`, and `next build` clean, and the full suite green (1597 tests, 81 files) — including 28 in `tests/profile-question-defaults.test.ts` and 26 in `tests/sensitive-data.test.ts`. Tests ran against a throwaway database rather than the deployed one, since the suite truncates between files. **Not verified in a browser**: this deployment runs a prebuilt Docker image, so the new review form isn't in it.

The Events page was promoted out of the Community nav group to its own top-level sidebar row in `b50c1d0`. ## batch selection is something you start, not something you're looking at

The board's checkboxes were visible on every card, in every view, all the time. That was never the design — the original 54-line version had them inside a collapsed disclosure, opened on purpose. Widening selection to all four views and all three batch actions (Claim, Task Pack export, bulk Move) kept the gate and dropped the mode, so the cost of a feature that most visits never use is paid by every visit: a column of empty tick boxes down the left of a board whose actual job is being read.

**Selection is now opt-in.** A `selecting` flag on the shared client island decides whether a card has a checkbox, and it starts `false`. `TaskSelectionBar` renders a single quiet "Select tasks" button until it's started, then takes over the row it was already occupying with select-all, the count, clear, and the export/move panels. The overflow gained a matching "Select tasks…" row, because the batch actions it offers live there and the way into the mode should be next to them.

**Leaving discards the selection rather than hiding it.** "Done" clears the set along with the checkboxes. Keeping a selection alive under a hidden UI is how you end up with a menu confidently promising "3 tasks selected" that nobody can see or revise — the count would be real and unfalsifiable from the screen. The mode is also escapable when a filter change empties the selectable set mid-selection: select-all goes disabled and greyed rather than checked, and the bar stays put with its Done button instead of vanishing and stranding the user in a mode with no exit.

## closing the gaps in open permissions — what travels, and what a shared item says

The open-permissions work landed in two commits; this is the part that turned out not to be finished by them, and all of it is small.

**An open flag doesn't travel, and now that's a test rather than a comment.** Cycle clone and Task Pack import both carry *grants* between communities and events, and both go through one function — `copyPermissionGrants` — so a Community's open modules travel nowhere, deliberately: a capability someone decided for their own members shouldn't follow a cloned event into a different set of members. That was true when written, and true now, but it was true by *omission*, which is the kind of thing that quietly stops being true. It's pinned now, along with the converse — clearing an open flag leaves the task grant alone, because the two are independent facts, not two states of one.

**`backstop` can't be opened, and the refusal is enforced at the write.** Its authority is a named person to notify, so there is nothing for "everyone" to be. The settings tab renders no checkbox and says why; `setModuleOpen` refuses it too, so a forged POST gets the same answer the UI would have given rather than a capability the interface promises doesn't exist. Thirteen other modules are openable, and opening one twice is one row.

**A shared needs-action section was claiming something false.** It said "nobody in particular is on the hook for these", which holds when a module is open and unheld and is wrong the moment it's open *and* three people hold it. It now says the item is outstanding for the Community rather than assigned to *you*, and adds that whoever holds the task sees it as their own — true in both cases. The related question of whether a shared section should *name* those holders is settled as no: a member lookup per open module on every dashboard render, to serve the readers least likely to need it, in a section whose heading already says "open to everyone".

Also: a spec section for the whole mechanic under Transparency & access, since it's a principle a reader of the spec would otherwise not know existed, and the plan document marked through to done — including the one item where the plan's own advice turned out to be wrong, recorded as withdrawn rather than quietly deleted.

## permissions a Community can open to everyone, and a Recruitment pipeline that can finish

Every permission in the system was task-gated: a capability existed because whoever currently held a task carrying a `permission_grant` row could do it, and nobody else could. That is a good default — authority you can point at, that goes away when the person leaves. But it has one failure mode with no way out. A Community that wants everyone to be able to evaluate applications, or draw the Zone plan, or close the budget has no way to say so, and the alternative — inventing tasks and claiming them so a resolver returns true — is not a setting anyone would find.

`open_permission_grant` adds that setting: one row per `(community, module)`, meaning *this Community has decided this capability is open to all its members*. It is deliberately a separate table rather than a nullable `permission_grant.task_id`, because every resolver reaches authority by joining a grant's task id to a `taskAssignment` — a `NULL` there would match nobody and grant nothing while looking correctly configured, which is the worst direction for a security setting to fail in. Thirteen of the fourteen modules can be opened this way; `backstop` cannot, because its authority is a *named person to notify* and a backstop with no name has nothing to do. Its checkbox is absent and says why.

The second half is what opening Recruitment actually fixes. `recruitmentEvaluatorCount` defaults to two, `recruitment` is single-cardinality per scope, and `computeRecruitmentOutcome` refuses to evaluate below the threshold — so a Community with one holder could never satisfy any rule above the mandatory fallback, and every application parked at `decision_pending` forever, surfacing only as a "stuck waiting on you" dashboard line. The data model always wanted an evaluation *panel* (`evaluation.evaluatorId` is per-evaluator); the access model permitted exactly one person. Opening the module is the fix, and `tests/open-permissions.test.ts` now has two ordinary members file evaluations and reach a `proceed` outcome, which was unreachable before.

Opening a module also had to not break the things that read "is this set up?". Eleven sites were using *grant existence* as a stand-in for *module configured*, and each failed differently: an open `conflict_team` left members able to review conflicts but **unable to file one**; its nav item disappeared; the recusal picker went empty while the recusal action itself worked; the Spatial-planning page told everyone "nobody can draw or edit"; and open Recruitment silently stopped scheduling intro calls and accompaniment tasks, because both take their `branchId` from the granting task and a member has no branch to fall back on. That last one is reported rather than papered over — inventing a branch would file a real poll and a real task under an unrelated one — and the hub says so.

Two smaller things fell out of doing it honestly. The needs-action lists were per-actor by construction, with copy in the second person ("Budget needs *your* attention"), so opening a module put everyone's outstanding work in everyone's feed and multiplied the nav badge; they now split `personal` from `shared`, where the distinction is **consent, not headcount** — a task with `capacity: 3` is deliberate redundancy and its holders each keep a personal item. And the Access & permissions tab never showed who actually held a task, even though `capacity` is the real control on that and nothing in the permission layer read it; each row now shows the holders by name up to three and a linked count above that.

Still deliberately not done: opening a module does **not** unlock a sensitive field gated to that module's grant. That coupling is real and invisible, and whether it should compose is a separate question about profile questions and consent — being worked out on its own.

## a phase you can read at a glance, and a number that stops being a number

The phase list on `/participation` rendered each phase's entire authoring form inline — two bordered date fieldsets with a segmented control apiece, a "Save dates" button, and a module-picker row — and buried the phase itself underneath. With a handful of phases the section became a wall of controls, and the one thing you'd come to check (when *is* this phase?) was the thing you had to read past the form to find. The rules below are all consequences of taking the summary seriously enough to write.

- **Each phase is now two lines and an `Edit`.** The card states its resolved date range, then says where it sits relative to the event in words; the date and module controls only mount when you ask for them. That's the `<details>`-for-edit rule the design conventions already set on every other form in the app — the phase view was the last surface still violating it. A pinned module moves from an invisible dropdown value to a `Tag` in the card header, because it changes the nav for everyone arriving while that phase is current and was otherwise only discoverable by opening the form that held it. The date range carries a shared year once ("Sep 1 – Sep 14, 2027") so a scannable list gives you a date rather than a repeated year.

- **The stored recipe is read out loud, and there is now one copy of the prose.** `src/lib/dates/describe.ts` replaces two near-identical inline formatters — this page's, and `tasks/[id]`'s milestone footer — both of which printed the raw machinery: `-4 day(s) from the event's start`, `0% of the way through the event`. Three rules, each because the number is a poor description of the day it points at:
  - **A negative offset is "before", a positive one is "after."** The sign is carried by the word, so nobody has to read a minus sign as a direction, and "1 day" is no longer "1 day(s)".
  - **A proportion is never printed as 0% or 100%.** Those aren't "the start" and "the end" of anything — they're just the first and last day of the event, which now says so. This is not an exotic case: `inferRelativeDate` compares strictly, so a phase beginning on the event's *first* day is stored as a `between` at 0, and `normalizeBoundary` re-bases to one every time the parent span changes.
  - **Zero days from an edge is the edge itself**, so "0% through the event" and "0 days after the event starts" — two different stored recipes for the same instant — now read as the same sentence.

- **Rounding a percentage needed a clamp, and finding that out was the point of checking.** The first pass rounded the proportion to a whole percent and *then* tested for 0/100, which quietly turns "0.27% of the way in" into "the first day" — a false claim about a phase that starts the day after the event does, and reachable on any event longer than a few months. The edges are now recognized by the stored value being *exactly* 0 or *exactly* 10000, and the displayed percent is clamped into 1–99 so the rounding can't walk a real proportion back out onto an edge. The exact date is on the line above regardless.

- **"A date you set by hand" was being reported about phases with no date at all.** `EMPTY_BOUNDARY` is itself `dateType: "absolute"`, so an unset boundary and a deliberately hand-typed one are identical across the recipe fields — the resolved date is the only thing telling them apart. Caught by rendering real authoring flows end-to-end (type a date → `inferRelativeDate` → stored recipe → printed prose) rather than hand-written fixtures: a phase with one boundary and no other claimed "ends a date you set by hand". The shared helper therefore takes the resolved date as part of its input — a milestone row has no cached `date` column the way a Phase boundary does, so `tasks/[id]` threads its `resolvedDate` in under the shared shape's name — and an unset boundary now reads "The end isn't set yet."

  Two things deliberately left alone. The **storage** is unchanged: 0 and 10000 remain perfectly good stored values, and collapsing them at write time would break the recipe-preserving edit path (`boundaryForEditing`) and the canonical re-basing in `normalizeBoundary` for no gain — the rule is about what gets *said*, not what's kept. And the **inference** is unchanged, so a phase entirely before the event still reports both edges against the start ("Starts 4 days before the event starts, ends 1 day before the event starts"); the repetition is honest about where the offsets are anchored, and eliding it with a pronoun would have made each line depend on the one above in a list people scan.

  Verified by `tests/dates-describe.test.ts` (13 cases pinning each rule, including the two-recipes-one-instant equivalence and the clamp at both ends), the existing `dates-resolve`/`date-display` suites, `tsc`, `eslint`, and a clean `next build`. Not verified in a browser: this working tree carries uncommitted migrations `0063`–`0074` that the local Postgres has never been migrated to, so every DB-backed test and the running app both fail on `cycle_indicators_enabled` regardless of this change — pre-existing, and reproduced on a clean stash to confirm it.

## community-wide coordination, and a permissions tab you can scan

- **Coordination can now skip the branch, for a community too small to want a coordinator per branch.** Coordination was already two widths — a branch column (an event-independent task in branch B covers all of branch B) and an event row (a task in event C covers all of C) — but a small community had no third answer, because **a branch is the smallest unit a task can be placed in**: `task.branchId` is `NOT NULL`, so no arrangement of ordinary tasks can express "every branch". The only workarounds were a coordination task per branch (exactly the duplication being avoided) or letting one branch's column quietly stand in for the whole community.

  `community_coordination` is a new grant module (migration `0069`) whose only difference is that **the branch is never part of its scope**. The scope rule is otherwise the ordinary one, unchanged: placement is the scope. Placed in an event it's that event's coordinator and nothing more — strictly, per the existing rule that a scoped coordinator never reaches outside its scope — and only a grant with **no event** goes community-wide, in which case the branch on its task is simply not read. That makes it cycle_variant rather than a community-only role, so a community can run community-wide, per-branch and per-event coordinators side by side, and the settings tab's tier table says so honestly instead of warning about a placement that works. It **coexists** with the other two widths and is multi-cardinality. The trade is worth naming: in exchange for never being narrowed to a branch, it's also never narrowed to an event unless you put it in one.

  It's deliberately a *module key* rather than a `scope` column on `permission_grant`: that column is exactly the second scope read that retiring `permission_grant.cycleId` (decision D8) removed, and capability-per-key is the shape the table already uses. Both keys resolve as one family in `src/lib/coordination.ts`, where the resolver reads placement *first* and module second — so a cycle-placed grant is a cycle row whichever key granted it, and the community-wide case can only ever be set by a grant with no cycle. `listCoordinationScopeIds` reports that case as a `communityWide` flag instead of enumerating every branch id, so the board, escalation queue and view-scope gates stay O(1) rather than each re-deriving "all branches".

- **The board's "Coordinated by {name}" tag was on essentially every task, and now only appears where someone needs to act.** One branch-wide coordination grant made *all* of that branch's tasks read "Coordinated by {name}", because the tag reused the same predicate that gates the card's Escalate action. Those are different questions, and conflating them made the tag carry no information: column semantics cover a branch across all its events, so coverage is true for ~100% of its tasks. The tag is now gated on `needsNamedCoordinator` — the escalation queue, plus unclaimed criticals, which is the exact trigger of the "Backstop: {name}" marker sitting beside it. Everything else keeps the coverage fact, which is what actually decides which actions a coordinator is offered. A community-wide holder is named last, only where no branch or event holder is, so a community that hasn't set one simply sees no tag rather than a name on everything. A tag that names a person should be earned by a task that needs one.

- **The permissions tab is grouped by how far each gate reaches — "Community-wide" and "Per-event" — and the per-module text is gone.** Fourteen modules each led their hint with the same "a task grants what it sits in" clause: one rule, stated fourteen times, in ~600 words of near-identical paragraph, with the part that actually differs (what holding the role *lets you do*) buried at the end of each. The shared rule is now stated once per section header, and the hints are reduced to the capability. The split is **derived from the tier table** rather than hand-listed, so a new module can't land in no section or in two — `tests/permissions.test.ts` asserts the two sections partition the module keys. Only the community-shaped tier earns its own section; the cycle-shaped and cycle-variant tiers share the per-event one, because the rule a reader needs is the same for both and the only real difference is the label each row already prints ("Evergreen" vs "Community-wide"). The task-detail checkbox list isn't sectioned, so it instead shows the derived scope under each checkbox — the same information, where the reader is actually deciding what to grant.

## open Assemblies on the Community hub, and a quieter sidebar

- **An open Assembly now shows on `/community`, and the Community nav item carries a badge.** But the badge deliberately counts only Assemblies you're actually still owed an answer on — a voting-phase one you haven't finished — never every open one. `spec.md` is emphatic that an Assembly gets "no built-in urgent notification, on purpose", and a badge lit for anything open would work straight against that: it would nag about a notice-phase agenda you can't vote on yet, and about an open agenda where nobody is waiting on anyone. So `isAwaitingMyAnswer` counts voting-phase only, and that one predicate is the single definition behind three surfaces — the hub's "N are waiting on your answer", the sidebar badge, and the /assemblies list's "Waiting on you" — so they cannot drift apart. The *listing* is passive and breaks no rule: nothing is sent, nothing interrupts, which is exactly how the "Current and upcoming events" cards on the same page are already treated, and why it lives on the community-wide page rather than the personal Dashboard. One shared `assemblyParticipationById` query serves the badge and the hub, and the hub reads `listOpenAssemblies` — so the badge is literally a count of what that page shows.
- **Link-header nav groups (Tasks, Community, Communication) now start collapsed; Modules starts open.** A `headerIsLink` group is a *link* first and a container second, so the row you click is its own destination and the sub-list is only alternate routes into it — expanding all of them by default turned the sidebar into a wall of indented text duplicating hubs each header already links to. Modules is the opposite shape: its header isn't a destination, so its items *are* the group, and collapsing it would hide the only content it has. The default is data in `nav-config.ts` as a new `defaultOpen`, and the sidebar's persisted state had to change shape to permit that: it stored a *set of closed groups* against a fixed "everything open" default, which can only ever add to the closed list — so a group now defaulting to closed could never be opened again, since clicking its chevron would have meant "close it" regardless of intent. It stores the chosen state per group instead, so opening works in both directions. The old `closedGroups` key is read once and converted rather than discarded, so nobody's sidebar springs back open because the format changed, and a test pins that `defaultOpen: false` can only appear on a group that both has a header link and has items — a header-less group collapsed by default has nowhere to go.

## Assemblies you can actually read, and one to decide your settings with

Assemblies had all the right data and none of it reached the screen. Reading an agenda was the worst of it: `options` was only ever rendered as the *inputs* of a vote form, and only once voting was open — so during agenda-building you couldn't check the options you'd just typed were right, and during **notice** (the phase whose entire purpose is "the agenda is locked and visible") a pick-one question was visually identical to a written-answer one. Nobody could read what they were about to vote on. Everything below follows from taking that seriously.

**Three real defects, not just awkward UI**

- **Options are now always visible, and the question says what kind it is.** Every agenda item carries an unconditional one-line shape — "Pick one · 4 answers to choose from", "Written answer · Everyone answers in their own words" — and lists its answers whenever the vote form isn't already showing them (i.e. every phase except voting, where the radios *are* the list). During voting the control moved out of the item cards and up into a single ballot, so the per-item cards below are unambiguously the review of what you just saved.
- **Options are normalised, once, in one place.** They arrive from three callers (the form, the JSON API, template seeding) and are trimmed, stripped of blanks, and checked for duplicates in `normalizeOptions`/`findDuplicateOption` — applied both by the zod schema at the action boundary *and* inside `addAgendaItem` itself, because that function already refuses to store a choice item with no options and shouldn't have been weaker for a direct lib call. Two duplicates used to produce two radios sharing one name **and** one value: the browser treats those as a single control, so checking one visually checked both, while the tally counted them as two answers. That silently misreported the result, which is worse than looking wrong.
- **A written-answer item can no longer carry options at all.** The old form kept its options field on screen for every response type, so typing options and then switching to Free text committed an item whose options could never be displayed, voted on, or edited again. The response type is now the single thing that decides whether an item has options. Options also arrive as repeated `option` fields rather than one comma-split string, so an option *containing* a comma is no longer impossible to express.

**Durations you can read**

- The three bare `agendaMinutes`/`noticeMinutes`/`votingMinutes` number boxes are one control: a number plus a unit (minutes/hours/days/weeks, so nobody types 2880 for a week), a **Urgent / Normal / Deliberate** preset that fills all three at once and stays individually editable, and a live preview of what the three numbers actually produce — "Agenda closes in 2 days · Voting opens in 4 days · Everything closes in 10 days". That preview is the thing the old form never had: it made you commit to three integers to find out what they meant. The defaults are unchanged (1/1/3 days), so nothing that worked before behaves differently. A zero-minute agenda now says outright that it would lock before anyone could add anything.
- A hand-rolled `relativeTime`/`humanizeDuration` pair (in `src/components/assemblies/time.ts`) replaces two divergent copies, and is deliberately not `Intl` — these strings render on both server and client, and a locale- or timezone-dependent formatter disagrees between the two.

**One ballot, not five round-trips**

- `submitAssemblyResponses` takes the whole agenda at once. A blank answer is *skipped* rather than rejected — leaving a field empty is how you say "no view on this one", and treating it as an error made a partial ballot unsubmittable. Failures are per-question and the rest still save, so a typo in one free-text box doesn't cost you four good answers. This also retired the old form's `multi.length > 0 ? multi : single` inference about which kind of question it was holding, which is exactly the kind of guess that breaks as soon as an unselected pick-any question is in the batch. The server distinguishes "not yours" from "voting isn't open" for a cross-community question id, rather than reporting the latter and hinting that someone else's Assembly exists.
- Unchecking every box in a pick-any question now says "Pick at least one of this question's answers" instead of the old "must be a non-empty subset of this question's options" — a different mistake deserves a different message.

**An open agenda needs an exit**

- `removeAgendaItem` lets you withdraw an item **you** added, while the agenda is open. Adding to an agenda is deliberately open to anyone with no approval step; without a matching exit the agenda was append-only for its whole window, so a typo or a badly-worded motion stayed visible to the entire community until the phase rolled over with no way for whoever made it to fix it. Your own items only — deliberately **not** modelled as a moderation power, since nothing in the spec grants one and an Assembly with no gatekeeping shouldn't quietly grow a delete button. Every item now also says who added it, which is the first question a member asks reading someone else's motion.

**Reading results, and knowing whether your vote is in**

- Choice results are proportional bars with counts and percentages instead of `"pancakes: 3"`; your own answer is marked in the tally, in the vote control, and on the free-text responses, which now carry member attribution (`You: …` on your own). Every item shows its response count in every phase, plus a "you haven't answered this one yet" note and how many members haven't weighed in at all. The phase line leads with the answer to the only question anyone opens this page with — "Voting closes in 2 days" — keeping the absolute timestamp underneath.
- The list page gains what it never had: the next closing boundary per Assembly, item/response counts, your participation ("you've answered 1 of 2"), and a **Waiting on you** section for live votes you haven't completed, listed *out of* Open rather than in addition to it.

**A rejected submit no longer eats your work**

- The agenda form used to submit to an action that redirected back with `?error=`, re-rendering an empty form — so a rejected submit destroyed the question text and the whole half-written option list, which is precisely when you most want to keep it. `addAgendaItemAction` now returns its failure, and `AgendaItemForm` holds the draft across the round-trip and shows the message inline. Verified live by closing an Assembly's agenda window server-side and submitting: the error appears with the text, the response type, and both options intact.

**The Founding settings template — deciding your settings together, without doing it by hand**

- `spec.md`'s "Two tiers of setting, not one" already commits a community to settling its *foundational* settings collectively: those "carry an additional expectation: an Assembly about the change should reach quorum … before Admins act on it." What never existed was a way to actually run one, and nothing in `src/` was a template, preset, seed, wizard, or checklist. There is now one starter: 18 agenda items across 6 areas — getting people in, who holds authority, critical tasks & endorsement, which modules are on, how we work together, data & privacy — covering exactly the settings a Community has to choose before it can really run (recruitment doors and evaluator count, the four invitation lanes, the 13 permission grants, task openness and endorsement thresholds, the 7 modules, staleness and call defaults, the 4 sensitive fields).
- **It stays advisory, exactly like any other Assembly, and that's what makes the write-up guide worth having.** Each item carries a `settingsMapping` naming the screen and field its answer becomes, and the closed-phase read view prints the tally next to that pointer — so "advisory" is still actionable, because whoever holds Admins is told precisely which field to change rather than having to work out which question was about which setting. Nothing reads that column to write a setting back. Seeded items are ordinary `assemblyQuestion` rows via the existing `addAgendaItem` path, so agenda lock, voting and tallies behave identically to a hand-written agenda and every item is removable.
- **Every option set is derived from the real enums and label maps** — `MODULE_DEFINITIONS`, `PERMISSION_MODULE_KEYS`/`PERMISSION_MODULE_LABELS`, `OPENNESS_LABELS`, `SENSITIVE_FIELD_KEYS`, the joining-lane names — so adding a module or renaming a permission updates the template automatically instead of letting it go quietly stale, which is the whole failure mode of asking a community to hand-write these. There are tests pinning that derivation.
- Reachable from `/assemblies/new` ("Use the Founding settings agenda") and prompted on `/settings` — the one place someone goes *because* they're about to configure something. The prompt disappears the moment a Founding-settings Assembly exists (read off `assembly.templateKey`, so the truth stays with the Assembly rather than being mirrored, and deleting it correctly brings the offer back), and otherwise on its own after a fortnight. It has no dismiss button: the two weeks *are* the answer to "I don't want this", and a "no thanks" would just mean it reappeared for the next person who didn't click it. The clock anchor is `community.foundersAssemblyPromptedAt` — deliberately "when we first showed it", not "how old the install is", since this is single-tenant self-hosted software and a deployment that has been running for a year and only just started using the tool properly must still be offered it.
- Three nullable columns, one migration (`0066`), no backfill: `assembly.template_key`, `assembly_question.settings_mapping`, `community.founders_assembly_prompted_at`. `template_key` is free text rather than a pgEnum on purpose — adding a template shouldn't cost a migration.

## board selection, navigation, and import follow-up

- The board's Unclaimed/Kanban/phase/coverage views now share card-level selection with Claim, filtered Task Pack export, and bulk placement Move actions. A tag filter can define a selectable cluster; uncapped tasks correctly count as having open slots.
- Branch coverage keeps its health status public while limiting detailed task lists, counts, and triage ordering to the relevant branch/cycle coordination scope.
- The Library header-only nav destination renders, `/community` is the single Community hub, and `/members` is directory-only.

## question field shapes

- **Six answer types, with the variations as flags rather than as more types.** `text` (one line or long), `single_choice`, `multi_choice`, `boolean` (yes/no), `date` and `number`, replacing `free_text`/`single_choice`/`multi_choice`/`date`. The point of keeping the list at six is that the orthogonal parts stay orthogonal: short-vs-long and a format check (none/email/phone/url) are two independent settings on a text field, because "an email is still a text field, still short, still deferrable" — a flat list would need `short_text`, `long_text`, `email`, `long_email`, `phone` and a branch in every renderer and validator for each. `free_text` is gone because it described neither its length nor anything else; existing rows migrate to `text` with the long-answer flag on, so no question changes how it renders.
- **A choice field can offer an "other" escape hatch.** This is the one that makes a closed list usable: a vocabulary you can count, with a way for people to answer in their own words, which is otherwise a choice between a list that excludes people and free text you can't aggregate. The words are stored as an ordinary string in the option's own slot, so an aggregate needs no special case to count the options. Deliberately **not** a ranking: pronouns aren't a priority order, and requiring a primary asks people to invent a fact about themselves. It does imply a list, so a list is also expected — a free-text-only pronoun field can't feed a diversity indicator, and shouldn't be asked to.
- **A Form submission is now actually validated.** It previously checked required-and-blank and nothing else, which was survivable when a field could only be text or a choice and was not survivable the moment a form could hold a number with bounds, a yes/no, or an email — a form would have accepted "banana" for a number and stored it. Every submitted value now goes through the same `validateFieldValue` a ProfileQuestion answer does, and the whole submission is rejected if any value fails.
- **One definition of a field's shape, one renderer.** New `src/lib/field-shape.ts` owns the type union, the flags, the validation and the submitted-value reading; `ProfileQuestion` and `Form.fields` both project into it, which is what spec's "Forms made of Questions? Partly" line always meant but which was previously two near-identical zod schemas, two value-extraction copies in `/apply` and `/feedback`, and **four** separate per-type rendering switches (the two answer forms, `FieldPreview`, and the Dashboard's prefilled-answer review). All of those now go through one component and one function, so a new type is an edit in one place. Forms also gain the three types they never had — `date`, `boolean` and `number` — despite already sharing the field builder with ProfileQuestion.
- **Booleans and numbers are stored as booleans and numbers**, not as the strings `"false"` and `"12"`, so an aggregate can count and sum them without re-parsing. A blank check no longer treats `false` or `0` as unanswered, which is the kind of quiet bug that drops people out of counts.
- Fixed two real bugs found while verifying: a choice field's escape-hatch input shared a name with its radio/checkbox, so leftover text in that box could overwrite the option actually chosen; and `/profile`'s answer action never routed through its own error handler, so a rejected value surfaced as a 500 instead of a message.
- **The other two question systems now read the same six types.** Task questions (Input rounds) and Assembly agenda items each carried their own three-value `free_text` enum, their own zod schema, their own validator and their own inline renderer — the third and fourth copies of a definition that already existed twice, each free to drift. So "when could you do this?" and "how many hours could you give?" were inexpressible on a task, and a body voting on how to spend a budget had no way to ask what the budget was. Both enums are rebuilt onto the shared six in migration `0068`, their validators are now `validateFieldValue`, and their renderers are `FieldPreview` — five inline type switches down to one. `free_text` rows migrate to `text` with the long-answer flag on in both tables, because every one of them rendered a textarea and an input round or agenda answer is usually a sentence; the column default is `true` there and `false` on `profile_question` for the same reason, which is worth stating because a generated migration gets it wrong.
- **What they deliberately do *not* get is the status model.** No `required`, no deferral, no "prefer not to say", no due date, no per-event scoping. An input round is an opinion or an offer and an agenda item is a position someone takes; in both, abstaining by not answering is already a complete response, so there is nothing to defer and nothing to decline. The shape is shared; the semantics are genuinely different, and keeping them separate is the point rather than a gap.
- **The tally can no longer quietly disagree with the response count.** A choice item with the escape hatch on can collect a free-text answer, which no option can claim — and the tally iterated `options`, so those answers were dropped while `total` still counted them, making the percentages next to it quietly wrong. Both the Assembly tally and the task-question tally now count them as their own visible "wrote their own answer" row, so the bars still sum to the figure printed above them. The same reasoning as showing the "other" bucket in an indicator rather than folding it away.
- **A blank submission is reported rather than crashed on.** Sharing the validator initially let a blank through as `null`, which `assembly_response.value` (NOT NULL) rejected with a raw database error — a regression against the old code's clean `ConflictError`. Rejecting is right for another reason too: the alternatives are deleting the response, which makes "Update answer" a silent no-op when someone clears a box to change their mind. The shared validator takes a `blankMessage` because its default, "This answer is required", is *false* for both new callers — nothing is required, and a member who pressed the button on an empty box needs to be told that rather than scolded, so each supplies its own wording.
- **A stored answer is shown as itself.** `String(r.value)` was correct while every non-choice answer was prose, and prints "false" and "2027-03-01" at a member once a yes/no and a date are real values. `formatFieldValue` is the read side of what `fieldValueFromFormData` writes: "Yes"/"No", a figure as a figure, and a canonical date formatted — but only for a `date` field, and only when the value really is one, so a free-text answer that happens to start with a date is left alone.
- **A `multi_choice` answer is strictly a set.** The shared validator initially coerced a lone value into a one-element array; accepting that would store a string where the shape promises a list and force every reader to handle both. No transport is inconvenienced, since checkboxes under one name always submit an array.
- **Describing a shape in words is one definition too.** `RESPONSE_TYPE_HINTS` and `RESPONSE_TYPE_NOUNS` join the label map, because the copy was being hand-written per surface and the failure mode is concrete: `QuestionShape` treated "not a choice" as "is prose", so the moment an agenda item could be a date, a figure or a yes/no it printed "Written answer — Everyone answers in their own words" under all three. A lookup can't drift like that, and a test pins that no type is missing a label, a hint or a noun. `agenda.ts`'s own `isChoiceType` and `AssemblyResponseType` are re-exports of the shared ones rather than lookalikes.
- **The Assembly ballot had to learn the new types too**, and this is the part that made the change more than a schema change. It's a controlled client component, so it can't use `FieldPreview`; but the agenda composer can now create a date, a figure or a yes/no, and leaving the ballot unable to render them would have let a community author questions its own voting form couldn't answer. It renders all six itself and serialises `false` and `0` as answers rather than absences. Its "N of M answered" count and its payload are now derived from one function instead of two parallel derivations, which is the case where a field the count called answered got dropped from the submission.

## a member's standing opt-out from published indicators

- **A member can now drop out of every published community indicator at once**, from a new "Community indicators" section on `/profile` (migration `0071`, one boolean on `member`). This is the consent mechanism that was missing: `allowPreferNotToSay` is a *response to one question* — still required on every published indicator — but neither that nor ticking the box on a question is the same as a member deciding once, "don't put me in any aggregate". A question invented in year two has no decline for them to have used.
- **It is a reporting exclusion, not an answering gate.** You can still answer every question while opted out, and answering still costs nothing in outstanding-question terms. Suppressing answering too would be a way to drop someone out of a *required* question by hiding the control, which is the opposite of what the control says on the tin. A test pins that the answer is still written.
- **An excluded person is out of the denominator, not just the numerator.** Both halves matter and they fail differently: leaving them in the population while dropping their answer would make the coverage line report a permanent "1 haven't" for someone who is still answering everything. `populationIds` is the single definition of who an indicator describes, and both the count and the answer filter read it, so they cannot drift.
- **Self-service, with no Admin path over it.** An Admin ability to exclude a member would be the same power as one to include them without asking, wearing a privacy label. `updateIndicatorExclusion` mirrors `updateContributionVisibility`'s existing shape for the same reason.
- **Deliberately the *opposite* default to `contributionVisible`, and the difference is the justification.** A contribution record is generated passively from task history — the member never did anything to create it, so sharing it has to be asked for. A profile question was asked, the member answered it, and answering already implied the community would see the answer; being counted in an aggregate of it is the expected consequence, not a new disclosure. Opt-*in* here would compound on the decline each published question already offers, and coverage would collapse to whoever knew to come and tick a box.
- **The control is its own section, not part of "Your answers"**, which only renders once there's something to show. The whole point of a standing opt-out is that it can be set *before* answering anything — a member who wants to be in the questions but out of the aggregates has to be able to say so first, and a control that appears only after you've answered is a control that informed nobody.
- **Known sharp edge, not hidden:** anyone who answered a question *before* its community published it was counted from the moment it was published, with no consent step at answer time. Opting out is immediate for them, but they had to find this first. The real fix is the one still open — publishing is currently an Admin's decision rather than the Community's, which `docs/spec.md`'s two-tiers rule says foundational settings should not be. **That remains the bigger gap.**
- Also corrected a wrong comment: the consent floor claimed `listCommunityIndicators` was "the JSON API's path in". There is no such route — both call sites are pages — so the read-side re-check is now documented as what it is, a defence against a row that predates a rule.

## sensitive profile questions, emergency access, and a settled consent model

The three-category question taxonomy (public / logistics / gated) is replaced by independent attributes, and the per-publication consent machinery built earlier in this same branch is **removed**. Migration `0076` adds `profile_question.sensitive` and `profile_question.emergency_access`; `0077` drops `member.excluded_from_indicators`, `profile_answer.indicator_consent` and the `indicator_consent` enum.

- **A profile question carries attributes, not a category.** `sensitive` and `emergencyAccess` join `publishedAsIndicator` and `scope`. There is no category column, because the three-category version failed on its own terms: "gated" turned out to be *access*, not a kind of data — t-shirt size isn't sensitive and still mustn't be readable by everyone — and folding it in as a category made "medication on site" inexpressible, being both sensitive and per-event. Full design and the proposed default set: `docs/default-profile-questions.md`.

- **Emergency access and publishing are refused as a contradiction**, on create and on update, in both directions. A published indicator is already readable by the whole community, so an override has nothing to reach — and the flag would be asserting the opposite of the truth about why anyone would need the answer. "If there's a fire, look up the community's t-shirt sizes" isn't a rule, it's a mistake, and a mistake in a flag that *overrides* a privacy default is worth catching at the settings boundary. Checked against the effective flag pair rather than the submitted one, since the form submits both on every save — so unpublishing and enabling emergency in one save works, as it must.

- **Consent is granted once, at the section, and never per question.** `member.excludedFromIndicators` becomes `consentsToCommunityIndicators`, defaulting to **true** — the deliberate opposite of `contributionVisible`, and for the same asymmetry: a contribution record is generated passively from task history so sharing it must be asked for, while an indicator aggregates answers the member gave knowing the section may appear. Answering *is* consenting, here and for emergency access alike.

  This retires work built earlier in the same branch: the `indicatorConsent` enum, the `pendingConsent` count, the "asked whether to be counted" coverage line, the `/questions` consent-request section, the Dashboard's consent element, and its share of the nav badge. They solved a per-publication nagging problem that section consent makes impossible, and they were triggered by an *admin's* action — a member could be re-asked about a question they'd already answered because somebody in settings ticked a box. The only thing that re-opens consent is widening a **sensitive** question's audience, and only for the member whose answer it is.

  A test asserts the shape of the absence: an exhaustive list of `profile_answer`'s columns, so re-adding a per-answer consent field is a test failure rather than a quiet reintroduction.

- **Consent is to a rule, not a list of people.** "Whoever holds the task" is consented to as a *relationship*, so a new claimer is inside what was agreed and needs no new conversation — the same shape as "anyone holding Kitchen" when Kitchen is open. Only edits to the rule re-open it: adding a task link, changing an access rule, turning on emergency access.

- **Sensitivity is made cheap-to-abuse deliberately not**, and that lands in this increment as the settings copy rather than as code: a non-sensitive, unrestricted question is **readable by the whole community**, so restricting one at all requires marking it sensitive *and* configuring rules. Under-labelling a health question therefore doesn't save an Admin any work, it publishes the data to everyone, visibly. The shortcut and the danger can't point the same way, so nothing has to be trusted to tick the right box — and it retires the per-module opt-in list that a hardcoded `allergies → kitchen` pairing would have needed. (The read-side enforcement lands with the access rules, next.)

**Still to come on this design:** access rules retargeted from a field enum to a question id, the per-answer share-with-audience checkbox (sensitive only, default on), required `emergencyAccessLog.explanation` for question reads, task-derived questions, the community-chosen prominent profile set, and setup-time seeding of the default question set.

## sensitive profile questions actually restrict something

`sensitive` and `emergency_access` were columns in the previous entry and nothing more. This is the read side that makes the first one mean something, plus the third way a question can contradict publication. Migration `0078` gives an access rule and a consent purpose a question to name, and adds the per-answer share flag.

- **An access rule can name a question, not just one of the four fixed member columns.** `sensitive_field_access_rule.field_key` becomes nullable beside a new `question_id`; exactly one of the two is set per row, enforced in `src/lib/sensitive-data.ts` by the same app-layer rule the table already used for its three unlock routes. The four member columns are `docs/spec.md`'s fixed set and stay exactly as they were — questions are additive beside them, not a replacement, and `consent_purpose` gains the matching `gates_question_id`. **`consent_record` is untouched**: consent stays keyed by legal purpose, which is the shape it already had, so this widens only *what a purpose can gate*. A purpose is a purpose whatever it gates, and the notice a member agreed to is the same text either way.

- **`sensitive` performs no restriction of its own — the rules do — so marking one with no rule is refused.** This is the load-bearing guard, and without it the flag is worse than nothing: `resolveReadableQuestions` fails closed, so a sensitive question with no rules has an *empty* audience, and an Admin who ticked the box believing they'd narrowed it to the kitchen team has instead narrowed it to nobody, invisibly. The settings toggle is disabled until a rule exists rather than hidden, because a greyed-out box that says why is the version someone can act on.

- **The read side fails closed, and is one function.** `resolveReadableQuestions` is the only definition of profile-question readability, applied inside `listOnceEverAnswers` rather than at each render site — a permission every consumer must remember to apply is one that eventually isn't, and the surface that forgets is the one that leaks. The ladder is three levels: not sensitive → everyone may read; sensitive → the union of holders of any linked rule; own answer → always readable at any level. Being wrong toward "nobody" costs a hidden answer; being wrong toward "everyone" costs someone's medication.

- **The rule is the half that goes first, which took a correction.** Requiring a rule to already find its question sensitive, *and* refusing to mark a question sensitive until a rule exists, is a deadlock with no legal starting move — the state is unreachable. So a rule against a not-yet-sensitive question is allowed and is a **staged** rule: it restricts nothing today, and starts restricting the moment the flag lands. Same for a consent purpose. The settings copy names the sequence.

- **The audience is a relationship, not a list of people.** A task rule is consented to as a *rule*, so Carol claiming a task Bob used to hold puts Carol inside what was agreed with no decision required from anyone — and Bob, who never held it, is not inside. Treating a claim as a consent event would either spam members or produce a notification they learn to ignore. Nothing is cached: deleting a rule stops the read on the next request, because the resolution is a function of current state rather than a stored entitlement.

- **`profile_answer.share_with_audience` is the member's own lever, on sensitive questions only, defaulting on.** Un-ticking reduces the answer to emergency-only and leaves it on their own profile — distinct from declining, which removes it from the profile too. A plain question is readable by the whole community, so there's no audience to decline joining and no box is offered; the writer forces the column back to `true` there, so it can never store a claim about the world that isn't true. Default on because the exposure is already bounded by the rules the community configured, so sharing is the expected consequence of answering and the safe choice shouldn't be the one people have to remember.

- **`sensitive` is now refused alongside `publishedAsIndicator`**, joining `emergency_access`. All three contradictions are one function: each is a claim that is *false* of a published question rather than a rule that could be satisfied differently. Sensitive says "restricted to an audience"; publishing says "in front of everyone"; emergency says "you might need this and not have it". A flag that lies is worse than a missing one, because the next person to read it trusts it.

**Still to come on this design:** emergency *reads* are not wired to the log yet (`emergency_access` is stored and guarded, but activating emergency mode doesn't yet surface question answers, and `emergencyAccessLog.explanation` being nullable still needs making required for question reads); task-derived questions inheriting their task's scope; the community-chosen prominent profile set; and setup-time seeding of the default question set.

## community indicators — publishing an answer as a fact about everyone

- **A community can now choose which of its standing questions are aggregated on `/community`.** A new `publishedAsIndicator` flag on `ProfileQuestion` plus an `indicator_visibility` enum (`public` / `coordination`), migration `0070`. This is the payoff of having asked something like pronouns in a shape that keeps its options countable: an answer that stays private teaches the community nothing, and an answer published without anyone choosing to is a disclosure no member agreed to. The section renders as "About this community", and reads "Chosen by this community from its own standing questions. Everyone here chose to answer their own; nobody is named."
- **Nobody chooses the display form — it's derived from the answer type**, because the alternatives are worse in a specific way each. Three families cover every publishable type: **split** (`single_choice`, `boolean` — everyone contributes exactly one thing, so the parts are shares of a whole), **distribution** (`multi_choice` — everyone may contribute several, so each count is "how many people chose this" and the counts deliberately *don't* sum to the answerer count), and **summary** (`number`, `date` — a magnitude or a point in time, which has nothing to split, and bucketing one would invent a histogram nobody asked for). A hand-picked chart option would let someone put a pick-any question in a pie, and a pie of "who picked what" implies slices of one whole when five people choosing three options each is fifteen slices over five people. `text` has no family and **cannot be published at all** — not "shows badly", but because the only honest total of a text field is the members' own words.
- **Indicators are public, full stop — never coordinator-gated.** An earlier draft had an `indicator_visibility` enum with a `coordination` option, and it was wrong twice over: most members still saw the coverage line, which is itself a set of facts about a small nameable group, and saw none of the content. An indicator's entire purpose is to tell the community something about itself, so the protections that belong on this surface are **consent** (a decline is required on every published question, a member can opt out of all indicators at once, and a pre-publication answer is asked about before it's counted) and **the community's own choice of what to publish** — not a permission tier. The column and enum are dropped in `0073` rather than left unused so they can't be read as still-supported. A test now asserts that granting coordination changes nothing, in either direction, as a guard against reintroducing a gate.
- **Every number carries its denominator, and a refusal is never silence.** The coverage line reads "3 of 4 answered · 1 preferred not to say · 1 haven't" — declined and merely-unanswered are different states with different meanings and are never merged, and the denominator is *every* member rather than the active ones, so the figure can't quietly flatter itself. The escape hatch's answers are a visible "Something else" row: folding them into a neighbouring option would undo the reason the hatch exists, dropping them would make the parts fail to sum, and only the **count** is ever published — what someone typed is theirs, and no "publish this indicator" toggle can consent to it on their behalf.
- **A number is summarised with a median as well as a mean**, because 3/3/60 has a mean of 22 that describes nobody in it. Both are labelled; the mean isn't dropped, it's just not presented as *the* number. Dates are a range (earliest/latest), not a histogram.
- **An edit can't silently unpublish an indicator.** Changing a published question's answer type to something unaggregable is **refused with a message naming the fix**, rather than quietly clearing the flag the way a stale `min`/`max` is cleared. Clearing would mean an admin editing an unrelated dropdown makes a community-chosen disclosure vanish from `/community` with nothing said. A label edit on a published question still works — a guard written as "reject any update to a published question" would have blocked that, and there's a test pinning it.
- **A checkbox that can't be ticked says why.** The settings toggle is disabled on a written answer or a per-event question, with the reason *and* its remedy attached, because a greyed-out option with no explanation reads as a broken app. The reason and the remedy are separate values, not one string: the two callers need different fixes, and concatenating them produced a message that told an admin to "change the answer type to pick one first" while they were trying to *stop* publishing. Archived questions stop publishing — a number nobody maintains, ageing silently, is worse for trust than none.
- **The indicators follow the Dashboard's existing "This event / All open events" choice, rather than getting a second control.** An event-scoped indicator is "of the eight people coming, five have told us their pronouns" — and only the *population* narrows, since the answers are once-ever standing facts. Deliberately one control for one underlying question ("who are we talking about?"): two controls is two things that can disagree, and a reader would have no way to tell which population a proportion described. The population is read from the same `Participation` `coming` rows as the "N members coming this event" count directly above it, so an indicator and the count under it can't describe different groups. `memberCountView` was hoisted above the query so both resolve the default the same way. `/community` stays community-wide — it isn't under `/[cycleScope]`, so it has no event view to narrow to.
- **A proportion that doesn't name its population is meaningless**, so an event-scoped section says so: "Each one describes the 3 members coming to Spring Weekend." Without that line the same indicator would silently mean two different things on two pages, which is the one failure a percentage can't survive. An event with nobody declared coming reports **0 of 0**, never the community's figures — a heading claiming these are the event's numbers while every figure is about someone who isn't coming is the worst answer available.
- **A published indicator now *requires* the question to offer "prefer not to say"** — the whole point of publishing is that people get counted in a number, and without a decline their only way out is to not answer. That's not a real opt-out, because silence is visible: it shows up as "2 haven't" in the coverage line, so the refusal leaks through the gap it was meant to protect, and a withheld answer is exactly as published as a given one. `declined` is stored with a null value and reported as its own figure, so a refusal is a refusal.
- **It takes a decline rather than a per-question "who may read this" rule**, which was the other thing on the table (and modelled, for allergies and an emergency contact, by `sensitive_field_access_rule`). That table exists because somebody has to read a *named individual's* value. An indicator has no such reader — the aggregate is the only thing that ever exists, and no code path anywhere shows one member's answer to anyone. So "who may see this?" is already answered, and the one that isn't is "may a member be counted without agreeing to be?", which is precisely what a decline is. The alternative would also have had to generalise a closed enum of field keys into one rule per question, for a question that has no answer.
- **The rule is enforced in three places, and the third is the one that's easy to miss.** Refusing to publish a question that doesn't offer it, and refusing to publish one on update. But also: **un-ticking the decline on a published question is refused** — an edit to a *consent* flag, which without this would leave a standing number on `/community` that members can no longer decline to be in. Withdrawing consent is a sequence, not a single save: unpublish, then withdraw, then republish has to be re-ticked deliberately. And the read side re-checks rather than trusting the write side, so a row predating the rule (or a restored backup) stops rendering instead of quietly continuing to publish — which also means this function, being the JSON API's path in, can't be used to route around it.
- **The reason is phrased as a noun phrase, not a sentence**, because both callers splice it into their own: "published as a community indicator, and *<reason>*." reads badly when the reason is itself a clause with an "and" in it. Same class of bug as the publish/stop remedy split below.
- **Worth knowing before turning this on for a sensitive question:** an event population is *smaller and more identifiable* than a community — "1 of 8 people coming uses they/them" is a sharper disclosure than "1 of 40 members do", because the reader knows exactly who the eight are. The `coordination` gate is the tool for that case and still applies when scoped, and the decline above is what makes being counted a choice. There is deliberately still **no automatic small-n suppression**: a hidden threshold would make a published indicator read as broken with no way to tell why, and inventing a disclosure rule nobody agreed to is worse than the community choosing.

## declaring participation from a dashboard, and per-event questions

- **Saying you're coming is now a one-click thing on a dashboard.** The Community hub carries "Current and upcoming events" unconditionally — one long horizontal card per open event with its name, date span, how many people are coming (out of the cap when one is set, plus outstanding held invite slots and an over-capacity marker), and a Coming/Maybe/Not coming control. The Dashboard carries the same strip whenever the nav switcher isn't already narrowed to one specific event, and a top-of-page ribbon ("You're not down as coming for *event*") when it is. Nothing was ever missing from the data model for this: `listOpenEventParticipationCards` just reads the open cycles through the same `getCycleParticipationSummary`/`getMyParticipation` the Events page uses, so the count can't drift from the real figure.
- **A status-only declaration no longer wipes the dates and note.** Clicking "Coming" sends only a status; the arrival date, departure date, and note someone typed into the Events page's full form are left alone. `declareParticipation` now treats an omitted field as "leave as-is" while an explicit `null` still clears it — which is exactly what that form has always sent. Without this, a one-click nudge would quietly destroy real data.
- **A new `/questions` page aggregates everything a member still owes an answer to**, grouped by scope: the standing once-ever facts, the current event, and the current phase. This is the "cycle onboarding" half of the two onboardings this app actually has (the other, one-time and community-wide, is the Dashboard's welcome panel). It's also where a declaration leads: the Dashboard/Community controls record the status and then, if that event has questions of its own, hand over to `/questions?cycle=<id>`, so the pairing is "say you're coming, then tell us what we need" rather than a gate in front of the first step.
- **Required questions are now chased rather than merely offered.** An admin can already mark a ProfileQuestion required and scope it per-event or per-phase; what was missing was anything that made that stick. A `required` question with no real answer now adds to the Dashboard's badge and gets its own element above the feed, both of which clear the moment it's answered. That's the forcing function that makes a one-click declaration safe — without it, required information would be collected by nobody the moment a member closed the questions form. `/questions` deliberately gets **no nav item**: it's a supporting page, and every other outstanding thing in this app already surfaces on the Dashboard.
- **A third response, "prefer not to say", distinct from deferring.** New `ProfileAnswerStatus` value `declined` plus a per-question `allowPreferNotToSay` toggle (off by default). A deferral is an honest gap with a promise to come back; a decline is a deliberate, permanent refusal that nothing chases — not a due date, not a reminder. Because it's per question, a community decides which facts about someone are theirs to decline and which are conditions of participating (are you over 18, do you hold a licence for the vehicle you're bringing). Worth being explicit that turning it on makes a question optional in practice, since picking it satisfies the requirement permanently — so `required` means "everyone has responded", not "everyone has a value", on those questions.
- **A decline is stored with a null value, so aggregates can tell it from silence.** Someone who declined is not in the "no answer" bucket, which is what makes it usable as a real signal rather than a synonym for not answering. The Coordination view's capacity list gained a fourth state to match: a declined member reads as "declined to say" rather than as a member who declared no hours, which would imply a response they withheld. Declines are revocable from /profile's "Your answers", which now also surfaces deferrals, so either can be changed after the fact.
- **Deferrals are configurable and time-boxed, so "I don't know yet" can come back — or not be offered at all.** Two new ProfileQuestion columns: `requiredBy` (the date after which a member's deferral stops counting) and `allowDeferral` (whether the button is offered at all, default on). Without the first, a plain required/deferred pair silently lost the information forever — honest in March, useless the week a community has to book a bed count; blank by default, which keeps a deferral permanent for a standing fact like an emergency contact, where that's exactly right. The second is for questions with no "not yet" at all (a date of birth, a legal name), where offering the button just invites a click that stores a non-answer. Turning `required` or `allowDeferral` off clears any stored due date rather than rejecting the save, so un-ticking the box is actually possible; a due date typed at creation onto a question that fails those tests is still rejected outright. Either state stops satisfying its question if the community later withdraws the option, so toggling a flag off can't leave a standing exemption behind.
- **A question scoped to a phase that hasn't started no longer counts against anyone.** `phaseForCycle` deliberately ignores start dates (it answers "which phase drives the nav highlight", where the next phase up is still the relevant one), but that made every future phase's questions outstanding from day one for a community that lays out its whole season up front. Question surfacing now also requires the phase to have actually begun.
- **Per-event answers now land on the event you were just looking at.** Both the read and write sides of `listOutstandingQuestions`/`answerProfileQuestion` accept an explicit cycle, validated against the member's own community and the open-cycle lifecycle. Previously cycle-scoped answers always stamped against the member's *declared* cycle, which is wrong whenever someone has declared for more than one open event. A client-supplied cycle id naming another community's event is rejected outright rather than silently honoured.
- `/profile`'s inline "Questions for you" list is now a pointer to `/questions` rather than a second rendering of the same data that couldn't reach questions for an event the member hadn't declared on. Its already-answered review section is untouched, and both it and the Dashboard's onboarding panel now render one shared question form instead of two near-copies.

Phases 0-45 are in place. Phases 0-15 are the full original phase list; Phases 16-19 close out the rest of what the tech spec treats as "core, not optional"; Phases 20-42 and 44 begin the next slice — real, designed modules from `docs/spec.md` scoped after the codebase already existed; Phases 43 and 45 are cross-cutting UI infrastructure, not spec.md modules, picked up ahead of the still-scoped-but-unbuilt Phases 46-47. Phases 0-10 cover the tech spec's full MVP scope:

- Deployable skeleton (Next.js + Drizzle + Postgres, Docker Compose, Caddy) and the core schema
- Magic-link auth with a minimal profile
- A server-enforced Task lifecycle API (claim/release/park/resume/finish, multi-slot capacity, dependency gating) and a kanban board UI to work it by hand
- Requirement-gated claiming (tier/language/completed-task/custom eligibility, enforced server-side)
- Cycle creation, blank or cloned from the previous cycle (phases and tasks included)
- A task proposal flow (bare title+description submissions, reviewed and activated onto the board)
- A task detail view carrying wiki notes (with revision history), comments, and resource links
- A settings screen for branches, tiers, and whether cycles/phases are on — no direct DB access needed
- A scheduled attention-level job flagging stale, overdue, or newly-unblocked tasks on the board automatically

Phases 11-15 add coordination mechanics beyond MVP scope:

- Subtasks — a current holder can split off a piece of a task as its own claimable card, without releasing the whole thing
- Task openness & request-to-join — claiming an already-held `request` or `coordination_approved` task now files a request the current holder(s) accept or decline, instead of an instant claim
- Admins & Community-endorsed openness — the first real access gate: `/settings` is now reachable only by a current holder of the Admins task, a real `community_endorsed` task on the board (put yourself forward, others endorse, it converts to a real claim once enough do) rather than a hardcoded role — falling back to any member until a Community's first Admins task is ever actually claimed
- Shadow slots & succession — join a task specifically to learn it (exempt from Requirements, doesn't count toward capacity), mark yourself outgoing to nudge the wiki summary before handing off, and a filled shadow slot pre-fills who a cloned cycle's task suggests next
- Remaining coordination mechanics — Requirement waiving with a required, standing-visible reason; a self-assign confirmation check for branch coordination holders (server-enforced, not just UI); an anonymous task signal and a talk-to-my-coordinator ping, both visible to that branch's coordination holders; a community-wide Escalation view; and bulk task selection (tag-based clustering, select-and-claim-with-exceptions)

Phase 16 adds Profile questions — a shared "standing fact about a member" mechanism (once-ever, per-cycle, or tied to one phase name), landing its first real use: a phase-scoped Availability question feeds a new Coordination view showing capacity-aware fitted-ask flags (has room / about right / over, or the exact declared number for members who've opted into sharing it) and who hasn't declared availability for the current phase at all.

Phase 17 adds Input rounds — small, task-specific questions (free text or closed-choice) that anyone can pose on any task at any time. Posing one queues it silently; on a fixed community-wide cadence, everything queued bundles into one round, answerable in a single sitting from a new `/input-rounds` page, and results stay visible on the task itself afterward. A round with nothing queued just doesn't fire.

Phase 18 adds Assemblies — community-wide decisions, from a genuinely urgent one-off to a slower structural question. Any member can propose one, picking their own agenda-building, notice, and voting window durations; the phase (agenda → notice → voting → closed) is always computed from those, never a separate status to keep in sync. Results are live-tallied and always visible, but never applied automatically — turning one into an actual change stays a deliberate human step through the ordinary settings screen.

Phase 19 adds Scheduling polls — "when can enough of the right people actually meet." An organizer opens a poll against a branch and a date range; members paint the windows they're free on a real click-and-drag day-by-time grid, blind — nobody, not even the organizer, sees who submitted what until a slot is confirmed, only the aggregate overlap. Two resolution modes (must overlap a fixed required list, or clear an attendance threshold) decide which slots qualify to confirm. Scheduling a poll also spins up two real tasks right away ("Facilitate…" and "Take notes & publish the summary…"), and a poll can optionally carry an open agenda and a read-tracked summary, each defaulting from its Branch's own setting, falling back to the Community's.

This closes out every phase from the plan's original list plus the "core, not optional" slice added after it.

Phase 20 adds Documentation — the one module that defaults on, same footing as Task notes rather than something a Community has to remember to enable. Freestanding `WikiPage`s carry the same revision-history shape as a task's wiki summary (any member edits, every edit is a new timestamped revision), optionally filed under a branch or left general. A page can also start as a bare question with no answer — it sits flagged unanswered until someone writes a real one, or until it's resolved as a duplicate of an existing page (dropping out of the main index, showing up on the canonical page as "also asked as…"). A new `/documentation` index browses these grouped by branch, alongside a read-only view of every task's own current wiki content — no new storage, just a different lens on data that already exists.

Phase 21 adds Conflict management — a reporting/recusal flow given real design weight, not a thin deferred afterthought. The conflict team isn't a dedicated relationship; it's just whoever currently holds a Community-designated task, same pattern as Admins and branch coordination. Filing a report takes nothing but wanting to talk to someone (no categorization or detail required up front), and recusal works from three directions — the reporter can exclude specific team members up front, and any team member can recuse themselves or a peer once a conflict of interest surfaces. The invisibility guarantee is enforced by the database query itself, not application-level filtering: an excluded team member's view of the report queue is genuinely indistinguishable from the report not existing. Acknowledging a report narrows visibility down to just the reporter and the point of contact; only the reporter can escalate it back open to the whole non-excluded team.

Phase 22 adds Sensitive data — purpose-bound, not role-bound, access to a small fixed set of member fields (health conditions, allergies, emergency contact, orientation). Off by default, and the first real use of `Community.modulesEnabled`'s on/off gating (unused since Phase 1) — later optional modules can register into the same small gate rather than each inventing their own. A Community defines which task or tier unlocks which field; a member always sees and edits their own values regardless. A new `/sensitive-data` page shows, for each field the current viewer is unlocked for, every member's value — the same "surface exactly what's relevant to what you hold" pattern `/coordination` and `/escalation` already use.

Phase 23 adds Contribution tracking — a member's own completed/active/future picture, computed live off Task/TaskAssignment, nothing entered by hand. Categories are Phases (spec's own example categories — "planning, build, live operation, wind-down" — read exactly like Phase names, so this reuses the Cycle/Phase schema rather than a second concept), merged across cycles by phase name; a phase-less task falls into a single "Overall" category. A task assigned in a phase that hasn't started yet counts as future signed-up regardless of its claim status — the same signal spec describes for Browse-period claims and later-phase assignments. A member always sees their own picture; a new opt-in toggle (off by default) lets them share it with the rest of the Community on `/contribution`.

Phase 24 adds the Dashboard — a member's home view, and the new post-login landing page (magic-link verification now lands here instead of `/profile`). A personalized feed reads live off existing state: pending join requests on tasks a member holds, upcoming check-ins on their Waiting tasks, and any currently-held task that's picked up an attention flag. An always-visible community snapshot panel shows Tier composition, Branch spread (distinct members currently holding a task per branch), and Branch health — a per-branch coarse status (*on track · attention needed · struggling*) computed entirely from existing task attention-level state, visible to everyone, with coordination-view holders additionally seeing the real flag counts behind it. Recruitment-facing items, onboarding progress, and anything Spatial-planning-dependent stay out of scope — those subsystems don't exist yet (Spatial planning is currently paused).

Phase 25 adds Forms — the last core shared primitive without a scoped consumer, landing its first real, non-Recruitment use in the same phase: post-cycle feedback. A Form's fields use the exact same free-text/single-choice/multi-choice shape Question and ProfileQuestion already use, but unlike a Question, a Form's fields are submitted together, once, as a single validated event — required fields block the whole submission. `Community.postCycleFeedbackFormId`/`feedbackReviewTaskId` name the community's standing survey and which task's holder reviews responses — the same "the task is the authority" pointer pattern Conflict management already established, not a dedicated role. A new `/feedback` page lets any member submit a response (anonymously, if the form allows it) and lets the review-task holder read every response.

Phase 26 adds the intake half of Budget — fixed costs and itemized proposals, before Phase 27 adds ranked-choice voting and confirmation on top. A `BudgetCycle` carries the non-negotiable fixed costs an admin enters up front, a proposal deadline, and an `ownerTaskId` (whoever holds that task is the budget owner, the same "the task is the authority" pattern Conflict management and post-cycle feedback already established) — only one active cycle per Community at a time for v1. Any member can submit an itemized `BudgetProposal` before the deadline, tag it to a branch, and edit it themselves until the cycle closes; a stored `totalAmount` gets recomputed on every write rather than summed on read. A new `/budget` page shows the current cycle's fixed costs and every proposal, with a submission form while proposals are open and an inline pre-filled edit form for a member's own proposals.

Phase 27 adds ranked-choice voting and confirmation — turning Phase 26's closed proposal list into an actual funded budget. Once the deadline's passed (or the owner judges the list complete), the `BudgetCycle`'s owner-task holder closes proposals to voting; any member can then submit a `BudgetVote` — a full ranking of every proposal plus an optional "how much would you contribute this year?" signal — replaceable until the owner confirms. The live voting view tallies a positional (Borda-style) score across submitted votes for the aggregate order, alongside each proposal's cost-per-member and a running total. Confirming locks in a funded set the owner chooses — informed by, not bound to, the ranking — with a rationale required only when that set actually deviates from what the ranked order alone would have funded. Once confirmed, `/budget` shows the final funded/not-funded breakdown and, for each member, the real ask against the number they signaled.

Phase 28 adds Event scheduling — a community's own internal programme, reusing the same "the task is the authority" pattern Budget/Conflict management/post-cycle feedback already established rather than inventing a new access model. Any member submits an `EventProposal` (host, title, duration, space needs, and a set of preferred slots) at any time; the `Community.eventSchedulingOwnerTaskId` holder reviews them, and every review recomputes fresh conflict flags — two proposals sharing a space with overlapping slots both get flagged, checked against whichever slots a proposal currently has (its confirmed one, once set, or its full preferred list otherwise). A flagged host can propose a different slot themselves, or the owner can ping them as a nudge, or just mediate directly and confirm a compromise slot outside what either side originally listed — ranked choice sets priorities, but the final call here is just as human. Once every currently-pending proposal is confirmed or declined, the owner publishes: a single timestamp locks them from further edits and makes them readable by every member on a new `/schedule` page, right alongside a member's own outstanding proposals and a submission form. There's no separate "the schedule" entity or cycle-wide gate — publishing just takes whatever's pending at the time, and a fresh batch can start accruing again immediately after.

Phase 29 adds the standing-structure half of Shifts/rota — recurring, never-"done" work distinct from a Task's one-shot claim/finish lifecycle. A `ShiftSeries` (optionally rotated off an existing Task, per Coordination mechanics' "genuinely unloved tasks ... rotate it") is created by any member, who becomes its coordinator automatically — or, if it names a source task, whoever currently holds that task is a coordinator too, the same access-follows-the-task model as everywhere else in this codebase. Occurrences are always explicitly batch-generated, never live-computed — a coordinator picks either a weekly day-of-week-and-time pattern or a plain explicit datetime list, and the system inserts the resulting rows once. Any member can sign up for an occurrence up to its capacity (first-come, no waitlist) and withdraw before it starts. A new `/shifts` page shows every upcoming occurrence grouped by series for browsing and sign-up, plus a coordinator-only management view listing each occurrence's current roster. Completion/no-show marking and the Contribution tracking integration are Phase 30's job, not this one's.

Phase 30 closes the loop on Shifts/rota — a shift occurrence's own completion signal, and Contribution tracking actually reading it. Once an occurrence's end time has passed, the signed-up member self-reports it completed (the same trust posture as everywhere else in this codebase), or the series' coordinator can mark a no-show instead — a real, logged call, never automatic. `/contribution` now shows a member's shift completions as their own entry, read together with but never folded into their task-based completed count, landing under "Overall" since a shift carries no Phase association the way a Task does — and no hours figure either, since a shift doesn't inherit a Task's Effort magnitude; completions are counted, not hour-weighted. The task detail page also gains "Rotate this task into a shift," a true one-click action available to any current holder that creates a new series pre-filled from the task (title, description, branch, capacity) while leaving the original task completely untouched — a third option alongside "mark yourself as outgoing" for a genuinely unloved task, per Coordination mechanics.

This closes out the Budget/Event scheduling/Shifts batch (Phases 25-30) in full.

Phase 31 adds Participation & capacity — core Cycle machinery, not gated behind Recruitment, since spec is explicit that even a community that never recruits new members wants to know who's actually coming. A new `Participation` table (per cycle, per member: unknown/coming/maybe/not-coming, arrival and departure dates, a note) is resubmittable as plans change, upserted in place the same way Assemblies' and Budget's own vote/response tables already are. This finally wires up `Cycle.capacity` and `Cycle.returningWindowClosesAt`, both unused since Phase 6 — a new `/participation` page shows the current cycle's remaining capacity (the plain, unclamped difference — going negative rather than blocking or queuing once it's full, since spec treats hitting zero early as an ordinary visible limit, not a special case) and whether the returning-priority window is open, purely computed from `now()` the same way Assemblies' own phase state already is. Whoever can start a cycle can also configure its capacity and window — no separate "cycle admin" concept. This also closes two real, previously-deferred lines: `/contribution` now shows the average per category across the cycle's currently `coming` members alongside a member's own picture, and `/dashboard`'s Community snapshot panel now shows a real active-member count.

Phase 32 adds Recruitment's public entry points — the first genuinely public, unauthenticated write surface this app has ever needed, and the real access-boundary change that has to come with it. Once a Community turns the "recruitment" module on, an *unrecognized* email verifying an ordinary magic link no longer silently creates a Member (the correct default while the module is off) — it's redirected to a real "no account found" page instead, while an existing member keeps logging in exactly as before either way. `CommunityInvite` gives any member a shareable, always-single-use join link (with "good fit"/"know personally" checkboxes for later evaluation logic to read); redeeming one skips the magic-link round-trip entirely — a valid, unused, unrevoked, unexpired token *is* the proof of legitimacy — and sets `referredByMemberId`/`joinedViaInviteId` on the new Member. A new public `/invite/[token]` page deliberately shows nothing about the inviting member or the community's roster, just a path to join. `Inquiry` is a genuinely low-structure "message us" box at a new public `/inquiry` page — no application form, just a message and contact info, landing in a queue visible to and claimable by whoever holds the community's designated recruitment-facing task. A new `/invites` page lets any member generate and revoke their own invite links, with an inquiry inbox section for the recruitment-task holder.

Phase 33 adds the actual evaluated-admission funnel — a public application, however many evaluators the Community assigns, and a configurable recommendation-to-outcome mapping. A new public `/apply` page renders whatever Form the Community configures as its application (`Community.recruitmentApplicationFormId`, the same pointer-to-a-Form convention post-cycle feedback already established) and submits it through a new `submitPublicFormResponse` — the one Form use case that has to work before someone's a Member at all. However many evaluators the Community assigns (`Community.recruitmentEvaluatorCount`, default 2) — resolved as whoever currently holds the recruitment task from Phase 32, not a separate assignment mechanism — each file an `Evaluation` (proceed/decline/unsure + notes) against an application on the new authenticated `/applications` page. `Community.recruitmentDecisionRules` is an ordered, community-configured list of `{conditions, outcome}` rules (first match wins, a required unconditional fallback) resolving the filed recommendations — live-computed, never persisted, since acting on a reached outcome is Phase 34's job — to `proceed`/`wider_discussion`/`decline`. An applicant can optionally reference an invite link's token on their application without redeeming it, feeding its "good fit"/"knows personally" checkboxes into the same decision rules, exactly as spec describes, without disturbing Phase 32's own unconditional invite-redemption path. A standing `RecruitmentSubscription` opt-in lets any member get alerted to new applications on `/applications` — a subscriber who isn't an evaluator sees that something's pending and its computed outcome, never the applicant's own answers.

Phase 34 adds what happens between "we have a recommendation" and "this person is fully in" — the intro call, the one real objection window, and the handoff to someone who'll accompany them. A new `RecruitmentDecision` is the real, persisted trigger point Phase 33 deliberately left uncomputed-and-unstored: the moment enough evaluators have filed, it freezes the matched rule's outcome and, for `proceed`/`decline`, resolves immediately to accepted/declined; a `wider_discussion` outcome instead opens a real time-boxed window (`Community.recruitmentWiderDiscussionHours`) that a new scheduled job auto-resolves per the rule's own `defaultResolution` — unless a subscribed member raised a real `Objection` first, in which case it waits on a recruitment-task holder's own manual call rather than the timer. Conversation scheduling reuses Scheduling polls (Phase 19) directly rather than forking it: `schedulingEntry.memberId` is now nullable with a `formResponseId` alternate, so a not-yet-a-Member applicant can be a required must-overlap participant tracked by their own application instead — a new public `/intro-call/[token]` page reuses the exact same drag-select grid the authenticated poll page already uses, so the applicant submits blind availability with no account needed, and a real slot only confirms once all three (both evaluators and the applicant) actually overlap. An acceptance auto-creates a claimable "Accompany new member" task, pre-filling a suggested accompanier from the referring invite's creator when the application named one. A configured rejection template surfaces on `/applications` next to a decline — never sent automatically.

Phase 35 adds the pipeline view that ties the whole Recruitment module together — a single, computed, never-separately-maintained view of everyone currently in flight, the same "list of people and where they are" instinct the task board already gives for tasks. Each candidate's stage (applied → evaluation in progress → call pending → call scheduled → decision pending → accepted/declined → accompaniment assigned) is read live off FormResponse/Evaluation/RecruitmentDecision/SchedulingPoll/Task state — no new stored field, and no scoring formula: alongside the candidate list, a new holder-only `/recruitment` page shows the current Cycle's remaining capacity (Phase 31) and a Tier/Branch composition breakdown as purely informational context, the same "what balanced means here is a human call" posture as everywhere else Orchard stops short of deciding for people. Candidates stuck evaluated-but-uncalled or called-but-undecided now surface as a real "needs action" section on `/dashboard` for whoever holds the recruitment task — closing Phase 24's own explicitly-deferred "recruitment-facing feed items" line.

This closes out the entire Recruitment batch (Phases 31-35) in full.

Phase 36 adds Spatial planning's foundation — the site itself (`Plot`) and its named organizational regions (`Zone`), plus the SVG-based collaborative drawing surface the rest of this module will render onto. A Plot belongs to a Cycle, not to the whole Community — `cycleId` is nullable for a Community that's never turned Cycles on at all (the same "optional association" pattern `BudgetCycle`/`EventProposal` already use for the identical reason), so nothing here silently persists across every Cycle a Community ever runs. Scale calibration (mark two points, enter the real-world distance) gets an optional extension: either point can also carry a real GPS coordinate, enough to compute a similarity transform for GeoJSON import/export without adopting a map-rendering library — entirely opt-in metadata layered on the same SVG-only editor, never a reason to draw anything differently. Phase 37 adds the actual things drawn on the site — tents, vehicles, structures, furniture — sized and positioned to real-world scale, plus the profile data that informs planning them. Phase 38 adds the collaborative editing-rights layer: a Placement always stays directly editable by the Spatial-planning holder, but a confirmed `PlacementMember` or the current holder of its `linkedTaskId` can now self-service move it too — the change applies and renders immediately (dashed outline) but lands `pending` until the holder approves or reverts it. ## Member competences: guided tags, language proficiency, and trait-based matching

Standalone new work, not a continuation of the phase sequence above — no `docs/development-plan.md` entry, no phase number. `member.tags` had always been meant to double as skills, interests, *and* languages (`docs/spec.md`'s own member sketch said so), but only ever got built as one flat, unnormalized `text[]` a member edits at `/profile` — no vocabulary (so "Spanish"/"spanish" silently failed to match each other), no onboarding step despite spec explicitly describing one ("the member defines their own tags and availability; this is the matching input"), and no way to record a language's proficiency at all. Coordinators need this for two different jobs — finding someone with a specific skill (search) and surfacing good-fit tasks to a new member who doesn't know what to pick (ranked suggestion) — and one flat tags array can't do both well at once.

**Guided tags**: `/profile`'s tags input, and both task-tag inputs (`/propose`, proposal activation), now suggest from a combined member+task tag vocabulary (`src/lib/tags.ts`'s `listAllDistinctTags`) via a plain `<datalist>` — zero client JS, still plain free text underneath, so nothing existing that reads `member.tags`/`task.tags` needed to change.

**Language & proficiency**: a new `member_language` table (language, one of basic/conversational/fluent/native) — repeatable, unlike a `ProfileQuestion` answer, which is why it's its own table rather than a reuse. Editable at `/profile` (add/delete, no admin gate, same self-service posture as tags/contact methods). The `language` Requirement type now checks this table (case-insensitive, any level) instead of `member.tags` — a real behavior change, so every existing language-Requirement test was updated to set up a `member_language` row instead of a `tags` array.

**Trait axes — the bigger addition**: bipolar scalar dimensions (e.g. "wants direction" ↔ "wants independence"), set on *both* members (their own stated preference) and tasks (a proposer's suggestion, reviewed at activation), compared by proximity to rank onboarding's task suggestions. This is deliberately distinct from tags, which stay a search/filter tool rather than the primary suggestion signal now that axes exist. A new `trait_axis` registry (`communityId`, `key`, `lowLabel`/`highLabel`, optional 5 `optionLabels` to render labeled choices instead of a generic scale, `askAtOnboarding`, `sortOrder`, `archivedAt`) is admin-managed at `/settings`'s Profile & Privacy tab, mirroring `ProfileQuestion`'s own CRUD pattern exactly — a registry rather than hardcoded columns/enum, so the exact axis list can change without a migration. Scale convention: integer -2..2 (5-point). `member_axis_value` and `task_axis_value` hold the actual positions, one row per member/task per axis they've set — except the one axis named `commitment_preference` (one-off ↔ ongoing/ownership), which has no `task_axis_value` row at all: its task-side value is derived live from the existing `Task.effort` enum instead (`one_off`→-2, `ongoing`→0, `owns_a_thing`→+2), since duplicating what's already on every task would drift.

The Dashboard's onboarding panel gains a new "How do you like to work?" section rendering whichever `askAtOnboarding` axes this member hasn't answered yet (`listOutstandingOnboardingAxes`) — kept deliberately short (3 axes is the working default) since more than that is too much for one first-session screen; every other axis is still settable any time at `/profile`, alongside the 3 onboarding ones (re-editable there too, not one-shot). A new shared `AxisScaleField` component (plain radios, no client JS) renders either mode. Task-side suggestions reuse the in-flight `suggested*` pattern already built for `suggestedTags`/`suggestedEffort` on `TaskProposal`: a new nullable `suggestedAxisValues` jsonb column, offered on `/propose`'s "Add more, if you know it" section, shown (and fully overridable) again at activation, written into real `task_axis_value` rows by `activateProposal` — mirroring exactly how `suggestedTags` becomes `task.tags` today. Tasks created through any other path (`subtasks.ts`, recruitment's accompaniment task, scheduling-poll auto-tasks, the `/api/tasks` route) simply start with no axis values, same as they already start with empty `tags` — no new UI needed there, and a task with no axis data just doesn't contribute to axis-proximity ranking rather than breaking anything.

`listTaskFitSuggestions` (`src/lib/onboarding.ts`) changes from "tag overlap OR a satisfied individual_gate Requirement, first N matches in arbitrary query order" to computing an internal (never displayed, never serialized) score per included candidate — average proximity across every axis both sides have a value for, plus a flat boost for tag overlap and for a satisfied gate — and sorting by it before taking the top N. Inclusion is now three-way (tag overlap, gate fit, *or* at least one shared axis), a real widening from the old two-way test. This is a deliberate reversal of that function's own prior comment claiming ranked suggestion was "permanently out of scope, same line Phase 50 draws" — confirmed with the user that what's actually meant to stay out of scope is *automatic assignment*, never internal scoring used only to order a surfaced list; nothing here gates a claim or picks anyone automatically. `docs/spec.md`'s matching MVP-deferral section and its Member/Requirement/onboarding sketches were updated to say so, rather than left stating the opposite of what's now true.

**Availability** (how much time someone has *this phase*, as opposed to trait axes' stable style preferences) needed no new code at all — `ProfileQuestion.feedsCapacitySignal` plus `/coordination`'s "Availability" table already implement it end to end, just never configured for a real question in this deployment before. Kept as a distinct signal from the new `commitment_preference` trait axis on purpose: one is a fluctuating capacity number, the other is a stable "when I do take something on, do I want it quick or ongoing" preference — collapsing them would lose one or the other.

Two new migrations (`member_language`; `trait_axis`/`member_axis_value`/`task_axis_value`/`task_proposal.suggested_axis_values`), both purely additive. 22 new tests (`tests/member-languages.test.ts`, `tests/trait-axes.test.ts`, plus extensions to `tests/onboarding.test.ts` and `tests/proposals.test.ts` covering axis-ranking order, axis-only inclusion, the commitment-preference/Effort special case, and `suggestedAxisValues` flowing through activation into real rows) — 1101 total passing, `tsc`/`eslint` clean.

Standalone, not a phase — a direct response to real usage feedback (also from Leaf): budget line items had no way to express "8 tables at $50 each" or "$10 per person," proposals couldn't be broken down by which Branch they were for, and there was no way to see whether pledged contributions actually covered costs.

Replaces all four `label|amount` textareas across the Budget page (create-cycle fixed costs, edit-cycle fixed costs, submit-proposal line items, edit-proposal line items).

## Kitchen: food & drinks, as an optional module

Standalone, not a phase — picked up from `docs/roadmap.md` and specced in `docs/food-drinks-module-plan.md`; `docs/spec.md`'s "Food & drinks (Fruit)" section is the original description this restores. Off by default, like every optional module: a Community turns Kitchen on under Settings → Modules, then grants the `kitchen` permission module on a task the same way Admins, branch coordination, and the Budget owner already work. Five new tables (`menu_plan`, `meal`, `dish`, `dish_ingredient`, `food_idea`), three enums, and one new sensitive-data column, in migration `0061_busy_luminals.sql`.

**Access rides the task, and a grant is multi-cardinality.** No Kitchen role column anywhere — `isKitchenOwner`/`requireKitchenOwner` (`src/lib/kitchen/access.ts`) answer "does this member currently *hold* a task granting `kitchen`," the same holder-join every other module uses, and a cycle-less task means the standing menu while a cycle-placed one means that cycle's. Because a community may legitimately have several people cooking (weeknight cook, weekend cook, a festival rota), `kitchen` joins `admin`/`branch_coordination`/`support` in `MULTI_CARDINALITY_MODULES`: one grant is full module access *in its own scope*, and grants on different tasks never displace each other. `isKitchenOwner(actor, cycleId?)` takes the scope the way `isEventSchedulingOwner` does.

**One publish gate, not a status column.** A `MenuPlan` is a named, dated container scoped to a cycle (or the standing menu), with a single `publishedAt`: null is a draft, visible and editable only to a scope's owner; set is published, readable by the whole community and locked against every further edit — meals, dishes, ingredients, and idea adoption all funnel through one `requireEditableMenuPlan`, so "published" can't be enforced in some places and forgotten in others. A non-owner sees the newest *published* plan in their scope and can file ideas against the newest plan of any kind; a draft in progress is genuinely invisible to them, not just hidden in the UI.

**Headcounts are the core, so recipes scale into an actual shopping list.** A `Meal` carries a plain absolute date (v1), an optional phase anchor, an optional link to a shifts `ShiftSeries` for the cooking roster, and a `headCount`. Each `Dish` records the `serves` its recipe as written feeds, and `scaledIngredients` multiplies every `dishIngredient` by `headCount / serves` **on read only** — nothing is ever written back, so changing the headcount or a serving count is free and never drifts. `purchaseList` then groups those scaled amounts into a per-meal shopping list by *exact* ingredient name: two dishes' "flour" merge into one line, but "flour" and "plain flour" deliberately stay separate, because quietly merging near-synonyms is how a shopping list loses an ingredient. A meal with no headcount stays at recipe scale and computes no purchase list at all, rather than inventing one from a guessed number.

**Food ideas are attributed, persistent, and adopted in one step.** Any member can file a recipe suggestion, dish request, or preference against the active plan — open to everyone, no grant needed, deliberately *not* anonymous, since a cook often needs to ask a follow-up about a recipe. Statuses are open/adopted/declined, and `adoptFromIdea` creates the dish (`source: "from_idea"`, back-linked both ways) and flips the idea in a single transaction, so an idea can't be adopted into a menu without its dish landing.

**The dietary panel reads member data only through the sensitive-data module's own gate.** `getMealConstraintPanel` returns `null` — the panel simply doesn't render — unless the field is actually unlocked for the reader, and it re-checks active consent per read exactly as `getSensitiveDataTable` does, so a withdrawal takes effect immediately. Allergen flags are a bounded `ALLERGEN_FLAGS` const rather than a DB enum (new flags are a one-line change, not a migration), matched against members' free-text allergy fields by keyword, which catches "dairy" for a `milk` flag and "cashews" for `tree_nuts` and honestly reports "may conflict, verify" rather than pretending to be a safety guarantee.

**A third sensitive-data unlock route, which this is the first consumer of.** A field can now be unlocked by "whoever currently holds *any* task granting module X," not just one named task or one tier — `sensitiveFieldAccessRule.unlockedByGrantModuleKey`, exactly one of the three routes per rule, configured in Settings → Access & permissions. It is deliberately **community-wide**: a sensitive field is one community record, so the rule names the module and the granting task's own cycle placement does *not* narrow the unlock. That's the shape allergies→kitchen needs — a cook holding the Kitchen grant for one cycle still plans against the whole community's menu, and the module route matches per-rule, so holding a `budget` task can never satisfy a rule that names `kitchen`.

An **ordering/equipment lens** rides the same page rather than duplicating task data: open tasks in the menu's scope whose tags match the supply vocabulary (`ordering`, `equipment`, `supply`, `shopping`), with their task resources, shown only to the scope's Kitchen owner. Holders also get a Dashboard needs-action row for an unpublished draft and for open ideas waiting on a draft they own; the feed entry is module-gated and degrades to `[]` for everyone else.
