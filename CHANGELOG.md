# Changelog

The build history behind [`README.md`](README.md)'s feature list — what each addition built and why it's shaped the way it is. Every numbered phase (0-69) of the original development plan is complete, covering the full original build plan; nothing after that is numbered — real, scoped-but-unbuilt work continues to get picked up off [`docs/roadmap.md`](docs/roadmap.md) as its own standalone feature entry, not a phase. For the full technical spec, see [`docs/spec.md`](docs/spec.md).

## Unreleased: closing the gaps in open permissions — what travels, and what a shared item says

The open-permissions work landed in two commits; this is the part that turned out not to be finished by them, and all of it is small.

**An open flag doesn't travel, and now that's a test rather than a comment.** Cycle clone and Task Pack import both carry *grants* between communities and events, and both go through one function — `copyPermissionGrants` — so a Community's open modules travel nowhere, deliberately: a capability someone decided for their own members shouldn't follow a cloned event into a different set of members. That was true when written, and true now, but it was true by *omission*, which is the kind of thing that quietly stops being true. It's pinned now, along with the converse — clearing an open flag leaves the task grant alone, because the two are independent facts, not two states of one.

**`backstop` can't be opened, and the refusal is enforced at the write.** Its authority is a named person to notify, so there is nothing for "everyone" to be. The settings tab renders no checkbox and says why; `setModuleOpen` refuses it too, so a forged POST gets the same answer the UI would have given rather than a capability the interface promises doesn't exist. Thirteen other modules are openable, and opening one twice is one row.

**A shared needs-action section was claiming something false.** It said "nobody in particular is on the hook for these", which holds when a module is open and unheld and is wrong the moment it's open *and* three people hold it. It now says the item is outstanding for the Community rather than assigned to *you*, and adds that whoever holds the task sees it as their own — true in both cases. The related question of whether a shared section should *name* those holders is settled as no: a member lookup per open module on every dashboard render, to serve the readers least likely to need it, in a section whose heading already says "open to everyone".

Also: a spec section for the whole mechanic under Transparency & access, since it's a principle a reader of the spec would otherwise not know existed, and the plan document marked through to done — including the one item where the plan's own advice turned out to be wrong, recorded as withdrawn rather than quietly deleted.

## Unreleased: permissions a Community can open to everyone, and a Recruitment pipeline that can finish

Every permission in the system was task-gated: a capability existed because whoever currently held a task carrying a `permission_grant` row could do it, and nobody else could. That is a good default — authority you can point at, that goes away when the person leaves. But it has one failure mode with no way out. A Community that wants everyone to be able to evaluate applications, or draw the Zone plan, or close the budget has no way to say so, and the alternative — inventing tasks and claiming them so a resolver returns true — is not a setting anyone would find.

`open_permission_grant` adds that setting: one row per `(community, module)`, meaning *this Community has decided this capability is open to all its members*. It is deliberately a separate table rather than a nullable `permission_grant.task_id`, because every resolver reaches authority by joining a grant's task id to a `taskAssignment` — a `NULL` there would match nobody and grant nothing while looking correctly configured, which is the worst direction for a security setting to fail in. Thirteen of the fourteen modules can be opened this way; `backstop` cannot, because its authority is a *named person to notify* and a backstop with no name has nothing to do. Its checkbox is absent and says why.

The second half is what opening Recruitment actually fixes. `recruitmentEvaluatorCount` defaults to two, `recruitment` is single-cardinality per scope, and `computeRecruitmentOutcome` refuses to evaluate below the threshold — so a Community with one holder could never satisfy any rule above the mandatory fallback, and every application parked at `decision_pending` forever, surfacing only as a "stuck waiting on you" dashboard line. The data model always wanted an evaluation *panel* (`evaluation.evaluatorId` is per-evaluator); the access model permitted exactly one person. Opening the module is the fix, and `tests/open-permissions.test.ts` now has two ordinary members file evaluations and reach a `proceed` outcome, which was unreachable before.

Opening a module also had to not break the things that read "is this set up?". Eleven sites were using *grant existence* as a stand-in for *module configured*, and each failed differently: an open `conflict_team` left members able to review conflicts but **unable to file one**; its nav item disappeared; the recusal picker went empty while the recusal action itself worked; the Spatial-planning page told everyone "nobody can draw or edit"; and open Recruitment silently stopped scheduling intro calls and accompaniment tasks, because both take their `branchId` from the granting task and a member has no branch to fall back on. That last one is reported rather than papered over — inventing a branch would file a real poll and a real task under an unrelated one — and the hub says so.

Two smaller things fell out of doing it honestly. The needs-action lists were per-actor by construction, with copy in the second person ("Budget needs *your* attention"), so opening a module put everyone's outstanding work in everyone's feed and multiplied the nav badge; they now split `personal` from `shared`, where the distinction is **consent, not headcount** — a task with `capacity: 3` is deliberate redundancy and its holders each keep a personal item. And the Access & permissions tab never showed who actually held a task, even though `capacity` is the real control on that and nothing in the permission layer read it; each row now shows the holders by name up to three and a linked count above that.

Still deliberately not done: opening a module does **not** unlock a sensitive field gated to that module's grant. That coupling is real and invisible, and whether it should compose is a separate question about profile questions and consent — being worked out on its own.

## Unreleased: a phase you can read at a glance, and a number that stops being a number

The phase list on `/participation` rendered each phase's entire authoring form inline — two bordered date fieldsets with a segmented control apiece, a "Save dates" button, and a module-picker row — and buried the phase itself underneath. With a handful of phases the section became a wall of controls, and the one thing you'd come to check (when *is* this phase?) was the thing you had to read past the form to find. The rules below are all consequences of taking the summary seriously enough to write.

- **Each phase is now two lines and an `Edit`.** The card states its resolved date range, then says where it sits relative to the event in words; the date and module controls only mount when you ask for them. That's the `<details>`-for-edit rule the design conventions already set on every other form in the app — the phase view was the last surface still violating it. A pinned module moves from an invisible dropdown value to a `Tag` in the card header, because it changes the nav for everyone arriving while that phase is current and was otherwise only discoverable by opening the form that held it. The date range carries a shared year once ("Sep 1 – Sep 14, 2027") so a scannable list gives you a date rather than a repeated year.

- **The stored recipe is read out loud, and there is now one copy of the prose.** `src/lib/dates/describe.ts` replaces two near-identical inline formatters — this page's, and `tasks/[id]`'s milestone footer — both of which printed the raw machinery: `-4 day(s) from the event's start`, `0% of the way through the event`. Three rules, each because the number is a poor description of the day it points at:
  - **A negative offset is "before", a positive one is "after."** The sign is carried by the word, so nobody has to read a minus sign as a direction, and "1 day" is no longer "1 day(s)".
  - **A proportion is never printed as 0% or 100%.** Those aren't "the start" and "the end" of anything — they're just the first and last day of the event, which now says so. This is not an exotic case: `inferRelativeDate` compares strictly, so a phase beginning on the event's *first* day is stored as a `between` at 0, and `normalizeBoundary` re-bases to one every time the parent span changes.
  - **Zero days from an edge is the edge itself**, so "0% through the event" and "0 days after the event starts" — two different stored recipes for the same instant — now read as the same sentence.

- **Rounding a percentage needed a clamp, and finding that out was the point of checking.** The first pass rounded the proportion to a whole percent and *then* tested for 0/100, which quietly turns "0.27% of the way in" into "the first day" — a false claim about a phase that starts the day after the event does, and reachable on any event longer than a few months. The edges are now recognized by the stored value being *exactly* 0 or *exactly* 10000, and the displayed percent is clamped into 1–99 so the rounding can't walk a real proportion back out onto an edge. The exact date is on the line above regardless.

- **"A date you set by hand" was being reported about phases with no date at all.** `EMPTY_BOUNDARY` is itself `dateType: "absolute"`, so an unset boundary and a deliberately hand-typed one are identical across the recipe fields — the resolved date is the only thing telling them apart. Caught by rendering real authoring flows end-to-end (type a date → `inferRelativeDate` → stored recipe → printed prose) rather than hand-written fixtures: a phase with one boundary and no other claimed "ends a date you set by hand". The shared helper therefore takes the resolved date as part of its input — a milestone row has no cached `date` column the way a Phase boundary does, so `tasks/[id]` threads its `resolvedDate` in under the shared shape's name — and an unset boundary now reads "The end isn't set yet."

  Two things deliberately left alone. The **storage** is unchanged: 0 and 10000 remain perfectly good stored values, and collapsing them at write time would break the recipe-preserving edit path (`boundaryForEditing`) and the canonical re-basing in `normalizeBoundary` for no gain — the rule is about what gets *said*, not what's kept. And the **inference** is unchanged, so a phase entirely before the event still reports both edges against the start ("Starts 4 days before the event starts, ends 1 day before the event starts"); the repetition is honest about where the offsets are anchored, and eliding it with a pronoun would have made each line depend on the one above in a list people scan.

  Verified by `tests/dates-describe.test.ts` (13 cases pinning each rule, including the two-recipes-one-instant equivalence and the clamp at both ends), the existing `dates-resolve`/`date-display` suites, `tsc`, `eslint`, and a clean `next build`. Not verified in a browser: this working tree carries uncommitted migrations `0063`–`0074` that the local Postgres has never been migrated to, so every DB-backed test and the running app both fail on `cycle_indicators_enabled` regardless of this change — pre-existing, and reproduced on a clean stash to confirm it.

## Unreleased: community-wide coordination, and a permissions tab you can scan

- **Coordination can now skip the branch, for a community too small to want a coordinator per branch.** Coordination was already two widths — a branch column (an event-independent task in branch B covers all of branch B) and an event row (a task in event C covers all of C) — but a small community had no third answer, because **a branch is the smallest unit a task can be placed in**: `task.branchId` is `NOT NULL`, so no arrangement of ordinary tasks can express "every branch". The only workarounds were a coordination task per branch (exactly the duplication being avoided) or letting one branch's column quietly stand in for the whole community.

  `community_coordination` is a new grant module (migration `0069`) whose only difference is that **the branch is never part of its scope**. The scope rule is otherwise the ordinary one, unchanged: placement is the scope. Placed in an event it's that event's coordinator and nothing more — strictly, per the existing rule that a scoped coordinator never reaches outside its scope — and only a grant with **no event** goes community-wide, in which case the branch on its task is simply not read. That makes it cycle_variant rather than a community-only role, so a community can run community-wide, per-branch and per-event coordinators side by side, and the settings tab's tier table says so honestly instead of warning about a placement that works. It **coexists** with the other two widths and is multi-cardinality. The trade is worth naming: in exchange for never being narrowed to a branch, it's also never narrowed to an event unless you put it in one.

  It's deliberately a *module key* rather than a `scope` column on `permission_grant`: that column is exactly the second scope read that retiring `permission_grant.cycleId` (decision D8) removed, and capability-per-key is the shape the table already uses. Both keys resolve as one family in `src/lib/coordination.ts`, where the resolver reads placement *first* and module second — so a cycle-placed grant is a cycle row whichever key granted it, and the community-wide case can only ever be set by a grant with no cycle. `listCoordinationScopeIds` reports that case as a `communityWide` flag instead of enumerating every branch id, so the board, escalation queue and view-scope gates stay O(1) rather than each re-deriving "all branches".

- **The board's "Coordinated by {name}" tag was on essentially every task, and now only appears where someone needs to act.** One branch-wide coordination grant made *all* of that branch's tasks read "Coordinated by {name}", because the tag reused the same predicate that gates the card's Escalate action. Those are different questions, and conflating them made the tag carry no information: column semantics cover a branch across all its events, so coverage is true for ~100% of its tasks. The tag is now gated on `needsNamedCoordinator` — the escalation queue, plus unclaimed criticals, which is the exact trigger of the "Backstop: {name}" marker sitting beside it. Everything else keeps the coverage fact, which is what actually decides which actions a coordinator is offered. A community-wide holder is named last, only where no branch or event holder is, so a community that hasn't set one simply sees no tag rather than a name on everything. A tag that names a person should be earned by a task that needs one.

- **The permissions tab is grouped by how far each gate reaches — "Community-wide" and "Per-event" — and the per-module text is gone.** Fourteen modules each led their hint with the same "a task grants what it sits in" clause: one rule, stated fourteen times, in ~600 words of near-identical paragraph, with the part that actually differs (what holding the role *lets you do*) buried at the end of each. The shared rule is now stated once per section header, and the hints are reduced to the capability. The split is **derived from the tier table** rather than hand-listed, so a new module can't land in no section or in two — `tests/permissions.test.ts` asserts the two sections partition the module keys. Only the community-shaped tier earns its own section; the cycle-shaped and cycle-variant tiers share the per-event one, because the rule a reader needs is the same for both and the only real difference is the label each row already prints ("Evergreen" vs "Community-wide"). The task-detail checkbox list isn't sectioned, so it instead shows the derived scope under each checkbox — the same information, where the reader is actually deciding what to grant.

## Unreleased: open Assemblies on the Community hub, and a quieter sidebar

- **An open Assembly now shows on `/community`, and the Community nav item carries a badge.** But the badge deliberately counts only Assemblies you're actually still owed an answer on — a voting-phase one you haven't finished — never every open one. `spec.md` is emphatic that an Assembly gets "no built-in urgent notification, on purpose", and a badge lit for anything open would work straight against that: it would nag about a notice-phase agenda you can't vote on yet, and about an open agenda where nobody is waiting on anyone. So `isAwaitingMyAnswer` counts voting-phase only, and that one predicate is the single definition behind three surfaces — the hub's "N are waiting on your answer", the sidebar badge, and the /assemblies list's "Waiting on you" — so they cannot drift apart. The *listing* is passive and breaks no rule: nothing is sent, nothing interrupts, which is exactly how the "Current and upcoming events" cards on the same page are already treated, and why it lives on the community-wide page rather than the personal Dashboard. One shared `assemblyParticipationById` query serves the badge and the hub, and the hub reads `listOpenAssemblies` — so the badge is literally a count of what that page shows.
- **Link-header nav groups (Tasks, Community, Communication) now start collapsed; Modules starts open.** A `headerIsLink` group is a *link* first and a container second, so the row you click is its own destination and the sub-list is only alternate routes into it — expanding all of them by default turned the sidebar into a wall of indented text duplicating hubs each header already links to. Modules is the opposite shape: its header isn't a destination, so its items *are* the group, and collapsing it would hide the only content it has. The default is data in `nav-config.ts` as a new `defaultOpen`, and the sidebar's persisted state had to change shape to permit that: it stored a *set of closed groups* against a fixed "everything open" default, which can only ever add to the closed list — so a group now defaulting to closed could never be opened again, since clicking its chevron would have meant "close it" regardless of intent. It stores the chosen state per group instead, so opening works in both directions. The old `closedGroups` key is read once and converted rather than discarded, so nobody's sidebar springs back open because the format changed, and a test pins that `defaultOpen: false` can only appear on a group that both has a header link and has items — a header-less group collapsed by default has nowhere to go.

## Unreleased: Assemblies you can actually read, and one to decide your settings with

Assemblies had all the right data and none of it reached the screen. Reading an agenda was the worst of it: `options` was only ever rendered as the *inputs* of a vote form, and only once voting was open — so during agenda-building you couldn't check the options you'd just typed were right, and during **notice** (the phase whose entire purpose is "the agenda is locked and visible") a pick-one question was visually identical to a written-answer one. Nobody could read what they were about to vote on. Everything below follows from taking that seriously.

**Three real defects, not just awkward UI**

- **Options are now always visible, and the question says what kind it is.** Every agenda item carries an unconditional one-line shape — "Pick one · 4 answers to choose from", "Written answer · Everyone answers in their own words" — and lists its answers whenever the vote form isn't already showing them (i.e. every phase except voting, where the radios *are* the list). During voting the control moved out of the item cards and up into a single ballot, so the per-item cards below are unambiguously the review of what you just saved.
- **Options are normalised, once, in one place.** They arrive from three callers (the form, the JSON API, template seeding) and are trimmed, stripped of blanks, and checked for duplicates in `normalizeOptions`/`findDuplicateOption` — applied both by the zod schema at the action boundary *and* inside `addAgendaItem` itself, because that function already refuses to store a choice item with no options and shouldn't have been weaker for a direct lib call. Two duplicates used to produce two radios sharing one name **and** one value: the browser treats those as a single control, so checking one visually checked both, while the tally counted them as two answers. That silently misreported the result, which is worse than looking wrong.
- **A written-answer item can no longer carry options at all.** The old form kept its options field on screen for every response type, so typing options and then switching to Free text committed an item whose options could never be displayed, voted on, or edited again. The response type is now the single thing that decides whether an item has options. Options also arrive as repeated `option` fields rather than one comma-split string, so an option *containing* a comma is no longer impossible to express.

**Durations you can read**

- The three bare `agendaMinutes`/`noticeMinutes`/`votingMinutes` number boxes are one control: a number plus a unit (minutes/hours/days/weeks, so nobody types 2880 for a week), a **Urgent / Normal / Deliberate** preset that fills all three at once and stays individually editable, and a live preview of what the three numbers actually produce — "Agenda closes in 2 days · Voting opens in 4 days · Everything closes in 10 days". That preview is the thing the old form never had: it made you commit to three integers to find out what they meant. The defaults are unchanged (1/1/3 days), so nothing that worked before behaves differently. A zero-minute agenda now says outright that it would lock before anyone could add anything.
- A hand-rolled `relativeTime`/`humanizeDuration` pair (in `src/components/assemblies/time.ts`) replaces two divergent copies, and is deliberately not `Intl` — these strings render on both server and client, and a locale- or timezone-dependent formatter disagrees between the two.

**One ballot, not five round-trips**

- `submitAssemblyResponses` takes the whole agenda at once. A blank answer is *skipped* rather than rejected — leaving a field empty is how you say "no view on this one", and treating it as an error made a partial ballot unsubmittable. Failures are per-question and the rest still save, so a typo in one free-text box doesn't cost you four good answers. This also retired the old form's `multi.length > 0 ? multi : single` inference about which kind of question it was holding, which is exactly the kind of guess that breaks as soon as an unselected pick-any question is in the batch. The server distinguishes "not yours" from "voting isn't open" for a cross-community question id, rather than reporting the latter and hinting that someone else's Assembly exists.
- Unchecking every box in a pick-any question now says "Pick at least one of this question's answers" instead of the old "must be a non-empty subset of this question's options" — a different mistake deserves a different message.

**An open agenda needs an exit**

- `removeAgendaItem` lets you withdraw an item **you** added, while the agenda is open. Adding to an agenda is deliberately open to anyone with no approval step; without a matching exit the agenda was append-only for its whole window, so a typo or a badly-worded motion stayed visible to the entire community until the phase rolled over with no way for whoever made it to fix it. Your own items only — deliberately **not** modelled as a moderation power, since nothing in the spec grants one and an Assembly with no gatekeeping shouldn't quietly grow a delete button. Every item now also says who added it, which is the first question a member asks reading someone else's motion.

**Reading results, and knowing whether your vote is in**

- Choice results are proportional bars with counts and percentages instead of `"pancakes: 3"`; your own answer is marked in the tally, in the vote control, and on the free-text responses, which now carry member attribution (`You: …` on your own). Every item shows its response count in every phase, plus a "you haven't answered this one yet" note and how many members haven't weighed in at all. The phase line leads with the answer to the only question anyone opens this page with — "Voting closes in 2 days" — keeping the absolute timestamp underneath.
- The list page gains what it never had: the next closing boundary per Assembly, item/response counts, your participation ("you've answered 1 of 2"), and a **Waiting on you** section for live votes you haven't completed, listed *out of* Open rather than in addition to it.

**A rejected submit no longer eats your work**

- The agenda form used to submit to an action that redirected back with `?error=`, re-rendering an empty form — so a rejected submit destroyed the question text and the whole half-written option list, which is precisely when you most want to keep it. `addAgendaItemAction` now returns its failure, and `AgendaItemForm` holds the draft across the round-trip and shows the message inline. Verified live by closing an Assembly's agenda window server-side and submitting: the error appears with the text, the response type, and both options intact.

**The Founding settings template — deciding your settings together, without doing it by hand**

- `spec.md`'s "Two tiers of setting, not one" already commits a community to settling its *foundational* settings collectively: those "carry an additional expectation: an Assembly about the change should reach quorum … before Admins act on it." What never existed was a way to actually run one, and nothing in `src/` was a template, preset, seed, wizard, or checklist. There is now one starter: 18 agenda items across 6 areas — getting people in, who holds authority, critical tasks & endorsement, which modules are on, how we work together, data & privacy — covering exactly the settings a Community has to choose before it can really run (recruitment doors and evaluator count, the four invitation lanes, the 13 permission grants, task openness and endorsement thresholds, the 7 modules, staleness and call defaults, the 4 sensitive fields).
- **It stays advisory, exactly like any other Assembly, and that's what makes the write-up guide worth having.** Each item carries a `settingsMapping` naming the screen and field its answer becomes, and the closed-phase read view prints the tally next to that pointer — so "advisory" is still actionable, because whoever holds Admins is told precisely which field to change rather than having to work out which question was about which setting. Nothing reads that column to write a setting back. Seeded items are ordinary `assemblyQuestion` rows via the existing `addAgendaItem` path, so agenda lock, voting and tallies behave identically to a hand-written agenda and every item is removable.
- **Every option set is derived from the real enums and label maps** — `MODULE_DEFINITIONS`, `PERMISSION_MODULE_KEYS`/`PERMISSION_MODULE_LABELS`, `OPENNESS_LABELS`, `SENSITIVE_FIELD_KEYS`, the joining-lane names — so adding a module or renaming a permission updates the template automatically instead of letting it go quietly stale, which is the whole failure mode of asking a community to hand-write these. There are tests pinning that derivation.
- Reachable from `/assemblies/new` ("Use the Founding settings agenda") and prompted on `/settings` — the one place someone goes *because* they're about to configure something. The prompt disappears the moment a Founding-settings Assembly exists (read off `assembly.templateKey`, so the truth stays with the Assembly rather than being mirrored, and deleting it correctly brings the offer back), and otherwise on its own after a fortnight. It has no dismiss button: the two weeks *are* the answer to "I don't want this", and a "no thanks" would just mean it reappeared for the next person who didn't click it. The clock anchor is `community.foundersAssemblyPromptedAt` — deliberately "when we first showed it", not "how old the install is", since this is single-tenant self-hosted software and a deployment that has been running for a year and only just started using the tool properly must still be offered it.
- Three nullable columns, one migration (`0066`), no backfill: `assembly.template_key`, `assembly_question.settings_mapping`, `community.founders_assembly_prompted_at`. `template_key` is free text rather than a pgEnum on purpose — adding a template shouldn't cost a migration.

## Unreleased: question field shapes

- **Six answer types, with the variations as flags rather than as more types.** `text` (one line or long), `single_choice`, `multi_choice`, `boolean` (yes/no), `date` and `number`, replacing `free_text`/`single_choice`/`multi_choice`/`date`. The point of keeping the list at six is that the orthogonal parts stay orthogonal: short-vs-long and a format check (none/email/phone/url) are two independent settings on a text field, because "an email is still a text field, still short, still deferrable" — a flat list would need `short_text`, `long_text`, `email`, `long_email`, `phone` and a branch in every renderer and validator for each. `free_text` is gone because it described neither its length nor anything else; existing rows migrate to `text` with the long-answer flag on, so no question changes how it renders.
- **A choice field can offer an "other" escape hatch.** This is the one that makes a closed list usable: a vocabulary you can count, with a way for people to answer in their own words, which is otherwise a choice between a list that excludes people and free text you can't aggregate. The words are stored as an ordinary string in the option's own slot, so an aggregate needs no special case to count the options. Deliberately **not** a ranking: pronouns aren't a priority order, and requiring a primary asks people to invent a fact about themselves. It does imply a list, so a list is also expected — a free-text-only pronoun field can't feed a diversity indicator, and shouldn't be asked to.
- **A Form submission is now actually validated.** It previously checked required-and-blank and nothing else, which was survivable when a field could only be text or a choice and was not survivable the moment a form could hold a number with bounds, a yes/no, or an email — a form would have accepted "banana" for a number and stored it. Every submitted value now goes through the same `validateFieldValue` a ProfileQuestion answer does, and the whole submission is rejected if any value fails.
- **One definition of a field's shape, one renderer.** New `src/lib/field-shape.ts` owns the type union, the flags, the validation and the submitted-value reading; `ProfileQuestion` and `Form.fields` both project into it, which is what spec's "Forms made of Questions? Partly" line always meant but which was previously two near-identical zod schemas, two value-extraction copies in `/apply` and `/feedback`, and **four** separate per-type rendering switches (the two answer forms, `FieldPreview`, and the Dashboard's prefilled-answer review). All of those now go through one component and one function, so a new type is an edit in one place. Forms also gain the three types they never had — `date`, `boolean` and `number` — despite already sharing the field builder with ProfileQuestion.
- **Booleans and numbers are stored as booleans and numbers**, not as the strings `"false"` and `"12"`, so an aggregate can count and sum them without re-parsing. A blank check no longer treats `false` or `0` as unanswered, which is the kind of quiet bug that drops people out of counts.
- Fixed two real bugs found while verifying: a choice field's escape-hatch input shared a name with its radio/checkbox, so leftover text in that box could overwrite the option actually chosen; and `/profile`'s answer action never routed through its own error handler, so a rejected value surfaced as a 500 instead of a message.
- **The other two question systems now read the same six types.** Task questions (Input rounds) and Assembly agenda items each carried their own three-value `free_text` enum, their own zod schema, their own validator and their own inline renderer — the third and fourth copies of a definition that already existed twice, each free to drift. So "when could you do this?" and "how many hours could you give?" were inexpressible on a task, and a body voting on how to spend a budget had no way to ask what the budget was. Both enums are rebuilt onto the shared six in migration `0068`, their validators are now `validateFieldValue`, and their renderers are `FieldPreview` — five inline type switches down to one. `free_text` rows migrate to `text` with the long-answer flag on in both tables, because every one of them rendered a textarea and an input round or agenda answer is usually a sentence; the column default is `true` there and `false` on `profile_question` for the same reason, which is worth stating because a generated migration gets it wrong.
- **What they deliberately do *not* get is the status model.** No `required`, no deferral, no "prefer not to say", no due date, no per-event scoping. An input round is an opinion or an offer and an agenda item is a position someone takes; in both, abstaining by not answering is already a complete response, so there is nothing to defer and nothing to decline. The shape is shared; the semantics are genuinely different, and keeping them separate is the point rather than a gap.
- **The tally can no longer quietly disagree with the response count.** A choice item with the escape hatch on can collect a free-text answer, which no option can claim — and the tally iterated `options`, so those answers were dropped while `total` still counted them, making the percentages next to it quietly wrong. Both the Assembly tally and the task-question tally now count them as their own visible "wrote their own answer" row, so the bars still sum to the figure printed above them. The same reasoning as showing the "other" bucket in an indicator rather than folding it away.
- **A blank submission is reported rather than crashed on.** Sharing the validator initially let a blank through as `null`, which `assembly_response.value` (NOT NULL) rejected with a raw database error — a regression against the old code's clean `ConflictError`. Rejecting is right for another reason too: the alternatives are deleting the response, which makes "Update answer" a silent no-op when someone clears a box to change their mind. The shared validator takes a `blankMessage` because its default, "This answer is required", is *false* for both new callers — nothing is required, and a member who pressed the button on an empty box needs to be told that rather than scolded, so each supplies its own wording.
- **A stored answer is shown as itself.** `String(r.value)` was correct while every non-choice answer was prose, and prints "false" and "2027-03-01" at a member once a yes/no and a date are real values. `formatFieldValue` is the read side of what `fieldValueFromFormData` writes: "Yes"/"No", a figure as a figure, and a canonical date formatted — but only for a `date` field, and only when the value really is one, so a free-text answer that happens to start with a date is left alone.
- **A `multi_choice` answer is strictly a set.** The shared validator initially coerced a lone value into a one-element array; accepting that would store a string where the shape promises a list and force every reader to handle both. No transport is inconvenienced, since checkboxes under one name always submit an array.
- **Describing a shape in words is one definition too.** `RESPONSE_TYPE_HINTS` and `RESPONSE_TYPE_NOUNS` join the label map, because the copy was being hand-written per surface and the failure mode is concrete: `QuestionShape` treated "not a choice" as "is prose", so the moment an agenda item could be a date, a figure or a yes/no it printed "Written answer — Everyone answers in their own words" under all three. A lookup can't drift like that, and a test pins that no type is missing a label, a hint or a noun. `agenda.ts`'s own `isChoiceType` and `AssemblyResponseType` are re-exports of the shared ones rather than lookalikes.
- **The Assembly ballot had to learn the new types too**, and this is the part that made the change more than a schema change. It's a controlled client component, so it can't use `FieldPreview`; but the agenda composer can now create a date, a figure or a yes/no, and leaving the ballot unable to render them would have let a community author questions its own voting form couldn't answer. It renders all six itself and serialises `false` and `0` as answers rather than absences. Its "N of M answered" count and its payload are now derived from one function instead of two parallel derivations, which is the case where a field the count called answered got dropped from the submission.

## Unreleased: a member's standing opt-out from published indicators

- **A member can now drop out of every published community indicator at once**, from a new "Community indicators" section on `/profile` (migration `0071`, one boolean on `member`). This is the consent mechanism that was missing: `allowPreferNotToSay` is a *response to one question* — still required on every published indicator — but neither that nor ticking the box on a question is the same as a member deciding once, "don't put me in any aggregate". A question invented in year two has no decline for them to have used.
- **It is a reporting exclusion, not an answering gate.** You can still answer every question while opted out, and answering still costs nothing in outstanding-question terms. Suppressing answering too would be a way to drop someone out of a *required* question by hiding the control, which is the opposite of what the control says on the tin. A test pins that the answer is still written.
- **An excluded person is out of the denominator, not just the numerator.** Both halves matter and they fail differently: leaving them in the population while dropping their answer would make the coverage line report a permanent "1 haven't" for someone who is still answering everything. `populationIds` is the single definition of who an indicator describes, and both the count and the answer filter read it, so they cannot drift.
- **Self-service, with no Admin path over it.** An Admin ability to exclude a member would be the same power as one to include them without asking, wearing a privacy label. `updateIndicatorExclusion` mirrors `updateContributionVisibility`'s existing shape for the same reason.
- **Deliberately the *opposite* default to `contributionVisible`, and the difference is the justification.** A contribution record is generated passively from task history — the member never did anything to create it, so sharing it has to be asked for. A profile question was asked, the member answered it, and answering already implied the community would see the answer; being counted in an aggregate of it is the expected consequence, not a new disclosure. Opt-*in* here would compound on the decline each published question already offers, and coverage would collapse to whoever knew to come and tick a box.
- **The control is its own section, not part of "Your answers"**, which only renders once there's something to show. The whole point of a standing opt-out is that it can be set *before* answering anything — a member who wants to be in the questions but out of the aggregates has to be able to say so first, and a control that appears only after you've answered is a control that informed nobody.
- **Known sharp edge, not hidden:** anyone who answered a question *before* its community published it was counted from the moment it was published, with no consent step at answer time. Opting out is immediate for them, but they had to find this first. The real fix is the one still open — publishing is currently an Admin's decision rather than the Community's, which `docs/spec.md`'s two-tiers rule says foundational settings should not be. **That remains the bigger gap.**
- Also corrected a wrong comment: the consent floor claimed `listCommunityIndicators` was "the JSON API's path in". There is no such route — both call sites are pages — so the read-side re-check is now documented as what it is, a defence against a row that predates a rule.

## Unreleased: sensitive profile questions, emergency access, and a settled consent model

The three-category question taxonomy (public / logistics / gated) is replaced by independent attributes, and the per-publication consent machinery built earlier in this same branch is **removed**. Migration `0076` adds `profile_question.sensitive` and `profile_question.emergency_access`; `0077` drops `member.excluded_from_indicators`, `profile_answer.indicator_consent` and the `indicator_consent` enum.

- **A profile question carries attributes, not a category.** `sensitive` and `emergencyAccess` join `publishedAsIndicator` and `scope`. There is no category column, because the three-category version failed on its own terms: "gated" turned out to be *access*, not a kind of data — t-shirt size isn't sensitive and still mustn't be readable by everyone — and folding it in as a category made "medication on site" inexpressible, being both sensitive and per-event. Full design and the proposed default set: `docs/default-profile-questions.md`.

- **Emergency access and publishing are refused as a contradiction**, on create and on update, in both directions. A published indicator is already readable by the whole community, so an override has nothing to reach — and the flag would be asserting the opposite of the truth about why anyone would need the answer. "If there's a fire, look up the community's t-shirt sizes" isn't a rule, it's a mistake, and a mistake in a flag that *overrides* a privacy default is worth catching at the settings boundary. Checked against the effective flag pair rather than the submitted one, since the form submits both on every save — so unpublishing and enabling emergency in one save works, as it must.

- **Consent is granted once, at the section, and never per question.** `member.excludedFromIndicators` becomes `consentsToCommunityIndicators`, defaulting to **true** — the deliberate opposite of `contributionVisible`, and for the same asymmetry: a contribution record is generated passively from task history so sharing it must be asked for, while an indicator aggregates answers the member gave knowing the section may appear. Answering *is* consenting, here and for emergency access alike.

  This retires work built earlier in the same branch: the `indicatorConsent` enum, the `pendingConsent` count, the "asked whether to be counted" coverage line, the `/questions` consent-request section, the Dashboard's consent element, and its share of the nav badge. They solved a per-publication nagging problem that section consent makes impossible, and they were triggered by an *admin's* action — a member could be re-asked about a question they'd already answered because somebody in settings ticked a box. The only thing that re-opens consent is widening a **sensitive** question's audience, and only for the member whose answer it is.

  A test asserts the shape of the absence: an exhaustive list of `profile_answer`'s columns, so re-adding a per-answer consent field is a test failure rather than a quiet reintroduction.

- **Consent is to a rule, not a list of people.** "Whoever holds the task" is consented to as a *relationship*, so a new claimer is inside what was agreed and needs no new conversation — the same shape as "anyone holding Kitchen" when Kitchen is open. Only edits to the rule re-open it: adding a task link, changing an access rule, turning on emergency access.

- **Sensitivity is made cheap-to-abuse deliberately not**, and that lands in this increment as the settings copy rather than as code: a non-sensitive, unrestricted question is **readable by the whole community**, so restricting one at all requires marking it sensitive *and* configuring rules. Under-labelling a health question therefore doesn't save an Admin any work, it publishes the data to everyone, visibly. The shortcut and the danger can't point the same way, so nothing has to be trusted to tick the right box — and it retires the per-module opt-in list that a hardcoded `allergies → kitchen` pairing would have needed. (The read-side enforcement lands with the access rules, next.)

**Still to come on this design:** access rules retargeted from a field enum to a question id, the per-answer share-with-audience checkbox (sensitive only, default on), required `emergencyAccessLog.explanation` for question reads, task-derived questions, the community-chosen prominent profile set, and setup-time seeding of the default question set.

## Unreleased: sensitive profile questions actually restrict something

`sensitive` and `emergency_access` were columns in the previous entry and nothing more. This is the read side that makes the first one mean something, plus the third way a question can contradict publication. Migration `0078` gives an access rule and a consent purpose a question to name, and adds the per-answer share flag.

- **An access rule can name a question, not just one of the four fixed member columns.** `sensitive_field_access_rule.field_key` becomes nullable beside a new `question_id`; exactly one of the two is set per row, enforced in `src/lib/sensitive-data.ts` by the same app-layer rule the table already used for its three unlock routes. The four member columns are `docs/spec.md`'s fixed set and stay exactly as they were — questions are additive beside them, not a replacement, and `consent_purpose` gains the matching `gates_question_id`. **`consent_record` is untouched**: consent stays keyed by legal purpose, which is the shape it already had, so this widens only *what a purpose can gate*. A purpose is a purpose whatever it gates, and the notice a member agreed to is the same text either way.

- **`sensitive` performs no restriction of its own — the rules do — so marking one with no rule is refused.** This is the load-bearing guard, and without it the flag is worse than nothing: `resolveReadableQuestions` fails closed, so a sensitive question with no rules has an *empty* audience, and an Admin who ticked the box believing they'd narrowed it to the kitchen team has instead narrowed it to nobody, invisibly. The settings toggle is disabled until a rule exists rather than hidden, because a greyed-out box that says why is the version someone can act on.

- **The read side fails closed, and is one function.** `resolveReadableQuestions` is the only definition of profile-question readability, applied inside `listOnceEverAnswers` rather than at each render site — a permission every consumer must remember to apply is one that eventually isn't, and the surface that forgets is the one that leaks. The ladder is three levels: not sensitive → everyone may read; sensitive → the union of holders of any linked rule; own answer → always readable at any level. Being wrong toward "nobody" costs a hidden answer; being wrong toward "everyone" costs someone's medication.

- **The rule is the half that goes first, which took a correction.** Requiring a rule to already find its question sensitive, *and* refusing to mark a question sensitive until a rule exists, is a deadlock with no legal starting move — the state is unreachable. So a rule against a not-yet-sensitive question is allowed and is a **staged** rule: it restricts nothing today, and starts restricting the moment the flag lands. Same for a consent purpose. The settings copy names the sequence.

- **The audience is a relationship, not a list of people.** A task rule is consented to as a *rule*, so Carol claiming a task Bob used to hold puts Carol inside what was agreed with no decision required from anyone — and Bob, who never held it, is not inside. Treating a claim as a consent event would either spam members or produce a notification they learn to ignore. Nothing is cached: deleting a rule stops the read on the next request, because the resolution is a function of current state rather than a stored entitlement.

- **`profile_answer.share_with_audience` is the member's own lever, on sensitive questions only, defaulting on.** Un-ticking reduces the answer to emergency-only and leaves it on their own profile — distinct from declining, which removes it from the profile too. A plain question is readable by the whole community, so there's no audience to decline joining and no box is offered; the writer forces the column back to `true` there, so it can never store a claim about the world that isn't true. Default on because the exposure is already bounded by the rules the community configured, so sharing is the expected consequence of answering and the safe choice shouldn't be the one people have to remember.

- **`sensitive` is now refused alongside `publishedAsIndicator`**, joining `emergency_access`. All three contradictions are one function: each is a claim that is *false* of a published question rather than a rule that could be satisfied differently. Sensitive says "restricted to an audience"; publishing says "in front of everyone"; emergency says "you might need this and not have it". A flag that lies is worse than a missing one, because the next person to read it trusts it.

**Still to come on this design:** emergency *reads* are not wired to the log yet (`emergency_access` is stored and guarded, but activating emergency mode doesn't yet surface question answers, and `emergencyAccessLog.explanation` being nullable still needs making required for question reads); task-derived questions inheriting their task's scope; the community-chosen prominent profile set; and setup-time seeding of the default question set.

## Unreleased: community indicators — publishing an answer as a fact about everyone

- **A community can now choose which of its standing questions are aggregated on `/community`.** A new `publishedAsIndicator` flag on `ProfileQuestion` plus an `indicator_visibility` enum (`public` / `coordination`), migration `0070`. This is the payoff of having asked something like pronouns in a shape that keeps its options countable: an answer that stays private teaches the community nothing, and an answer published without anyone choosing to is a disclosure no member agreed to. The section renders as "About this community", and reads "Chosen by this community from its own standing questions. Everyone here chose to answer their own; nobody is named."
- **Nobody chooses the display form — it's derived from the answer type**, because the alternatives are worse in a specific way each. Three families cover every publishable type: **split** (`single_choice`, `boolean` — everyone contributes exactly one thing, so the parts are shares of a whole), **distribution** (`multi_choice` — everyone may contribute several, so each count is "how many people chose this" and the counts deliberately *don't* sum to the answerer count), and **summary** (`number`, `date` — a magnitude or a point in time, which has nothing to split, and bucketing one would invent a histogram nobody asked for). A hand-picked chart option would let someone put a pick-any question in a pie, and a pie of "who picked what" implies slices of one whole when five people choosing three options each is fifteen slices over five people. `text` has no family and **cannot be published at all** — not "shows badly", but because the only honest total of a text field is the members' own words.
- **Indicators are public, full stop — never coordinator-gated.** An earlier draft had an `indicator_visibility` enum with a `coordination` option, and it was wrong twice over: most members still saw the coverage line, which is itself a set of facts about a small nameable group, and saw none of the content. An indicator's entire purpose is to tell the community something about itself, so the protections that belong on this surface are **consent** (a decline is required on every published question, a member can opt out of all indicators at once, and a pre-publication answer is asked about before it's counted) and **the community's own choice of what to publish** — not a permission tier. The column and enum are dropped in `0073` rather than left unused so they can't be read as still-supported. A test now asserts that granting coordination changes nothing, in either direction, as a guard against reintroducing a gate.
- **Every number carries its denominator, and a refusal is never silence.** The coverage line reads "3 of 4 answered · 1 preferred not to say · 1 haven't" — declined and merely-unanswered are different states with different meanings and are never merged, and the denominator is *every* member rather than the active ones, so the figure can't quietly flatter itself. The escape hatch's answers are a visible "Something else" row: folding them into a neighbouring option would undo the reason the hatch exists, dropping them would make the parts fail to sum, and only the **count** is ever published — what someone typed is theirs, and no "publish this indicator" toggle can consent to it on their behalf.
- **A number is summarised with a median as well as a mean**, because 3/3/60 has a mean of 22 that describes nobody in it. Both are labelled; the mean isn't dropped, it's just not presented as *the* number. Dates are a range (earliest/latest), not a histogram.
- **An edit can't silently unpublish an indicator.** Changing a published question's answer type to something unaggregable is **refused with a message naming the fix**, rather than quietly clearing the flag the way a stale `min`/`max` is cleared. Clearing would mean an admin editing an unrelated dropdown makes a community-chosen disclosure vanish from `/community` with nothing said. A label edit on a published question still works — a guard written as "reject any update to a published question" would have blocked that, and there's a test pinning it.
- **A checkbox that can't be ticked says why.** The settings toggle is disabled on a written answer or a per-event question, with the reason *and* its remedy attached, because a greyed-out option with no explanation reads as a broken app. The reason and the remedy are separate values, not one string: the two callers need different fixes, and concatenating them produced a message that told an admin to "change the answer type to pick one first" while they were trying to *stop* publishing. Archived questions stop publishing — a number nobody maintains, ageing silently, is worse for trust than none.
- **The indicators follow the Dashboard's existing "This event / All open events" choice, rather than getting a second control.** An event-scoped indicator is "of the eight people coming, five have told us their pronouns" — and only the *population* narrows, since the answers are once-ever standing facts. Deliberately one control for one underlying question ("who are we talking about?"): two controls is two things that can disagree, and a reader would have no way to tell which population a proportion described. The population is read from the same `Participation` `coming` rows as the "N members coming this event" count directly above it, so an indicator and the count under it can't describe different groups. `memberCountView` was hoisted above the query so both resolve the default the same way. `/community` stays community-wide — it isn't under `/[cycleScope]`, so it has no event view to narrow to.
- **A proportion that doesn't name its population is meaningless**, so an event-scoped section says so: "Each one describes the 3 members coming to Spring Weekend." Without that line the same indicator would silently mean two different things on two pages, which is the one failure a percentage can't survive. An event with nobody declared coming reports **0 of 0**, never the community's figures — a heading claiming these are the event's numbers while every figure is about someone who isn't coming is the worst answer available.
- **A published indicator now *requires* the question to offer "prefer not to say"** — the whole point of publishing is that people get counted in a number, and without a decline their only way out is to not answer. That's not a real opt-out, because silence is visible: it shows up as "2 haven't" in the coverage line, so the refusal leaks through the gap it was meant to protect, and a withheld answer is exactly as published as a given one. `declined` is stored with a null value and reported as its own figure, so a refusal is a refusal.
- **It takes a decline rather than a per-question "who may read this" rule**, which was the other thing on the table (and modelled, for allergies and an emergency contact, by `sensitive_field_access_rule`). That table exists because somebody has to read a *named individual's* value. An indicator has no such reader — the aggregate is the only thing that ever exists, and no code path anywhere shows one member's answer to anyone. So "who may see this?" is already answered, and the one that isn't is "may a member be counted without agreeing to be?", which is precisely what a decline is. The alternative would also have had to generalise a closed enum of field keys into one rule per question, for a question that has no answer.
- **The rule is enforced in three places, and the third is the one that's easy to miss.** Refusing to publish a question that doesn't offer it, and refusing to publish one on update. But also: **un-ticking the decline on a published question is refused** — an edit to a *consent* flag, which without this would leave a standing number on `/community` that members can no longer decline to be in. Withdrawing consent is a sequence, not a single save: unpublish, then withdraw, then republish has to be re-ticked deliberately. And the read side re-checks rather than trusting the write side, so a row predating the rule (or a restored backup) stops rendering instead of quietly continuing to publish — which also means this function, being the JSON API's path in, can't be used to route around it.
- **The reason is phrased as a noun phrase, not a sentence**, because both callers splice it into their own: "published as a community indicator, and *<reason>*." reads badly when the reason is itself a clause with an "and" in it. Same class of bug as the publish/stop remedy split below.
- **Worth knowing before turning this on for a sensitive question:** an event population is *smaller and more identifiable* than a community — "1 of 8 people coming uses they/them" is a sharper disclosure than "1 of 40 members do", because the reader knows exactly who the eight are. The `coordination` gate is the tool for that case and still applies when scoped, and the decline above is what makes being counted a choice. There is deliberately still **no automatic small-n suppression**: a hidden threshold would make a published indicator read as broken with no way to tell why, and inventing a disclosure rule nobody agreed to is worse than the community choosing.

## Unreleased: declaring participation from a dashboard, and per-event questions

- **Saying you're coming is now a one-click thing on a dashboard.** The Community hub carries "Current and upcoming events" unconditionally — one long horizontal card per open event with its name, date span, how many people are coming (out of the cap when one is set, plus outstanding held invite slots and an over-capacity marker), and a Coming/Maybe/Not coming control. The Dashboard carries the same strip whenever the nav switcher isn't already narrowed to one specific event, and a top-of-page ribbon ("You're not down as coming for *event*") when it is. Nothing was ever missing from the data model for this: `listOpenEventParticipationCards` just reads the open cycles through the same `getCycleParticipationSummary`/`getMyParticipation` the Events page uses, so the count can't drift from the real figure.
- **A status-only declaration no longer wipes the dates and note.** Clicking "Coming" sends only a status; the arrival date, departure date, and note someone typed into the Events page's full form are left alone. `declareParticipation` now treats an omitted field as "leave as-is" while an explicit `null` still clears it — which is exactly what that form has always sent. Without this, a one-click nudge would quietly destroy real data.
- **A new `/questions` page aggregates everything a member still owes an answer to**, grouped by scope: the standing once-ever facts, the current event, and the current phase. This is the "cycle onboarding" half of the two onboardings this app actually has (the other, one-time and community-wide, is the Dashboard's welcome panel). It's also where a declaration leads: the Dashboard/Community controls record the status and then, if that event has questions of its own, hand over to `/questions?cycle=<id>`, so the pairing is "say you're coming, then tell us what we need" rather than a gate in front of the first step.
- **Required questions are now chased rather than merely offered.** An admin can already mark a ProfileQuestion required and scope it per-event or per-phase; what was missing was anything that made that stick. A `required` question with no real answer now adds to the Dashboard's badge and gets its own element above the feed, both of which clear the moment it's answered. That's the forcing function that makes a one-click declaration safe — without it, required information would be collected by nobody the moment a member closed the questions form. `/questions` deliberately gets **no nav item**: it's a supporting page, and every other outstanding thing in this app already surfaces on the Dashboard.
- **A third response, "prefer not to say", distinct from deferring.** New `ProfileAnswerStatus` value `declined` plus a per-question `allowPreferNotToSay` toggle (off by default). A deferral is an honest gap with a promise to come back; a decline is a deliberate, permanent refusal that nothing chases — not a due date, not a reminder. Because it's per question, a community decides which facts about someone are theirs to decline and which are conditions of participating (are you over 18, do you hold a licence for the vehicle you're bringing). Worth being explicit that turning it on makes a question optional in practice, since picking it satisfies the requirement permanently — so `required` means "everyone has responded", not "everyone has a value", on those questions.
- **A decline is stored with a null value, so aggregates can tell it from silence.** Someone who declined is not in the "no answer" bucket, which is what makes it usable as a real signal rather than a synonym for not answering. The Coordination view's capacity list gained a fourth state to match: a declined member reads as "declined to say" rather than as a member who declared no hours, which would imply a response they withheld. Declines are revocable from /profile's "Your answers", which now also surfaces deferrals, so either can be changed after the fact.
- **Deferrals are configurable and time-boxed, so "I don't know yet" can come back — or not be offered at all.** Two new ProfileQuestion columns: `requiredBy` (the date after which a member's deferral stops counting) and `allowDeferral` (whether the button is offered at all, default on). Without the first, a plain required/deferred pair silently lost the information forever — honest in March, useless the week a community has to book a bed count; blank by default, which keeps a deferral permanent for a standing fact like an emergency contact, where that's exactly right. The second is for questions with no "not yet" at all (a date of birth, a legal name), where offering the button just invites a click that stores a non-answer. Turning `required` or `allowDeferral` off clears any stored due date rather than rejecting the save, so un-ticking the box is actually possible; a due date typed at creation onto a question that fails those tests is still rejected outright. Either state stops satisfying its question if the community later withdraws the option, so toggling a flag off can't leave a standing exemption behind.
- **A question scoped to a phase that hasn't started no longer counts against anyone.** `phaseForCycle` deliberately ignores start dates (it answers "which phase drives the nav highlight", where the next phase up is still the relevant one), but that made every future phase's questions outstanding from day one for a community that lays out its whole season up front. Question surfacing now also requires the phase to have actually begun.
- **Per-event answers now land on the event you were just looking at.** Both the read and write sides of `listOutstandingQuestions`/`answerProfileQuestion` accept an explicit cycle, validated against the member's own community and the open-cycle lifecycle. Previously cycle-scoped answers always stamped against the member's *declared* cycle, which is wrong whenever someone has declared for more than one open event. A client-supplied cycle id naming another community's event is rejected outright rather than silently honoured.
- `/profile`'s inline "Questions for you" list is now a pointer to `/questions` rather than a second rendering of the same data that couldn't reach questions for an event the member hadn't declared on. Its already-answered review section is untouched, and both it and the Dashboard's onboarding panel now render one shared question form instead of two near-copies.

- Subtasks — a current holder can split off a piece of a task as its own claimable card, without releasing the whole thing
- Task openness & request-to-join — claiming an already-held `request` or `coordination_approved` task now files a request the current holder(s) accept or decline, instead of an instant claim
- Admins & Community-endorsed openness — the first real access gate: `/settings` is now reachable only by a current holder of the Admins task, a real `community_endorsed` task on the board (put yourself forward, others endorse, it converts to a real claim once enough do) rather than a hardcoded role — falling back to any member until a Community's first Admins task is ever actually claimed
- Shadow slots & succession — join a task specifically to learn it (exempt from Requirements, doesn't count toward capacity), mark yourself outgoing to nudge the wiki summary before handing off, and a filled shadow slot pre-fills who a cloned cycle's task suggests next
- Remaining coordination mechanics — Requirement waiving with a required, standing-visible reason; a self-assign confirmation check for branch coordination holders (server-enforced, not just UI); an anonymous task signal and a talk-to-my-coordinator ping, both visible to that branch's coordination holders; a community-wide Escalation view; and bulk task selection (tag-based clustering, select-and-claim-with-exceptions)

Phase 16 adds Profile questions — a shared "standing fact about a member" mechanism (once-ever, per-cycle, or tied to one phase name), landing its first real use: a phase-scoped Availability question feeds a new Coordination view showing capacity-aware fitted-ask flags (has room / about right / over, or the exact declared number for members who've opted into sharing it) and who hasn't declared availability for the current phase at all.

Phase 17 adds Input rounds — small, task-specific questions (free text or closed-choice) that anyone can pose on any task at any time. Posing one queues it silently; on a fixed community-wide cadence, everything queued bundles into one round, answerable in a single sitting from a new `/input-rounds` page, and results stay visible on the task itself afterward. A round with nothing queued just doesn't fire.

Phase 18 adds Assemblies — community-wide decisions, from a genuinely urgent one-off to a slower structural question. Any member can propose one, picking their own agenda-building, notice, and voting window durations; the phase (agenda → notice → voting → closed) is always computed from those, never a separate status to keep in sync. Results are live-tallied and always visible, but never applied automatically — turning one into an actual change stays a deliberate human step through the ordinary settings screen.

Phase 19 adds Scheduling polls — "when can enough of the right people actually meet." An organizer opens a poll against a branch and a date range; members paint the windows they're free on a real click-and-drag day-by-time grid, blind — nobody, not even the organizer, sees who submitted what until a slot is confirmed, only the aggregate overlap. Two resolution modes (must overlap a fixed required list, or clear an attendance threshold) decide which slots qualify to confirm. Scheduling a poll also spins up two real tasks right away ("Facilitate…" and "Take notes & publish the summary…"), and a poll can optionally carry an open agenda and a read-tracked summary, each defaulting from its Branch's own setting, falling back to the Community's.

This closes out every phase from the plan's original list plus the "core, not optional" slice added after it.

Phase 20 adds Documentation — the one module that defaults on, same footing as Task notes rather than something a Community has to remember to enable. Freestanding `WikiPage`s carry the same revision-history shape as a task's wiki summary (any member edits, every edit is a new timestamped revision), optionally filed under a branch or left general. A page can also start as a bare question with no answer — it sits flagged unanswered until someone writes a real one, or until it's resolved as a duplicate of an existing page (dropping out of the main index, showing up on the canonical page as "also asked as…"). A new `/documentation` index browses these grouped by branch, alongside a read-only view of every task's own current wiki content — no new storage, just a different lens on data that already exists.

Phase 21 adds Conflict management — a reporting/recusal flow given real design weight, not a thin deferred afterthought. The conflict team isn't a dedicated relationship; it's just whoever currently holds a Community-designated task, same pattern as Admins and branch coordination. Filing a report takes nothing but wanting to talk to someone (no categorization or detail required up front), and recusal works from three directions — the reporter can exclude specific team members up front, and any team member can recuse themselves or a peer once a conflict of interest surfaces. The invisibility guarantee is enforced by the database query itself, not application-level filtering: an excluded team member's view of the report queue is genuinely indistinguishable from the report not existing. Acknowledging a report narrows visibility down to just the reporter and the point of contact; only the reporter can escalate it back open to the whole non-excluded team.

Phase 22 adds Sensitive data — purpose-bound, not role-bound, access to a small fixed set of member fields (health conditions, allergies, emergency contact, orientation). Off by default, and the first real use of `Community.modulesEnabled`'s on/off gating (unused since Phase 1) — later optional modules can register into the same small gate rather than each inventing their own. A Community defines which task or tier unlocks which field; a member always sees and edits their own values regardless. A new `/sensitive-data` page shows, for each field the current viewer is unlocked for, every member's value — the same "surface exactly what's relevant to what you hold" pattern `/coordination` and `/escalation` already use.

Phase 23 adds Contribution tracking — a member's own completed/active/future picture, computed live off Task/TaskAssignment, nothing entered by hand. Categories are Phases (spec's own example categories — "planning, build, live operation, wind-down" — read exactly like Phase names, so this reuses the Cycle/Phase schema rather than a second concept), merged across cycles by phase name; a phase-less task falls into a single "Overall" category. A task assigned in a phase that hasn't started yet counts as future signed-up regardless of its claim status — the same signal spec describes for Browse-period claims and later-phase assignments. A member always sees their own picture; a new opt-in toggle (off by default) lets them share it with the rest of the Community on `/contribution`.

Phase 24 adds the Dashboard — a member's home view, and the new post-login landing page (magic-link verification now lands here instead of `/profile`). A personalized feed reads live off existing state: pending join requests on tasks a member holds, upcoming check-ins on their Waiting tasks, and any currently-held task that's picked up an attention flag. An always-visible community snapshot panel shows Tier composition, Branch spread (distinct members currently holding a task per branch), and Branch health — a per-branch coarse status (*on track · attention needed · struggling*) computed entirely from existing task attention-level state, visible to everyone, with coordination-view holders additionally seeing the real flag counts behind it. Recruitment-facing items, onboarding progress, and anything Spatial-planning-dependent stay out of scope — those subsystems don't exist yet (Spatial planning is currently paused).

Phase 25 adds Forms — the last core shared primitive without a scoped consumer, landing its first real, non-Recruitment use in the same phase: post-cycle feedback. A Form's fields use the exact same free-text/single-choice/multi-choice shape Question and ProfileQuestion already use, but unlike a Question, a Form's fields are submitted together, once, as a single validated event — required fields block the whole submission. `Community.postCycleFeedbackFormId`/`feedbackReviewTaskId` name the community's standing survey and which task's holder reviews responses — the same "the task is the authority" pointer pattern Conflict management already established, not a dedicated role. A new `/feedback` page lets any member submit a response (anonymously, if the form allows it) and lets the review-task holder read every response.

Phase 26 adds the intake half of Budget — fixed costs and itemized proposals, before Phase 27 adds ranked-choice voting and confirmation on top. A `BudgetCycle` carries the non-negotiable fixed costs an admin enters up front, a proposal deadline, and an `ownerTaskId` (whoever holds that task is the budget owner, the same "the task is the authority" pattern Conflict management and post-cycle feedback already established) — only one active cycle per Community at a time for v1. Any member can submit an itemized `BudgetProposal` before the deadline, tag it to a branch, and edit it themselves until the cycle closes; a stored `totalAmount` gets recomputed on every write rather than summed on read. A new `/budget` page shows the current cycle's fixed costs and every proposal, with a submission form while proposals are open and an inline pre-filled edit form for a member's own proposals.

Phase 27 adds ranked-choice voting and confirmation — turning Phase 26's closed proposal list into an actual funded budget. Once the deadline's passed (or the owner judges the list complete), the `BudgetCycle`'s owner-task holder closes proposals to voting; any member can then submit a `BudgetVote` — a full ranking of every proposal plus an optional "how much would you contribute this year?" signal — replaceable until the owner confirms. The live voting view tallies a positional (Borda-style) score across submitted votes for the aggregate order, alongside each proposal's cost-per-member and a running total. Confirming locks in a funded set the owner chooses — informed by, not bound to, the ranking — with a rationale required only when that set actually deviates from what the ranked order alone would have funded. Once confirmed, `/budget` shows the final funded/not-funded breakdown and, for each member, the real ask against the number they signaled.

Phase 28 adds Event scheduling — a community's own internal programme, reusing the same "the task is the authority" pattern Budget/Conflict management/post-cycle feedback already established rather than inventing a new access model. Any member submits an `EventProposal` (host, title, duration, space needs, and a set of preferred slots) at any time; the `Community.eventSchedulingOwnerTaskId` holder reviews them, and every review recomputes fresh conflict flags — two proposals sharing a space with overlapping slots both get flagged, checked against whichever slots a proposal currently has (its confirmed one, once set, or its full preferred list otherwise). A flagged host can propose a different slot themselves, or the owner can ping them as a nudge, or just mediate directly and confirm a compromise slot outside what either side originally listed — ranked choice sets priorities, but the final call here is just as human. Once every currently-pending proposal is confirmed or declined, the owner publishes: a single timestamp locks them from further edits and makes them readable by every member on a new `/schedule` page, right alongside a member's own outstanding proposals and a submission form. There's no separate "the schedule" entity or cycle-wide gate — publishing just takes whatever's pending at the time, and a fresh batch can start accruing again immediately after.

Phase 29 adds the standing-structure half of Shifts/rota — recurring, never-"done" work distinct from a Task's one-shot claim/finish lifecycle. A `ShiftSeries` (optionally rotated off an existing Task, per Coordination mechanics' "genuinely unloved tasks ... rotate it") is created by any member, who becomes its coordinator automatically — or, if it names a source task, whoever currently holds that task is a coordinator too, the same access-follows-the-task model as everywhere else in this codebase. Occurrences are always explicitly batch-generated, never live-computed — a coordinator picks either a weekly day-of-week-and-time pattern or a plain explicit datetime list, and the system inserts the resulting rows once. Any member can sign up for an occurrence up to its capacity (first-come, no waitlist) and withdraw before it starts. A new `/shifts` page shows every upcoming occurrence grouped by series for browsing and sign-up, plus a coordinator-only management view listing each occurrence's current roster. Completion/no-show marking and the Contribution tracking integration are Phase 30's job, not this one's.

Phase 30 closes the loop on Shifts/rota — a shift occurrence's own completion signal, and Contribution tracking actually reading it. Once an occurrence's end time has passed, the signed-up member self-reports it completed (the same trust posture as everywhere else in this codebase), or the series' coordinator can mark a no-show instead — a real, logged call, never automatic. `/contribution` now shows a member's shift completions as their own entry, read together with but never folded into their task-based completed count, landing under "Overall" since a shift carries no Phase association the way a Task does — and no hours figure either, since a shift doesn't inherit a Task's Effort magnitude; completions are counted, not hour-weighted. The task detail page also gains "Rotate this task into a shift," a true one-click action available to any current holder that creates a new series pre-filled from the task (title, description, branch, capacity) while leaving the original task completely untouched — a third option alongside "mark yourself as outgoing" for a genuinely unloved task, per Coordination mechanics.

This closes out the Budget/Event scheduling/Shifts batch (Phases 25-30) in full.

Phase 31 adds Participation & capacity — core Cycle machinery, not gated behind Recruitment, since spec is explicit that even a community that never recruits new members wants to know who's actually coming. A new `Participation` table (per cycle, per member: unknown/coming/maybe/not-coming, arrival and departure dates, a note) is resubmittable as plans change, upserted in place the same way Assemblies' and Budget's own vote/response tables already are. This finally wires up `Cycle.capacity` and `Cycle.returningWindowClosesAt`, both unused since Phase 6 — a new `/participation` page shows the current cycle's remaining capacity (the plain, unclamped difference — going negative rather than blocking or queuing once it's full, since spec treats hitting zero early as an ordinary visible limit, not a special case) and whether the returning-priority window is open, purely computed from `now()` the same way Assemblies' own phase state already is. Whoever can start a cycle can also configure its capacity and window — no separate "cycle admin" concept. This also closes two real, previously-deferred lines: `/contribution` now shows the average per category across the cycle's currently `coming` members alongside a member's own picture, and `/dashboard`'s Community snapshot panel now shows a real active-member count.

Phase 32 adds Recruitment's public entry points — the first genuinely public, unauthenticated write surface this app has ever needed, and the real access-boundary change that has to come with it. Once a Community turns the "recruitment" module on, an *unrecognized* email verifying an ordinary magic link no longer silently creates a Member (the correct default while the module is off) — it's redirected to a real "no account found" page instead, while an existing member keeps logging in exactly as before either way. `CommunityInvite` gives any member a shareable, always-single-use join link (with "good fit"/"know personally" checkboxes for later evaluation logic to read); redeeming one skips the magic-link round-trip entirely — a valid, unused, unrevoked, unexpired token *is* the proof of legitimacy — and sets `referredByMemberId`/`joinedViaInviteId` on the new Member. A new public `/invite/[token]` page deliberately shows nothing about the inviting member or the community's roster, just a path to join. `Inquiry` is a genuinely low-structure "message us" box at a new public `/inquiry` page — no application form, just a message and contact info, landing in a queue visible to and claimable by whoever holds the community's designated recruitment-facing task. A new `/invites` page lets any member generate and revoke their own invite links, with an inquiry inbox section for the recruitment-task holder.

Phase 33 adds the actual evaluated-admission funnel — a public application, however many evaluators the Community assigns, and a configurable recommendation-to-outcome mapping. A new public `/apply` page renders whatever Form the Community configures as its application (`Community.recruitmentApplicationFormId`, the same pointer-to-a-Form convention post-cycle feedback already established) and submits it through a new `submitPublicFormResponse` — the one Form use case that has to work before someone's a Member at all. However many evaluators the Community assigns (`Community.recruitmentEvaluatorCount`, default 2) — resolved as whoever currently holds the recruitment task from Phase 32, not a separate assignment mechanism — each file an `Evaluation` (proceed/decline/unsure + notes) against an application on the new authenticated `/applications` page. `Community.recruitmentDecisionRules` is an ordered, community-configured list of `{conditions, outcome}` rules (first match wins, a required unconditional fallback) resolving the filed recommendations — live-computed, never persisted, since acting on a reached outcome is Phase 34's job — to `proceed`/`wider_discussion`/`decline`. An applicant can optionally reference an invite link's token on their application without redeeming it, feeding its "good fit"/"knows personally" checkboxes into the same decision rules, exactly as spec describes, without disturbing Phase 32's own unconditional invite-redemption path. A standing `RecruitmentSubscription` opt-in lets any member get alerted to new applications on `/applications` — a subscriber who isn't an evaluator sees that something's pending and its computed outcome, never the applicant's own answers.

Phase 34 adds what happens between "we have a recommendation" and "this person is fully in" — the intro call, the one real objection window, and the handoff to someone who'll accompany them. A new `RecruitmentDecision` is the real, persisted trigger point Phase 33 deliberately left uncomputed-and-unstored: the moment enough evaluators have filed, it freezes the matched rule's outcome and, for `proceed`/`decline`, resolves immediately to accepted/declined; a `wider_discussion` outcome instead opens a real time-boxed window (`Community.recruitmentWiderDiscussionHours`) that a new scheduled job auto-resolves per the rule's own `defaultResolution` — unless a subscribed member raised a real `Objection` first, in which case it waits on a recruitment-task holder's own manual call rather than the timer. Conversation scheduling reuses Scheduling polls (Phase 19) directly rather than forking it: `schedulingEntry.memberId` is now nullable with a `formResponseId` alternate, so a not-yet-a-Member applicant can be a required must-overlap participant tracked by their own application instead — a new public `/intro-call/[token]` page reuses the exact same drag-select grid the authenticated poll page already uses, so the applicant submits blind availability with no account needed, and a real slot only confirms once all three (both evaluators and the applicant) actually overlap. An acceptance auto-creates a claimable "Accompany new member" task, pre-filling a suggested accompanier from the referring invite's creator when the application named one. A configured rejection template surfaces on `/applications` next to a decline — never sent automatically.

Phase 35 adds the pipeline view that ties the whole Recruitment module together — a single, computed, never-separately-maintained view of everyone currently in flight, the same "list of people and where they are" instinct the task board already gives for tasks. Each candidate's stage (applied → evaluation in progress → call pending → call scheduled → decision pending → accepted/declined → accompaniment assigned) is read live off FormResponse/Evaluation/RecruitmentDecision/SchedulingPoll/Task state — no new stored field, and no scoring formula: alongside the candidate list, a new holder-only `/recruitment` page shows the current Cycle's remaining capacity (Phase 31) and a Tier/Branch composition breakdown as purely informational context, the same "what balanced means here is a human call" posture as everywhere else Orchard stops short of deciding for people. Candidates stuck evaluated-but-uncalled or called-but-undecided now surface as a real "needs action" section on `/dashboard` for whoever holds the recruitment task — closing Phase 24's own explicitly-deferred "recruitment-facing feed items" line.

This closes out the entire Recruitment batch (Phases 31-35) in full.

Phase 36 adds Spatial planning's foundation — the site itself (`Plot`) and its named organizational regions (`Zone`), plus the SVG-based collaborative drawing surface the rest of this module will render onto. A Plot belongs to a Cycle, not to the whole Community — `cycleId` is nullable for a Community that's never turned Cycles on at all (the same "optional association" pattern `BudgetCycle`/`EventProposal` already use for the identical reason), so nothing here silently persists across every Cycle a Community ever runs. Scale calibration (mark two points, enter the real-world distance) gets an optional extension: either point can also carry a real GPS coordinate, enough to compute a similarity transform for GeoJSON import/export without adopting a map-rendering library — entirely opt-in metadata layered on the same SVG-only editor, never a reason to draw anything differently. A new `/spatial-planning` page lets whoever holds the community's designated Spatial-planning task import a base image or vector boundary, hand-draw one from scratch, or clone a previous Cycle's Plot and its Zones wholesale as a starting point; editing goes down to the vertex level — drag to move a point, click an edge's midpoint to insert one, select-and-delete to remove one — with a live area label and a live per-edge length label, both recomputed continuously while dragging, not just after a save. Export offers a scope (one Zone or the whole Plot) and a format (an SVG image, or GeoJSON using real coordinates when the Plot is geo-anchored). Any member can view; only the Spatial-planning task holder can create or edit — the same "task is the authority" pattern this codebase already uses for Budget/Event scheduling/Recruitment.

Phase 37 adds the actual things drawn on the site — tents, vehicles, structures, furniture — sized and positioned to real-world scale, plus the profile data that informs planning them. A `Placement` is a rectangle, circle, polygon, or line at real-world scale, with a category (tent/vehicle/structure/furniture/generic — its rendered color follows category, no separate stored color field, unlike Zone) and an optional link to a Task or to zero-or-more confirmed Members (`PlacementMember`, always `confirmed` in this phase — the `invited` state and the accept/decline flow that actually uses it are Phase 38's). Rotation is a drag handle on a selected rectangle, not a typed angle — the one shape type it applies to, since a circle is rotation-invariant and a polygon/line is reshaped by moving its own points instead. A small Community-scoped `PlacementTemplate` library — seeded with common defaults, grown by saving any drawn Placement into it — lets a new Placement start from a saved shape instead of a blank draw. Phase 36's standalone cross-cycle cloning now also copies Placements: a cloned Placement's Zone link remaps onto the newly-cloned Zone, while its Task link is always dropped and it gets no linked Members at all, since neither carries a guaranteed match on this path. Export now covers Placements too, in the same image/GeoJSON choice Zone already had (a circle exports as a GeoJSON Point + radius, not an approximated polygon). Any member can view and set their own Space preferences (sleep/space arrangement, vehicle dimensions, who they'd like to be placed near, who they expect to actually share a tent/vehicle with); only the Spatial-planning task holder sees everyone's, for planning purposes.

Phase 38 adds the collaborative editing-rights layer: a Placement always stays directly editable by the Spatial-planning holder, but a confirmed `PlacementMember` or the current holder of its `linkedTaskId` can now self-service move it too — the change applies and renders immediately (dashed outline) but lands `pending` until the holder approves or reverts it. Approve keeps the new geometry; revert restores the last-confirmed one and leaves the mover a `PlacementRevertNotice` with an optional note — the one moment in this whole flow that needs real persisted state, since a revert is the only edit that leaves no other trace it happened. Sharing a Placement is now a real invite/accept/decline round trip (`syncPlacementMembers` diffs the member list on every save rather than replacing it wholesale, so accepted members keep their status across unrelated edits), and cloning a whole Cycle can now optionally carry the Spatial plan along with it — remapping each cloned Placement's `linkedTaskId` onto that same clone's freshly-cloned Task, the one clone path where that link actually survives, gated on the actor holding the Spatial-planning task specifically rather than just being cycle-initiation-eligible.

This completes the Spatial planning module (Phases 36-38) as scoped in `docs/development-plan.md`.

Phase 39 gives Cycle and Phase a real, resolvable date spine — the shared absolute/relative shape spec defines once and Task milestones/Freestanding events will reuse later. A Cycle can now carry its own optional `startDate`/`endDate`; a Phase's start and end can each independently be a hand-typed absolute date, or relative — a signed day offset from one of the Cycle's own boundaries, or a percent of the way between them — with the resolved date eagerly cached and recomputed on every write that could move it (the boundary's own recipe changing, or the anchor Cycle's own dates moving), a deliberate exception to this codebase's usual lazy-computed-on-read posture, since existing reads in `contribution.ts`/`attention/job.ts`/`profile-questions/capacity.ts` already expect a plain date column. Editing a relative boundary works two ways that land on the same stored data: type a new offset or percent directly, or give a target date to drag it to — either way, what's actually persisted is the recomputed recipe, never a bare date. A soft, non-blocking flag surfaces when an offset-mode item has drifted closer to the boundary it *isn't* anchored to; a hard check (an end can't resolve before its own start) is enforced on any direct edit, but never blocks a boundary drifting into violation because something else moved. Cloning carries the recipe, not the date: a relative boundary's mode/anchor/offset-or-percent travels forward as-is, and even a hand-dated phase gets converted into a derived offset recipe against the source cycle's own start date, so every clone produces a usable starting recommendation. The `/participation` page's Cycle-settings section now includes start/end date fields, alongside a new Phase-dates section for editing each phase's boundaries and seeing its resolved dates and any standing flags.

Phase 40 lets a Community group its Cycles into named types (Season, Reunion, Workday), mainly so a Tier can define a criterion that counts occurrences of one *kind* of cycle without a lighter gathering padding the number. A new `/settings` "Cycle types" section defines them (with an optional suggested starting Cycle — the closest thing this codebase has to a "pack" until Task Pack, as a real portable mechanism, gets built) and a Cycle can be tagged with one at creation. `Tier`'s `cycle_type_count` criterion — the fifth value its enum has been scoped for since Phase 1 — becomes the first Tier criterion this codebase actually computes (tenure/completion/cohort stay manual-assignment-only, same as before): a member's tier membership is recomputed and kept in sync automatically whenever they declare their Participation plans for a Cycle, reading how many Cycles of the configured type they've said they're `coming` to. `/profile`'s tier checkboxes now only offer manually-assigned tiers — a computed one is entirely owned by its own sync logic and shown as live progress instead (e.g. "Experienced (Season): 2/2 — earned"). Also closes a small standing note from Phase 36: the standalone spatial-plan clone picker now defaults to the most recent Cycle *of the same type* as the one being planned, ahead of a more-recent Cycle of a different type.

Phase 41 lets a task carry zero or more user-labeled dates ("Deposit due," "Order arrives") — a `TaskMilestone`, using the same absolute/relative date shape as Phase, but generalized to a 4-way anchor (a Phase's start/end, or the task's own Cycle's start/end, not just the Cycle boundary a Phase is always anchored to) since a milestone's parent can be either. Confirmation follows ownership, reusing Spatial planning's propose→pending→approve shape rather than a fourth version of it: a task's current holder adds, edits, or removes a milestone directly; anyone else's addition shows immediately but lands pending until a holder confirms or rejects it (rejecting just removes the row); an unclaimed task has no holder to gate against, so any addition confirms immediately. Unlike Phase's own boundaries, a milestone's resolved date is never cached — nothing pre-existing reads it expecting a plain column, so it stays fully live-computed on read, this codebase's default posture. Cloning a Cycle now also carries a task's confirmed relative milestones forward (a still-pending one, or an absolute one, doesn't survive the clone), remapping a Phase reference onto its newly-cloned Phase the same way Phase 39 already remaps Phase boundaries. New Milestones section on the task detail page, alongside the existing wiki/comments/resources.

Phase 42 adds Freestanding events — a personal or shared calendar entry that isn't about any one task ("applications close," "the potluck"). A `CalendarEvent` reuses the exact date shape Phase boundaries use (Phase 39): anchored to a Cycle only, never a Phase, with its resolved date cached and cascade-recomputed the same way, since (unlike Task milestones) nothing about an event needs it live-only. It always has exactly one owner, its creator — no approval step anywhere in this flow. Sharing it fans out one `CalendarEventInvite` per invitee, reusing Spatial planning's invite→accept shape (Phase 38): a single named individual, a Branch's current roster, or the whole Community in one action; each invitee independently accepts (putting it on their own calendar) or declines. Unlike Placement's own invites, a decline is a real, persisted record rather than a deleted row, so re-running a bulk invite later (to catch anyone new) skips someone who already said no rather than re-asking. "A Branch's current roster" resolves the same way Phase 24's own Branch-spread dashboard metric already does — the distinct members currently holding a task in that Branch, since no real Branch-membership roster exists anywhere in this codebase. A still-pending invite surfaces on the Dashboard, alongside a fix for the same surfacing that Spatial planning's own Phase 38 invites/pending-reviews/revert-notices turned out to need too — computed and returned since that phase, but never actually rendered on the Dashboard page itself until now. New `/calendar-events` page for creating, sharing, and responding — expected to fold into a unified Calendar view once Phase 44 lands.

Phase 43 replaces the placeholder flat nav — a single inline-styled row of ~25 links, unscoped by module or permission — with a real shell: a collapsible icon-rail on desktop (icon-only ↔ labeled+grouped, state kept in `localStorage`), a hamburger drawer on mobile, and Tailwind CSS v4 adopted project-wide as this codebase's first real UI/styling pass. Every authenticated route moved under a new `src/app/(app)/` route group (URLs unchanged), with one shared layout now doing what every one of those ~26 pages used to do for itself: check the session, compute nav state, and mount the shell. Grouping (Tasks / Calendar / Community / Modules) reuses each module's own existing enablement/holder checks rather than inventing a second permission system — a disabled module simply doesn't appear, and whoever currently holds a module's gating task (Budget, Shifts, Recruitment, Event scheduling, Conflict reports, Feedback, Spatial planning, Coordination) gets it auto-pinned to the top of the nav. A small badge on Dashboard surfaces the same personal-feed count Phase 24 already computes — no new notification schema.

Phase 44 adds the payoff view this whole calendar-work batch was building toward — one Community-wide `/calendar` reading every dated thing already in the app as its own read-only layer: Phase/Cycle boundaries, a member's own confirmed task milestones, their own calendar events, Input rounds' next cutoff, an Assembly's agenda/notice/voting windows (until it closes), a resolved Scheduling poll's confirmed slot, the published Event-scheduling programme's confirmed slots, and — `ProfileQuestion.responseType` gaining a `date` option — an opted-in birthday, recomputed to its next yearly occurrence rather than stored as a stale one-off. A real month grid plus a flat upcoming list, both server-rendered with no new client JS; Freestanding events' own create/share/respond UI (Phase 42) moves onto this page wholesale, closing that phase's own "expected to fold in" note, and `/calendar-events` is gone. The Pack-import date preview spec calls for turned up a real, load-bearing gap first: no UI anywhere had ever called `createCycle` at all, and no "review screen" existed to extend — `/participation` gains a minimal, real "start a new cycle" form (blank or clone-previous) plus a genuine non-mutating preview (calendar or list, toggled by the reviewer) showing exactly what a clone would resolve to against a hypothetical destination start/end, reusing the same recompute the real Cycle-settings form already uses — so a preview's numbers are guaranteed to match what actually lands once the clone commits and its dates get set for real. A resolved gap along the way: spec's own "Scheduling polls' deadlines" doesn't name a real field — a poll only produces one genuinely dated moment (its confirmed slot), so that's the layer, not an open-ended availability range.

## Member competences: guided tags, language proficiency, and trait-based matching

Standalone new work, not a continuation of the phase sequence above — no `docs/development-plan.md` entry, no phase number. `member.tags` had always been meant to double as skills, interests, *and* languages (`docs/spec.md`'s own member sketch said so), but only ever got built as one flat, unnormalized `text[]` a member edits at `/profile` — no vocabulary (so "Spanish"/"spanish" silently failed to match each other), no onboarding step despite spec explicitly describing one ("the member defines their own tags and availability; this is the matching input"), and no way to record a language's proficiency at all. Coordinators need this for two different jobs — finding someone with a specific skill (search) and surfacing good-fit tasks to a new member who doesn't know what to pick (ranked suggestion) — and one flat tags array can't do both well at once.

**Guided tags**: `/profile`'s tags input, and both task-tag inputs (`/propose`, proposal activation), now suggest from a combined member+task tag vocabulary (`src/lib/tags.ts`'s `listAllDistinctTags`) via a plain `<datalist>` — zero client JS, still plain free text underneath, so nothing existing that reads `member.tags`/`task.tags` needed to change.

**Language & proficiency**: a new `member_language` table (language, one of basic/conversational/fluent/native) — repeatable, unlike a `ProfileQuestion` answer, which is why it's its own table rather than a reuse. Editable at `/profile` (add/delete, no admin gate, same self-service posture as tags/contact methods). The `language` Requirement type now checks this table (case-insensitive, any level) instead of `member.tags` — a real behavior change, so every existing language-Requirement test was updated to set up a `member_language` row instead of a `tags` array.

**Trait axes — the bigger addition**: bipolar scalar dimensions (e.g. "wants direction" ↔ "wants independence"), set on *both* members (their own stated preference) and tasks (a proposer's suggestion, reviewed at activation), compared by proximity to rank onboarding's task suggestions. This is deliberately distinct from tags, which stay a search/filter tool rather than the primary suggestion signal now that axes exist. A new `trait_axis` registry (`communityId`, `key`, `lowLabel`/`highLabel`, optional 5 `optionLabels` to render labeled choices instead of a generic scale, `askAtOnboarding`, `sortOrder`, `archivedAt`) is admin-managed at `/settings`'s Profile & Privacy tab, mirroring `ProfileQuestion`'s own CRUD pattern exactly — a registry rather than hardcoded columns/enum, so the exact axis list can change without a migration. Scale convention: integer -2..2 (5-point). `member_axis_value` and `task_axis_value` hold the actual positions, one row per member/task per axis they've set — except the one axis named `commitment_preference` (one-off ↔ ongoing/ownership), which has no `task_axis_value` row at all: its task-side value is derived live from the existing `Task.effort` enum instead (`one_off`→-2, `ongoing`→0, `owns_a_thing`→+2), since duplicating what's already on every task would drift.

The Dashboard's onboarding panel gains a new "How do you like to work?" section rendering whichever `askAtOnboarding` axes this member hasn't answered yet (`listOutstandingOnboardingAxes`) — kept deliberately short (3 axes is the working default) since more than that is too much for one first-session screen; every other axis is still settable any time at `/profile`, alongside the 3 onboarding ones (re-editable there too, not one-shot). A new shared `AxisScaleField` component (plain radios, no client JS) renders either mode. Task-side suggestions reuse the in-flight `suggested*` pattern already built for `suggestedTags`/`suggestedEffort` on `TaskProposal`: a new nullable `suggestedAxisValues` jsonb column, offered on `/propose`'s "Add more, if you know it" section, shown (and fully overridable) again at activation, written into real `task_axis_value` rows by `activateProposal` — mirroring exactly how `suggestedTags` becomes `task.tags` today. Tasks created through any other path (`subtasks.ts`, recruitment's accompaniment task, scheduling-poll auto-tasks, the `/api/tasks` route) simply start with no axis values, same as they already start with empty `tags` — no new UI needed there, and a task with no axis data just doesn't contribute to axis-proximity ranking rather than breaking anything.

`listTaskFitSuggestions` (`src/lib/onboarding.ts`) changes from "tag overlap OR a satisfied individual_gate Requirement, first N matches in arbitrary query order" to computing an internal (never displayed, never serialized) score per included candidate — average proximity across every axis both sides have a value for, plus a flat boost for tag overlap and for a satisfied gate — and sorting by it before taking the top N. Inclusion is now three-way (tag overlap, gate fit, *or* at least one shared axis), a real widening from the old two-way test. This is a deliberate reversal of that function's own prior comment claiming ranked suggestion was "permanently out of scope, same line Phase 50 draws" — confirmed with the user that what's actually meant to stay out of scope is *automatic assignment*, never internal scoring used only to order a surfaced list; nothing here gates a claim or picks anyone automatically. `docs/spec.md`'s matching MVP-deferral section and its Member/Requirement/onboarding sketches were updated to say so, rather than left stating the opposite of what's now true.

**Availability** (how much time someone has *this phase*, as opposed to trait axes' stable style preferences) needed no new code at all — `ProfileQuestion.feedsCapacitySignal` plus `/coordination`'s "Availability" table already implement it end to end, just never configured for a real question in this deployment before. Kept as a distinct signal from the new `commitment_preference` trait axis on purpose: one is a fluctuating capacity number, the other is a stable "when I do take something on, do I want it quick or ongoing" preference — collapsing them would lose one or the other.

Two new migrations (`member_language`; `trait_axis`/`member_axis_value`/`task_axis_value`/`task_proposal.suggested_axis_values`), both purely additive. 22 new tests (`tests/member-languages.test.ts`, `tests/trait-axes.test.ts`, plus extensions to `tests/onboarding.test.ts` and `tests/proposals.test.ts` covering axis-ranking order, axis-only inclusion, the commitment-preference/Effort special case, and `suggestedAxisValues` flowing through activation into real rows) — 1101 total passing, `tsc`/`eslint` clean.

## Budget: line-item multipliers, per-branch tracking, a contribution balance, and a structured entry form

Standalone, not a phase — a direct response to real usage feedback (also from Leaf): budget line items had no way to express "8 tables at $50 each" or "$10 per person," proposals couldn't be broken down by which Branch they were for, and there was no way to see whether pledged contributions actually covered costs.

**Line-item multipliers** — `BudgetLineItem` (the shape shared by `BudgetCycle.fixedCosts` and `BudgetProposal.lineItems`) gains two mutually-exclusive optional fields: `quantity` (a plain manually-entered count) and `perAttendee` (scales live off however many members currently have Participation `coming` for the BudgetCycle's linked real Cycle, via a new `getBudgetCycleAttendeeCount`). New `lineItemQuantity`/`lineItemTotal`/`sumLineItems` helpers (`src/lib/budget/cycles.ts`) compute a line item's real contribution; `getBudgetVotingView` now recomputes every proposal's live total against the *current* attendee count on every read rather than trusting `budgetProposal.totalAmount`'s write-time snapshot, so a perAttendee item's contribution stays accurate as Participation answers come in, right up through confirmation. The mutual-exclusivity constraint is enforced both by a zod `.refine()` (for Server-Action callers) and by a new `requireValidLineItems` re-check inside the lib functions themselves (for direct lib callers, e.g. tests) — the zod-only version silently passed for a direct caller until a test caught it live.

**Per-Branch tracking** — any line item, fixed cost or proposal item, can now carry its own optional `branchId`, independent of (and overriding, for display) `BudgetProposal`'s own top-level default branch — covering a single proposal that spans more than one Branch. `requireValidLineItems` validates every referenced Branch belongs to the actor's Community in one batched query. The Budget page computes a live "requested/confirmed budget by branch" rollup (fixed costs plus either every currently-submitted proposal's items, or just the confirmed set once the cycle is `confirmed`) directly from already-loaded data, the same posture `fixedTotal`/`proposalsTotal` already took rather than a new lib function.

**Contribution balance** — `getBudgetVotingView` now sums every non-null `contributionSignal` vote into `totalPledged`/`pledgeCount`, and (once a cycle is `confirmed`) computes `confirmedTotal`/`confirmedBalance` against the actual funded set. Surfaced as one clear "pledges leave a $X surplus/shortfall" summary line, colored success/danger — a deliberately simpler design than an earlier per-rank "balance if funded to here" column, dropped after looking at Open Collective (open-source; leans on one always-visible balance line, not a detailed per-transaction projection) as prior art before settling on the shape.

## Forms fields can map to a Profile question, closing the application→profile gap

Standalone, not a phase — the user noticed the trait-axis sliders and Profile questions built in an earlier standalone pass (see "Member competences," above) had nowhere to be filled in, which led into a design question: shouldn't the answers someone already gives on a recruitment application (name, pronouns, an emergency contact) just become their real profile instead of being asked a second time at onboarding? `docs/spec.md`'s own Profile questions section already frames `surfaces` as open-ended ("application, onboarding, wherever") but notes recruitment's application intake was built on the separate Forms primitive instead (Phase 33) — a Form's fields are submitted together as one opaque, all-or-nothing bundle, a Question is always independently answerable, a real behavioral difference `docs/spec.md`'s Forms section draws deliberately, not an oversight. Rather than retrofitting Forms into `surfaces`, this generalizes the existing `isNameField`/`isEmailField` pattern (`src/lib/forms.ts`, Phase 48): any Form field can now name which once-ever `ProfileQuestion` its answer should seed.

**`mapsToProfileQuestionId`** — a new optional key on a Form field (alongside `isNameField`/`isEmailField`), validated at `createForm`/`updateForm` time against three rules: the referenced question must exist, belong to the same community, and be `once_ever`-scoped (`per_cycle`/`phase` questions have no cycle to stamp against at the point an applicant converts — a real, deliberate restriction, not a gap). At most one field can map to the same question, same posture as the existing name/email uniqueness check. The Settings → Forms builder (`FormBuilder.tsx`/`FieldShapeEditor.tsx`) grows a "maps to profile question" dropdown per field, populated from the community's own once-ever questions, with the same client-side dedup-on-select `updateFieldAt` already gives isNameField/isEmailField.

**Seeding at conversion** — `maybeConvertApplicantToMember` (`src/lib/recruitment/decisions.ts`) now loops every mapped field after resolving the new member, reusing `answerProfileQuestion` itself (not a parallel write path) to validate and write a real, `answered` `ProfileAnswer` from that same application value. Best-effort: a blank answer or a shape mismatch (e.g. the applicant's free text doesn't match a since-changed `single_choice` question's options) just skips that one field rather than blocking conversion — the member can always answer it directly afterward. Runs under the same `convertedMemberId` idempotency guard the rest of the function already has, so it can never double-write.

**Onboarding doesn't re-ask what it already has** — `listOnceEverAnswers` (`src/lib/profile-questions/answers.ts`) gains the same `{ surface }` narrowing `listOutstandingQuestions` already had, so the Dashboard's onboarding panel can ask for just the once-ever, onboarding-tagged questions this member already has a real answer for. New `PrefilledAnswersReview.tsx` (`"use client"`) renders that set as one compact "Already on file from your application — Pronouns: they/them · …" line with a small pencil button; clicking it swaps in a real edit form (prefilled, one field per mapped question) with Apply/Cancel, styled as a single confirmation step rather than re-litigating each question one at a time the way a genuinely outstanding question still does. New bulk action `submitOnboardingPrefilledAnswersAction` (`dashboard/actions.ts`) answers every reviewed question in one submit via repeated `answerProfileQuestion` calls — the only form in this codebase's profile-question surfaces that bundles more than one question per submit, deliberately, since the review UI presents them together even though each answer is still independently validated and written.

No schema or migration — `mapsToProfileQuestionId` is an optional key on the existing `form.fields` jsonb array. 9 new tests: `tests/forms.test.ts` (accepts a valid once-ever mapping; rejects two fields mapped to the same question, a `per_cycle`-scoped target, an archived target, a cross-community target, both at create and update time), `tests/recruitment-conversion.test.ts` (a mapped field seeds a real `ProfileAnswer` that both shows up via `listOnceEverAnswers({ surface: "onboarding" })` and is correctly excluded from `listOutstandingQuestions({ surface: "onboarding" })`; a shape-mismatched mapped field is skipped without blocking conversion), `tests/profile-questions.test.ts` (`listOnceEverAnswers`'s new surface filter) — 1118 of 1118 passing across the full suite, `tsc`/`eslint` clean.

## Board views: a view switcher, a by-phase layout, and deadline milestones

Standalone, not a phase — every numbered phase (0-69) is done, and per the user, nothing after that gets numbered; this and every entry above it that says "not a phase" is that same kind of work. Picked off a gap in `docs/spec.md`'s own Views section rather than a stretch goal spec.md ever explicitly named: that section describes four board lenses — "group by status → kanban; sort by phase/deadline → schedule; group by branch → coordinator coverage; filter by tags → what fits me" — and only the first and last were ever actually built. `/board` had a single hardcoded kanban-by-status layout the whole time; `task.phaseId` and the milestone system already carried the data a phase/deadline view needs, just never surfaced. ## Kitchen: food & drinks, as an optional module

Standalone, not a phase — picked up from `docs/roadmap.md` and specced in `docs/food-drinks-module-plan.md`; `docs/spec.md`'s "Food & drinks (Fruit)" section is the original description this restores. Off by default, like every optional module: a Community turns Kitchen on under Settings → Modules, then grants the `kitchen` permission module on a task the same way Admins, branch coordination, and the Budget owner already work. Five new tables (`menu_plan`, `meal`, `dish`, `dish_ingredient`, `food_idea`), three enums, and one new sensitive-data column, in migration `0061_busy_luminals.sql`.

**Access rides the task, and a grant is multi-cardinality.** No Kitchen role column anywhere — `isKitchenOwner`/`requireKitchenOwner` (`src/lib/kitchen/access.ts`) answer "does this member currently *hold* a task granting `kitchen`," the same holder-join every other module uses, and a cycle-less task means the standing menu while a cycle-placed one means that cycle's. Because a community may legitimately have several people cooking (weeknight cook, weekend cook, a festival rota), `kitchen` joins `admin`/`branch_coordination`/`support` in `MULTI_CARDINALITY_MODULES`: one grant is full module access *in its own scope*, and grants on different tasks never displace each other. `isKitchenOwner(actor, cycleId?)` takes the scope the way `isEventSchedulingOwner` does.

**One publish gate, not a status column.** A `MenuPlan` is a named, dated container scoped to a cycle (or the standing menu), with a single `publishedAt`: null is a draft, visible and editable only to a scope's owner; set is published, readable by the whole community and locked against every further edit — meals, dishes, ingredients, and idea adoption all funnel through one `requireEditableMenuPlan`, so "published" can't be enforced in some places and forgotten in others. A non-owner sees the newest *published* plan in their scope and can file ideas against the newest plan of any kind; a draft in progress is genuinely invisible to them, not just hidden in the UI.

**Headcounts are the core, so recipes scale into an actual shopping list.** A `Meal` carries a plain absolute date (v1), an optional phase anchor, an optional link to a shifts `ShiftSeries` for the cooking roster, and a `headCount`. Each `Dish` records the `serves` its recipe as written feeds, and `scaledIngredients` multiplies every `dishIngredient` by `headCount / serves` **on read only** — nothing is ever written back, so changing the headcount or a serving count is free and never drifts. `purchaseList` then groups those scaled amounts into a per-meal shopping list by *exact* ingredient name: two dishes' "flour" merge into one line, but "flour" and "plain flour" deliberately stay separate, because quietly merging near-synonyms is how a shopping list loses an ingredient. A meal with no headcount stays at recipe scale and computes no purchase list at all, rather than inventing one from a guessed number.

**Food ideas are attributed, persistent, and adopted in one step.** Any member can file a recipe suggestion, dish request, or preference against the active plan — open to everyone, no grant needed, deliberately *not* anonymous, since a cook often needs to ask a follow-up about a recipe. Statuses are open/adopted/declined, and `adoptFromIdea` creates the dish (`source: "from_idea"`, back-linked both ways) and flips the idea in a single transaction, so an idea can't be adopted into a menu without its dish landing.

**The dietary panel reads member data only through the sensitive-data module's own gate.** `getMealConstraintPanel` returns `null` — the panel simply doesn't render — unless the field is actually unlocked for the reader, and it re-checks active consent per read exactly as `getSensitiveDataTable` does, so a withdrawal takes effect immediately. Allergen flags are a bounded `ALLERGEN_FLAGS` const rather than a DB enum (new flags are a one-line change, not a migration), matched against members' free-text allergy fields by keyword, which catches "dairy" for a `milk` flag and "cashews" for `tree_nuts` and honestly reports "may conflict, verify" rather than pretending to be a safety guarantee.

**A third sensitive-data unlock route, which this is the first consumer of.** A field can now be unlocked by "whoever currently holds *any* task granting module X," not just one named task or one tier — `sensitiveFieldAccessRule.unlockedByGrantModuleKey`, exactly one of the three routes per rule, configured in Settings → Access & permissions. It is deliberately **community-wide**: a sensitive field is one community record, so the rule names the module and the granting task's own cycle placement does *not* narrow the unlock. That's the shape allergies→kitchen needs — a cook holding the Kitchen grant for one cycle still plans against the whole community's menu, and the module route matches per-rule, so holding a `budget` task can never satisfy a rule that names `kitchen`.

An **ordering/equipment lens** rides the same page rather than duplicating task data: open tasks in the menu's scope whose tags match the supply vocabulary (`ordering`, `equipment`, `supply`, `shopping`), with their task resources, shown only to the scope's Kitchen owner. Holders also get a Dashboard needs-action row for an unpublished draft and for open ideas waiting on a draft they own; the feed entry is module-gated and degrades to `[]` for everyone else.
