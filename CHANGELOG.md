# Changelog

The build history behind [`README.md`](README.md)'s feature list, one entry per phase of [`docs/development-plan.md`](docs/development-plan.md) — what each phase added and why it's shaped the way it is. For what's scoped next but not yet built, see the development plan itself; for the full technical spec, see [`docs/spec.md`](docs/spec.md).

Phases 0-45 are in place. Phases 0-15 are the full original phase list; Phases 16-19 close out the rest of what the tech spec treats as "core, not optional"; Phases 20-42 and 44 begin the next slice — real, designed modules from `docs/spec.md` scoped after the codebase already existed; Phases 43 and 45 are cross-cutting UI infrastructure, not spec.md modules, picked up ahead of the still-scoped-but-unbuilt Phases 46-47. Phases 0-10 cover the tech spec's full MVP scope:

- Deployable skeleton (Next.js + Drizzle + Postgres, Docker Compose, Caddy) and the core schema
- Magic-link auth with a minimal profile
- A server-enforced Task lifecycle API (claim/release/park/resume/finish, multi-slot capacity, dependency gating) and a kanban board UI to work it by hand
- Requirement-gated claiming (tier/language/completed-task/custom eligibility, enforced server-side)
- Cycle creation, blank or cloned from the previous cycle (phases and tasks included)
- A task proposal flow (bare title+description submissions, reviewed and activated onto the board)
- A task detail view carrying wiki notes (with revision history), comments, and resource links
- A settings screen for branches, tiers, and whether cycles/phases are on — no direct DB access needed
- A scheduled attention-level job flagging stale, overdue, or newly-unblocked tasks on the board automatically

Phases 11-15 add coordination mechanics beyond MVP scope:

- Subtasks — a current holder can split off a piece of a task as its own claimable card, without releasing the whole thing
- Task openness & request-to-join — claiming an already-held `request` or `coordination_approved` task now files a request the current holder(s) accept or decline, instead of an instant claim
- Admins & Community-endorsed openness — the first real access gate: `/settings` is now reachable only by a current holder of the Admins task, a real `community_endorsed` task on the board (put yourself forward, others endorse, it converts to a real claim once enough do) rather than a hardcoded role — falling back to any member until a Community's first Admins task is ever actually claimed
- Shadow slots & succession — join a task specifically to learn it (exempt from Requirements, doesn't count toward capacity), mark yourself outgoing to nudge the wiki summary before handing off, and a filled shadow slot pre-fills who a cloned cycle's task suggests next
- Remaining coordination mechanics — Requirement waiving with a required, standing-visible reason; a self-assign confirmation check for branch coordination holders (server-enforced, not just UI); an anonymous task signal and a talk-to-my-coordinator ping, both visible to that branch's coordination holders; a community-wide Escalation view; and bulk task selection (tag-based clustering, select-and-claim-with-exceptions)

Phase 16 adds Profile questions — a shared "standing fact about a member" mechanism (once-ever, per-cycle, or tied to one phase name), landing its first real use: a phase-scoped Availability question feeds a new Coordination view showing capacity-aware fitted-ask flags (has room / about right / over, or the exact declared number for members who've opted into sharing it) and who hasn't declared availability for the current phase at all.

Phase 17 adds Input rounds — small, task-specific questions (free text or closed-choice) that anyone can pose on any task at any time. Posing one queues it silently; on a fixed community-wide cadence, everything queued bundles into one round, answerable in a single sitting from a new `/input-rounds` page, and results stay visible on the task itself afterward. A round with nothing queued just doesn't fire.

Phase 18 adds Assemblies — community-wide decisions, from a genuinely urgent one-off to a slower structural question. Any member can propose one, picking their own agenda-building, notice, and voting window durations; the phase (agenda → notice → voting → closed) is always computed from those, never a separate status to keep in sync. Results are live-tallied and always visible, but never applied automatically — turning one into an actual change stays a deliberate human step through the ordinary settings screen.

Phase 19 adds Scheduling polls — "when can enough of the right people actually meet." An organizer opens a poll against a branch and a date range; members paint the windows they're free on a real click-and-drag day-by-time grid, blind — nobody, not even the organizer, sees who submitted what until a slot is confirmed, only the aggregate overlap. Two resolution modes (must overlap a fixed required list, or clear an attendance threshold) decide which slots qualify to confirm. Scheduling a poll also spins up two real tasks right away ("Facilitate…" and "Take notes & publish the summary…"), and a poll can optionally carry an open agenda and a read-tracked summary, each defaulting from its Branch's own setting, falling back to the Community's.

This closes out every phase from the plan's original list plus the "core, not optional" slice added after it.

Phase 20 adds Documentation — the one module that defaults on, same footing as Task notes rather than something a Community has to remember to enable. Freestanding `WikiPage`s carry the same revision-history shape as a task's wiki summary (any member edits, every edit is a new timestamped revision), optionally filed under a branch or left general. A page can also start as a bare question with no answer — it sits flagged unanswered until someone writes a real one, or until it's resolved as a duplicate of an existing page (dropping out of the main index, showing up on the canonical page as "also asked as…"). A new `/documentation` index browses these grouped by branch, alongside a read-only view of every task's own current wiki content — no new storage, just a different lens on data that already exists.

Phase 21 adds Conflict management — a reporting/recusal flow given real design weight, not a thin deferred afterthought. The conflict team isn't a dedicated relationship; it's just whoever currently holds a Community-designated task, same pattern as Admins and branch coordination. Filing a report takes nothing but wanting to talk to someone (no categorization or detail required up front), and recusal works from three directions — the reporter can exclude specific team members up front, and any team member can recuse themselves or a peer once a conflict of interest surfaces. The invisibility guarantee is enforced by the database query itself, not application-level filtering: an excluded team member's view of the report queue is genuinely indistinguishable from the report not existing. Acknowledging a report narrows visibility down to just the reporter and the point of contact; only the reporter can escalate it back open to the whole non-excluded team.

Phase 22 adds Sensitive data — purpose-bound, not role-bound, access to a small fixed set of member fields (health conditions, allergies, emergency contact, orientation). Off by default, and the first real use of `Community.modulesEnabled`'s on/off gating (unused since Phase 1) — later optional modules can register into the same small gate rather than each inventing their own. A Community defines which task or tier unlocks which field; a member always sees and edits their own values regardless. A new `/sensitive-data` page shows, for each field the current viewer is unlocked for, every member's value — the same "surface exactly what's relevant to what you hold" pattern `/coordination` and `/escalation` already use.

Phase 23 adds Contribution tracking — a member's own completed/active/future picture, computed live off Task/TaskAssignment, nothing entered by hand. Categories are Phases (spec's own example categories — "planning, build, live operation, wind-down" — read exactly like Phase names, so this reuses the Cycle/Phase schema rather than a second concept), merged across cycles by phase name; a phase-less task falls into a single "Overall" category. A task assigned in a phase that hasn't started yet counts as future signed-up regardless of its claim status — the same signal spec describes for Browse-period claims and later-phase assignments. A member always sees their own picture; a new opt-in toggle (off by default) lets them share it with the rest of the Community on `/contribution`.

Phase 24 adds the Dashboard — a member's home view, and the new post-login landing page (magic-link verification now lands here instead of `/profile`). A personalized feed reads live off existing state: pending join requests on tasks a member holds, upcoming check-ins on their Waiting tasks, and any currently-held task that's picked up an attention flag. An always-visible community snapshot panel shows Tier composition, Branch spread (distinct members currently holding a task per branch), and Branch health — a per-branch coarse status (*on track · attention needed · struggling*) computed entirely from existing task attention-level state, visible to everyone, with coordination-view holders additionally seeing the real flag counts behind it. Recruitment-facing items, onboarding progress, and anything Spatial-planning-dependent stay out of scope — those subsystems don't exist yet (Spatial planning is currently paused).

Phase 25 adds Forms — the last core shared primitive without a scoped consumer, landing its first real, non-Recruitment use in the same phase: post-cycle feedback. A Form's fields use the exact same free-text/single-choice/multi-choice shape Question and ProfileQuestion already use, but unlike a Question, a Form's fields are submitted together, once, as a single validated event — required fields block the whole submission. `Community.postCycleFeedbackFormId`/`feedbackReviewTaskId` name the community's standing survey and which task's holder reviews responses — the same "the task is the authority" pointer pattern Conflict management already established, not a dedicated role. A new `/feedback` page lets any member submit a response (anonymously, if the form allows it) and lets the review-task holder read every response.

Phase 26 adds the intake half of Budget — fixed costs and itemized proposals, before Phase 27 adds ranked-choice voting and confirmation on top. A `BudgetCycle` carries the non-negotiable fixed costs an admin enters up front, a proposal deadline, and an `ownerTaskId` (whoever holds that task is the budget owner, the same "the task is the authority" pattern Conflict management and post-cycle feedback already established) — only one active cycle per Community at a time for v1. Any member can submit an itemized `BudgetProposal` before the deadline, tag it to a branch, and edit it themselves until the cycle closes; a stored `totalAmount` gets recomputed on every write rather than summed on read. A new `/budget` page shows the current cycle's fixed costs and every proposal, with a submission form while proposals are open and an inline pre-filled edit form for a member's own proposals.

Phase 27 adds ranked-choice voting and confirmation — turning Phase 26's closed proposal list into an actual funded budget. Once the deadline's passed (or the owner judges the list complete), the `BudgetCycle`'s owner-task holder closes proposals to voting; any member can then submit a `BudgetVote` — a full ranking of every proposal plus an optional "how much would you contribute this year?" signal — replaceable until the owner confirms. The live voting view tallies a positional (Borda-style) score across submitted votes for the aggregate order, alongside each proposal's cost-per-member and a running total. Confirming locks in a funded set the owner chooses — informed by, not bound to, the ranking — with a rationale required only when that set actually deviates from what the ranked order alone would have funded. Once confirmed, `/budget` shows the final funded/not-funded breakdown and, for each member, the real ask against the number they signaled.

Phase 28 adds Event scheduling — a community's own internal programme, reusing the same "the task is the authority" pattern Budget/Conflict management/post-cycle feedback already established rather than inventing a new access model. Any member submits an `EventProposal` (host, title, duration, space needs, and a set of preferred slots) at any time; the `Community.eventSchedulingOwnerTaskId` holder reviews them, and every review recomputes fresh conflict flags — two proposals sharing a space with overlapping slots both get flagged, checked against whichever slots a proposal currently has (its confirmed one, once set, or its full preferred list otherwise). A flagged host can propose a different slot themselves, or the owner can ping them as a nudge, or just mediate directly and confirm a compromise slot outside what either side originally listed — ranked choice sets priorities, but the final call here is just as human. Once every currently-pending proposal is confirmed or declined, the owner publishes: a single timestamp locks them from further edits and makes them readable by every member on a new `/schedule` page, right alongside a member's own outstanding proposals and a submission form. There's no separate "the schedule" entity or cycle-wide gate — publishing just takes whatever's pending at the time, and a fresh batch can start accruing again immediately after.

Phase 29 adds the standing-structure half of Shifts/rota — recurring, never-"done" work distinct from a Task's one-shot claim/finish lifecycle. A `ShiftSeries` (optionally rotated off an existing Task, per Coordination mechanics' "genuinely unloved tasks ... rotate it") is created by any member, who becomes its coordinator automatically — or, if it names a source task, whoever currently holds that task is a coordinator too, the same access-follows-the-task model as everywhere else in this codebase. Occurrences are always explicitly batch-generated, never live-computed — a coordinator picks either a weekly day-of-week-and-time pattern or a plain explicit datetime list, and the system inserts the resulting rows once. Any member can sign up for an occurrence up to its capacity (first-come, no waitlist) and withdraw before it starts. A new `/shifts` page shows every upcoming occurrence grouped by series for browsing and sign-up, plus a coordinator-only management view listing each occurrence's current roster. Completion/no-show marking and the Contribution tracking integration are Phase 30's job, not this one's.

Phase 30 closes the loop on Shifts/rota — a shift occurrence's own completion signal, and Contribution tracking actually reading it. Once an occurrence's end time has passed, the signed-up member self-reports it completed (the same trust posture as everywhere else in this codebase), or the series' coordinator can mark a no-show instead — a real, logged call, never automatic. `/contribution` now shows a member's shift completions as their own entry, read together with but never folded into their task-based completed count, landing under "Overall" since a shift carries no Phase association the way a Task does — and no hours figure either, since a shift doesn't inherit a Task's Effort magnitude; completions are counted, not hour-weighted. The task detail page also gains "Rotate this task into a shift," a true one-click action available to any current holder that creates a new series pre-filled from the task (title, description, branch, capacity) while leaving the original task completely untouched — a third option alongside "mark yourself as outgoing" for a genuinely unloved task, per Coordination mechanics.

This closes out the Budget/Event scheduling/Shifts batch (Phases 25-30) in full.

Phase 31 adds Participation & capacity — core Cycle machinery, not gated behind Recruitment, since spec is explicit that even a community that never recruits new members wants to know who's actually coming. A new `Participation` table (per cycle, per member: unknown/coming/maybe/not-coming, arrival and departure dates, a note) is resubmittable as plans change, upserted in place the same way Assemblies' and Budget's own vote/response tables already are. This finally wires up `Cycle.capacity` and `Cycle.returningWindowClosesAt`, both unused since Phase 6 — a new `/participation` page shows the current cycle's remaining capacity (the plain, unclamped difference — going negative rather than blocking or queuing once it's full, since spec treats hitting zero early as an ordinary visible limit, not a special case) and whether the returning-priority window is open, purely computed from `now()` the same way Assemblies' own phase state already is. Whoever can start a cycle can also configure its capacity and window — no separate "cycle admin" concept. This also closes two real, previously-deferred lines: `/contribution` now shows the average per category across the cycle's currently `coming` members alongside a member's own picture, and `/dashboard`'s Community snapshot panel now shows a real active-member count.

Phase 32 adds Recruitment's public entry points — the first genuinely public, unauthenticated write surface this app has ever needed, and the real access-boundary change that has to come with it. Once a Community turns the "recruitment" module on, an *unrecognized* email verifying an ordinary magic link no longer silently creates a Member (the correct default while the module is off) — it's redirected to a real "no account found" page instead, while an existing member keeps logging in exactly as before either way. `CommunityInvite` gives any member a shareable, always-single-use join link (with "good fit"/"know personally" checkboxes for later evaluation logic to read); redeeming one skips the magic-link round-trip entirely — a valid, unused, unrevoked, unexpired token *is* the proof of legitimacy — and sets `referredByMemberId`/`joinedViaInviteId` on the new Member. A new public `/invite/[token]` page deliberately shows nothing about the inviting member or the community's roster, just a path to join. `Inquiry` is a genuinely low-structure "message us" box at a new public `/inquiry` page — no application form, just a message and contact info, landing in a queue visible to and claimable by whoever holds the community's designated recruitment-facing task. A new `/invites` page lets any member generate and revoke their own invite links, with an inquiry inbox section for the recruitment-task holder.

Phase 33 adds the actual evaluated-admission funnel — a public application, however many evaluators the Community assigns, and a configurable recommendation-to-outcome mapping. A new public `/apply` page renders whatever Form the Community configures as its application (`Community.recruitmentApplicationFormId`, the same pointer-to-a-Form convention post-cycle feedback already established) and submits it through a new `submitPublicFormResponse` — the one Form use case that has to work before someone's a Member at all. However many evaluators the Community assigns (`Community.recruitmentEvaluatorCount`, default 2) — resolved as whoever currently holds the recruitment task from Phase 32, not a separate assignment mechanism — each file an `Evaluation` (proceed/decline/unsure + notes) against an application on the new authenticated `/applications` page. `Community.recruitmentDecisionRules` is an ordered, community-configured list of `{conditions, outcome}` rules (first match wins, a required unconditional fallback) resolving the filed recommendations — live-computed, never persisted, since acting on a reached outcome is Phase 34's job — to `proceed`/`wider_discussion`/`decline`. An applicant can optionally reference an invite link's token on their application without redeeming it, feeding its "good fit"/"knows personally" checkboxes into the same decision rules, exactly as spec describes, without disturbing Phase 32's own unconditional invite-redemption path. A standing `RecruitmentSubscription` opt-in lets any member get alerted to new applications on `/applications` — a subscriber who isn't an evaluator sees that something's pending and its computed outcome, never the applicant's own answers.

Phase 34 adds what happens between "we have a recommendation" and "this person is fully in" — the intro call, the one real objection window, and the handoff to someone who'll accompany them. A new `RecruitmentDecision` is the real, persisted trigger point Phase 33 deliberately left uncomputed-and-unstored: the moment enough evaluators have filed, it freezes the matched rule's outcome and, for `proceed`/`decline`, resolves immediately to accepted/declined; a `wider_discussion` outcome instead opens a real time-boxed window (`Community.recruitmentWiderDiscussionHours`) that a new scheduled job auto-resolves per the rule's own `defaultResolution` — unless a subscribed member raised a real `Objection` first, in which case it waits on a recruitment-task holder's own manual call rather than the timer. Conversation scheduling reuses Scheduling polls (Phase 19) directly rather than forking it: `schedulingEntry.memberId` is now nullable with a `formResponseId` alternate, so a not-yet-a-Member applicant can be a required must-overlap participant tracked by their own application instead — a new public `/intro-call/[token]` page reuses the exact same drag-select grid the authenticated poll page already uses, so the applicant submits blind availability with no account needed, and a real slot only confirms once all three (both evaluators and the applicant) actually overlap. An acceptance auto-creates a claimable "Accompany new member" task, pre-filling a suggested accompanier from the referring invite's creator when the application named one. A configured rejection template surfaces on `/applications` next to a decline — never sent automatically.

Phase 35 adds the pipeline view that ties the whole Recruitment module together — a single, computed, never-separately-maintained view of everyone currently in flight, the same "list of people and where they are" instinct the task board already gives for tasks. Each candidate's stage (applied → evaluation in progress → call pending → call scheduled → decision pending → accepted/declined → accompaniment assigned) is read live off FormResponse/Evaluation/RecruitmentDecision/SchedulingPoll/Task state — no new stored field, and no scoring formula: alongside the candidate list, a new holder-only `/recruitment` page shows the current Cycle's remaining capacity (Phase 31) and a Tier/Branch composition breakdown as purely informational context, the same "what balanced means here is a human call" posture as everywhere else Orchard stops short of deciding for people. Candidates stuck evaluated-but-uncalled or called-but-undecided now surface as a real "needs action" section on `/dashboard` for whoever holds the recruitment task — closing Phase 24's own explicitly-deferred "recruitment-facing feed items" line.

This closes out the entire Recruitment batch (Phases 31-35) in full.

Phase 36 adds Spatial planning's foundation — the site itself (`Plot`) and its named organizational regions (`Zone`), plus the SVG-based collaborative drawing surface the rest of this module will render onto. A Plot belongs to a Cycle, not to the whole Community — `cycleId` is nullable for a Community that's never turned Cycles on at all (the same "optional association" pattern `BudgetCycle`/`EventProposal` already use for the identical reason), so nothing here silently persists across every Cycle a Community ever runs. Scale calibration (mark two points, enter the real-world distance) gets an optional extension: either point can also carry a real GPS coordinate, enough to compute a similarity transform for GeoJSON import/export without adopting a map-rendering library — entirely opt-in metadata layered on the same SVG-only editor, never a reason to draw anything differently. A new `/spatial-planning` page lets whoever holds the community's designated Spatial-planning task import a base image or vector boundary, hand-draw one from scratch, or clone a previous Cycle's Plot and its Zones wholesale as a starting point; editing goes down to the vertex level — drag to move a point, click an edge's midpoint to insert one, select-and-delete to remove one — with a live area label and a live per-edge length label, both recomputed continuously while dragging, not just after a save. Export offers a scope (one Zone or the whole Plot) and a format (an SVG image, or GeoJSON using real coordinates when the Plot is geo-anchored). Any member can view; only the Spatial-planning task holder can create or edit — the same "task is the authority" pattern this codebase already uses for Budget/Event scheduling/Recruitment.

Phase 37 adds the actual things drawn on the site — tents, vehicles, structures, furniture — sized and positioned to real-world scale, plus the profile data that informs planning them. A `Placement` is a rectangle, circle, polygon, or line at real-world scale, with a category (tent/vehicle/structure/furniture/generic — its rendered color follows category, no separate stored color field, unlike Zone) and an optional link to a Task or to zero-or-more confirmed Members (`PlacementMember`, always `confirmed` in this phase — the `invited` state and the accept/decline flow that actually uses it are Phase 38's). Rotation is a drag handle on a selected rectangle, not a typed angle — the one shape type it applies to, since a circle is rotation-invariant and a polygon/line is reshaped by moving its own points instead. A small Community-scoped `PlacementTemplate` library — seeded with common defaults, grown by saving any drawn Placement into it — lets a new Placement start from a saved shape instead of a blank draw. Phase 36's standalone cross-cycle cloning now also copies Placements: a cloned Placement's Zone link remaps onto the newly-cloned Zone, while its Task link is always dropped and it gets no linked Members at all, since neither carries a guaranteed match on this path. Export now covers Placements too, in the same image/GeoJSON choice Zone already had (a circle exports as a GeoJSON Point + radius, not an approximated polygon). Any member can view and set their own Space preferences (sleep/space arrangement, vehicle dimensions, who they'd like to be placed near, who they expect to actually share a tent/vehicle with); only the Spatial-planning task holder sees everyone's, for planning purposes.

Phase 38 adds the collaborative editing-rights layer: a Placement always stays directly editable by the Spatial-planning holder, but a confirmed `PlacementMember` or the current holder of its `linkedTaskId` can now self-service move it too — the change applies and renders immediately (dashed outline) but lands `pending` until the holder approves or reverts it. Approve keeps the new geometry; revert restores the last-confirmed one and leaves the mover a `PlacementRevertNotice` with an optional note — the one moment in this whole flow that needs real persisted state, since a revert is the only edit that leaves no other trace it happened. Sharing a Placement is now a real invite/accept/decline round trip (`syncPlacementMembers` diffs the member list on every save rather than replacing it wholesale, so accepted members keep their status across unrelated edits), and cloning a whole Cycle can now optionally carry the Spatial plan along with it — remapping each cloned Placement's `linkedTaskId` onto that same clone's freshly-cloned Task, the one clone path where that link actually survives, gated on the actor holding the Spatial-planning task specifically rather than just being cycle-initiation-eligible.

This completes the Spatial planning module (Phases 36-38) as scoped in `docs/development-plan.md`.

Phase 39 gives Cycle and Phase a real, resolvable date spine — the shared absolute/relative shape spec defines once and Task milestones/Freestanding events will reuse later. A Cycle can now carry its own optional `startDate`/`endDate`; a Phase's start and end can each independently be a hand-typed absolute date, or relative — a signed day offset from one of the Cycle's own boundaries, or a percent of the way between them — with the resolved date eagerly cached and recomputed on every write that could move it (the boundary's own recipe changing, or the anchor Cycle's own dates moving), a deliberate exception to this codebase's usual lazy-computed-on-read posture, since existing reads in `contribution.ts`/`attention/job.ts`/`profile-questions/capacity.ts` already expect a plain date column. Editing a relative boundary works two ways that land on the same stored data: type a new offset or percent directly, or give a target date to drag it to — either way, what's actually persisted is the recomputed recipe, never a bare date. A soft, non-blocking flag surfaces when an offset-mode item has drifted closer to the boundary it *isn't* anchored to; a hard check (an end can't resolve before its own start) is enforced on any direct edit, but never blocks a boundary drifting into violation because something else moved. Cloning carries the recipe, not the date: a relative boundary's mode/anchor/offset-or-percent travels forward as-is, and even a hand-dated phase gets converted into a derived offset recipe against the source cycle's own start date, so every clone produces a usable starting recommendation. The `/participation` page's Cycle-settings section now includes start/end date fields, alongside a new Phase-dates section for editing each phase's boundaries and seeing its resolved dates and any standing flags.

Phase 40 lets a Community group its Cycles into named types (Season, Reunion, Workday), mainly so a Tier can define a criterion that counts occurrences of one *kind* of cycle without a lighter gathering padding the number. A new `/settings` "Cycle types" section defines them (with an optional suggested starting Cycle — the closest thing this codebase has to a "pack" until Task Pack, as a real portable mechanism, gets built) and a Cycle can be tagged with one at creation. `Tier`'s `cycle_type_count` criterion — the fifth value its enum has been scoped for since Phase 1 — becomes the first Tier criterion this codebase actually computes (tenure/completion/cohort stay manual-assignment-only, same as before): a member's tier membership is recomputed and kept in sync automatically whenever they declare their Participation plans for a Cycle, reading how many Cycles of the configured type they've said they're `coming` to. `/profile`'s tier checkboxes now only offer manually-assigned tiers — a computed one is entirely owned by its own sync logic and shown as live progress instead (e.g. "Experienced (Season): 2/2 — earned"). Also closes a small standing note from Phase 36: the standalone spatial-plan clone picker now defaults to the most recent Cycle *of the same type* as the one being planned, ahead of a more-recent Cycle of a different type.

Phase 41 lets a task carry zero or more user-labeled dates ("Deposit due," "Order arrives") — a `TaskMilestone`, using the same absolute/relative date shape as Phase, but generalized to a 4-way anchor (a Phase's start/end, or the task's own Cycle's start/end, not just the Cycle boundary a Phase is always anchored to) since a milestone's parent can be either. Confirmation follows ownership, reusing Spatial planning's propose→pending→approve shape rather than a fourth version of it: a task's current holder adds, edits, or removes a milestone directly; anyone else's addition shows immediately but lands pending until a holder confirms or rejects it (rejecting just removes the row); an unclaimed task has no holder to gate against, so any addition confirms immediately. Unlike Phase's own boundaries, a milestone's resolved date is never cached — nothing pre-existing reads it expecting a plain column, so it stays fully live-computed on read, this codebase's default posture. Cloning a Cycle now also carries a task's confirmed relative milestones forward (a still-pending one, or an absolute one, doesn't survive the clone), remapping a Phase reference onto its newly-cloned Phase the same way Phase 39 already remaps Phase boundaries. New Milestones section on the task detail page, alongside the existing wiki/comments/resources.

Phase 42 adds Freestanding events — a personal or shared calendar entry that isn't about any one task ("applications close," "the potluck"). A `CalendarEvent` reuses the exact date shape Phase boundaries use (Phase 39): anchored to a Cycle only, never a Phase, with its resolved date cached and cascade-recomputed the same way, since (unlike Task milestones) nothing about an event needs it live-only. It always has exactly one owner, its creator — no approval step anywhere in this flow. Sharing it fans out one `CalendarEventInvite` per invitee, reusing Spatial planning's invite→accept shape (Phase 38): a single named individual, a Branch's current roster, or the whole Community in one action; each invitee independently accepts (putting it on their own calendar) or declines. Unlike Placement's own invites, a decline is a real, persisted record rather than a deleted row, so re-running a bulk invite later (to catch anyone new) skips someone who already said no rather than re-asking. "A Branch's current roster" resolves the same way Phase 24's own Branch-spread dashboard metric already does — the distinct members currently holding a task in that Branch, since no real Branch-membership roster exists anywhere in this codebase. A still-pending invite surfaces on the Dashboard, alongside a fix for the same surfacing that Spatial planning's own Phase 38 invites/pending-reviews/revert-notices turned out to need too — computed and returned since that phase, but never actually rendered on the Dashboard page itself until now. New `/calendar-events` page for creating, sharing, and responding — expected to fold into a unified Calendar view once Phase 44 lands.

Phase 43 replaces the placeholder flat nav — a single inline-styled row of ~25 links, unscoped by module or permission — with a real shell: a collapsible icon-rail on desktop (icon-only ↔ labeled+grouped, state kept in `localStorage`), a hamburger drawer on mobile, and Tailwind CSS v4 adopted project-wide as this codebase's first real UI/styling pass. Every authenticated route moved under a new `src/app/(app)/` route group (URLs unchanged), with one shared layout now doing what every one of those ~26 pages used to do for itself: check the session, compute nav state, and mount the shell. Grouping (Tasks / Calendar / Community / Modules) reuses each module's own existing enablement/holder checks rather than inventing a second permission system — a disabled module simply doesn't appear, and whoever currently holds a module's gating task (Budget, Shifts, Recruitment, Event scheduling, Conflict reports, Feedback, Spatial planning, Coordination) gets it auto-pinned to the top of the nav. A small badge on Dashboard surfaces the same personal-feed count Phase 24 already computes — no new notification schema.
